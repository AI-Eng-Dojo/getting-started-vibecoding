# ADR の書式

ADR は `docs/adr/` に置き、連番で命名します。`0001-slug.md`、`0002-slug.md` のように。

`docs/adr/` ディレクトリは遅延的に作成してください。最初の ADR が必要になったときにだけ作ります。

## テンプレート

```md
# {決定の短いタイトル}

{一〜三文: どんな背景で、何を決め、なぜそう決めたか。}
```

これだけです。ADR は一段落で構いません。価値があるのは、決定が下されたという*事実*と、その*理由*を記録することであって、項目を埋めることではありません。

## 任意のセクション

本当に価値を足すときにだけ含めてください。ほとんどの ADR には不要です。

- **Status** フロントマター(`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 決定を後から見直す場合に有用
- **検討した選択肢** — 却下した代替案を憶えておく価値があるときだけ
- **影響** — 自明でない波及効果を明示する必要があるときだけ

## 採番

`docs/adr/` を走査して既存の最大番号を調べ、一つ増やしてください。

## ADR を提案すべきとき

次の三つがすべて満たされる必要があります。

1. **元に戻しにくい** — あとで考えを変えるコストが無視できない
2. **背景がないと不可解** — 将来の読み手がコードを見て「なぜこんなやり方をしたのか」と首をかしげる
3. **本物のトレードオフの結果** — 実在する選択肢があり、具体的な理由で一つを選んだ

簡単に元に戻せる決定なら、記録は不要です。どうせ戻すのですから。不可解でないなら、誰も理由を疑問に思いません。実在する代替案がなかったなら、「当たり前のことをした」以上に記録すべきものはありません。

### 該当するもの

- **アーキテクチャの形。** 「モノレポを採用する。」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres へ投影する。」
- **コンテキスト間の連携パターン。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する。」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダー、デプロイ先。すべてのライブラリではなく、差し替えに四半期かかるようなものだけ。
- **境界とスコープの決定。** 「顧客データは Customer コンテキストが所有し、他のコンテキストは ID でのみ参照する。」*やらない*と決めたことは、*やる*と決めたことと同じくらい価値があります。
- **あえて定石を外した判断。** 「X の理由で ORM ではなく手書き SQL を使う。」まともな読み手なら逆を想定するようなものすべて。これがあれば、次のエンジニアが意図的な設計を「修正」せずに済みます。
- **コードに現れない制約。** 「コンプライアンス要件により AWS は使えない。」「パートナー API の契約上、応答時間は 200ms 未満でなければならない。」
- **却下の理由が自明でない代替案。** GraphQL を検討したうえで微妙な理由で REST を選んだなら、記録してください。さもないと半年後に誰かがまた GraphQL を提案します。
