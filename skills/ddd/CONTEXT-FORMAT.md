# CONTEXT.md の書式

## 構造

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するのかを一〜二文で。}

## 言葉

**Order(注文)**:
{その用語を一〜二文で説明する}
_避ける_: Purchase、transaction

**Invoice(請求書)**:
納品後に顧客へ送る支払いの請求。
_避ける_: Bill、payment request

**Customer(顧客)**:
注文を行う個人または組織。
_避ける_: Client、buyer、account
```

## ルール

- **意見を持つこと。** 同じ概念に複数の言葉があるなら、最良の一つを選び、残りを `_避ける_` に列挙してください。
- **定義は締まった短さで。** 最大でも一〜二文。それが何を*する*かではなく、何で*ある*かを定義します。
- **このプロジェクトのコンテキスト固有の用語だけを含めること。** 一般的なプログラミング概念(タイムアウト、エラー型、ユーティリティのパターンなど)は、プロジェクトで多用されていても含めません。用語を追加する前に問うてください。これはこのコンテキスト固有の概念か、それとも一般的なプログラミング概念か。前者だけが対象です。
- **自然なまとまりが現れたら小見出しでグループ化すること。** すべての用語が一つのまとまった領域に属するなら、フラットな一覧のままで構いません。

## 単一コンテキストと複数コンテキスト

**単一コンテキスト(ほとんどのリポジトリ):** リポジトリのルートに `CONTEXT.md` を一つ置きます。

**複数コンテキスト:** リポジトリのルートに置いた `CONTEXT-MAP.md` が、コンテキストの一覧、所在、相互の関係を示します。

```md
# コンテキストマップ

## コンテキスト

- [Ordering](./src/ordering/CONTEXT.md) — 顧客の注文を受け付け、追跡する
- [Billing](./src/billing/CONTEXT.md) — 請求書を発行し、支払いを処理する
- [Fulfillment](./src/fulfillment/CONTEXT.md) — 倉庫のピッキングと出荷を管理する

## 関係

- **Ordering → Fulfillment**: Ordering が `OrderPlaced` イベントを発行し、Fulfillment がそれを受けてピッキングを開始する
- **Fulfillment → Billing**: Fulfillment が `ShipmentDispatched` イベントを発行し、Billing がそれを受けて請求書を発行する
- **Ordering ↔ Billing**: `CustomerId` と `Money` の型を共有する
```

どちらの構造かは、このスキルが次のように推定します。

- `CONTEXT-MAP.md` があれば、それを読んでコンテキストを見つける
- ルートに `CONTEXT.md` だけがあれば、単一コンテキスト
- どちらもなければ、最初の用語が確定した時点でルートに `CONTEXT.md` を遅延作成する

複数のコンテキストが存在する場合は、いま話している話題がどれに関係するかを推定してください。判断がつかなければ、ユーザーに尋ねてください。
