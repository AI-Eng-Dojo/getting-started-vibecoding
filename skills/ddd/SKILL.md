# ドメインモデリング

設計を進めながら、プロジェクトのドメインモデルを能動的に構築し、磨き上げてください。これは*能動的*な営みです。用語に異議を唱え、エッジケースのシナリオを考え出し、用語集と決定が固まったその瞬間に書き留めます。(語彙を確認するために `CONTEXT.md` を*読むだけ*なら、それはこのスキルではありません。どのスキルでもできる一行の習慣です。このスキルは、モデルを消費するときではなく、モデルを変更するときのためのものです。)

## ファイル構成

ほとんどのリポジトリはコンテキストが一つです。

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` があれば、そのリポジトリは複数のコンテキストを持っています。マップは各コンテキストの所在を示します。

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延的に作成してください。書くべき内容ができたときにだけ作ります。`CONTEXT.md` が存在しなければ、最初の用語が確定した時点で作成します。`docs/adr/` が存在しなければ、最初の ADR が必要になった時点で作成します。

## セッション中にすること

### 用語集に照らして異議を唱える

`CONTEXT.md` にある既存の言葉遣いと矛盾する用語をユーザーが使ったら、その場で指摘してください。「用語集では『キャンセル』を X と定義していますが、いまは Y の意味で使っているように見えます。どちらでしょうか?」

### 曖昧な言葉を鋭くする

ユーザーが曖昧な用語や多義的な用語を使ったら、正確な正式名称を提案してください。「『アカウント』とおっしゃいましたが、それは Customer ですか、User ですか。この二つは別物です。」

### 具体的なシナリオで検討する

ドメインの関係性が話題になったら、具体的なシナリオでストレステストしてください。エッジケースを突くシナリオを考え出し、概念同士の境界について正確な回答を引き出します。

### コードと突き合わせる

ユーザーが「こう動く」と述べたら、コードが同意しているか確認してください。矛盾を見つけたら、必ず表に出します。「コードは Order 全体をキャンセルしていますが、いま部分キャンセルが可能だとおっしゃいました。どちらが正しいですか?」

### CONTEXT.md をその場で更新する

用語が確定したら、その場で `CONTEXT.md` を更新してください。まとめて後回しにせず、起きたその瞬間に記録します。書式は [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) に従ってください。

`CONTEXT.md` には実装の詳細を一切含めないでください。`CONTEXT.md` を仕様書、走り書き、実装上の決定の置き場として扱ってはいけません。あくまで用語集であり、それ以外の何物でもありません。

### ADR は控えめに提案する

次の三つがすべて満たされるときにだけ、ADR の作成を提案してください。

1. **元に戻しにくい** — あとで考えを変えるコストが無視できない
2. **背景がないと不可解** — 将来の読み手が「なぜこうしたのか」と疑問に思う
3. **本物のトレードオフの結果** — 実在する選択肢があり、具体的な理由で一つを選んだ

一つでも欠けるなら、ADR は作りません。書式は [ADR-FORMAT.md](./ADR-FORMAT.md) に従ってください。
