# 2軸コードレビュー

**「動いている」は、レビューを通ったという意味ではありません。** 別々の2つの質問に、別々に答えてください。

| 軸 | 質問 |
|---|---|
| **仕様どおりか（Spec）** | 頼まれたものを作ったか。頼まれていないものを作っていないか |
| **作法どおりか（Standards）** | このプロジェクトの決めごとと、読みやすさの基本に沿っているか |

## この2つを混ぜてはいけません

片方が片方を隠すからです。

- **作法は完璧だが、違うものを作っている** → Standards合格・Spec不合格
- **頼まれたとおりだが、書き方が散らかっている** → Spec合格・Standards不合格

1本のリストにまとめると、この状態が見えなくなります。**報告は最後まで2つに分けたままにしてください。** どちらが重要かの順位付けもしません。

## 最初に守ること

**勝手に直さないでください。** まず報告だけをします。何を直すかはユーザーが決めます。承認を受けてから修正に入ってください。

**セキュリティはこのスキルの対象外です。** 秘密情報の直書き、入力の未検証な使用、外部への通信などは `security-review` の担当です。ここで見つけても報告に混ぜず、「セキュリティレビューでも見てください」と一行添えるだけにしてください。**`.claude/security-reviewed` を作成・削除してはいけません。** あの印は `security-review` だけが扱います。

## レビューする範囲を決める

ユーザーが基準点（ブランチ名・コミット・`main` など）を指定していればそれを使い、`git diff <基準点>...HEAD` で差分を取ります。

指定がなければ、**今日変更されたファイル**を対象にしてください。それも分からなければ、対象をユーザーに確認します。**リポジトリ全体を読み直さないでください。**

---

## 軸1: 仕様どおりか（Spec）

### 仕様の出どころ

次の順で探し、見つかった最初のものを仕様として扱います。

1. `README.md` の「できること」「完成判定」「今回やらないこと」
2. `TASKS.md` の各項目と「完了定義」
3. 上のどちらも無ければ、**「仕様が見つからないため、この軸はレビューできません」と報告**してください。推測で仕様を作らないこと

### 報告する3種類

- **足りない・途中まで**: 仕様に書かれているのに、実装されていない／条件の一部しか満たしていない
- **頼まれていないもの**: 仕様に無いのに実装されている機能。**「今回やらないこと」に書かれているものが実装されていたら、これは重い指摘です**
- **取り違え**: 実装はされているが、仕様が求めているものと意味が違う

**必ず仕様の該当箇所を引用してください。** 「READMEにこう書いてある」の一行があるかどうかで、指摘の説得力が変わります。

---

## 軸2: 作法どおりか（Standards）

### 決めごとの出どころ

`CLAUDE.md`・`CONTEXT.md`・その他プロジェクト内の取り決めがあれば、**それが最優先**です。書かれていることと、下のベースラインが食い違ったら、書かれているほうに従ってください。

`CONTEXT.md`（用語集）がある場合は、**コードの中の名前が用語集と一致しているか**を必ず見てください。会話とコードで違う言葉を使っているのは、あとで必ず効いてくるズレです。

### ベースライン（決めごとが無いとき、または加えて見るとき）

- **名前が意味を表していない** — 読んで何をするか分からない関数名・変数名
- **同じことが何度も書かれている** — コピーして少し変えた塊が2箇所以上ある
- **同じ判定が散らばっている** — 同じ条件分岐が複数の場所に現れる
- **1つの変更が何箇所にも散る** — 1つの仕様を変えるのに、離れた場所を何箇所も直す必要がある
- **使われていない一般化** — 仕様が求めていない汎用性のために複雑になっている
- **長いつなぎ** — `a.b().c().d()` のように、呼び出し側が知らなくていい内部構造に依存している

**すべて判断の問題であって、違反ではありません。** 「こう直すべき」ではなく「こうしたほうが読みやすい、理由はこれ」の形で書いてください。整形ツールが自動で直すこと（インデント・空白・引用符）は指摘しないでください。

## 報告の形式

```
## 仕様どおりか（Spec）

### ⟨足りない／頼まれていない／取り違え⟩ 短い見出し
- 場所: ファイル名:行番号
- 仕様には: ⟨README.md や TASKS.md からの引用⟩
- 実装は: ⟨実際にどうなっているか⟩
- どうするか: ⟨提案⟩

## 作法どおりか（Standards）

### ⟨観点名⟩ 短い見出し
- 場所: ファイル名:行番号
- 何が読みにくいか: ⟨具体的に⟩
- どう書き直すか: ⟨提案⟩
```

最後に**1行だけ**サマリを書きます。

```
仕様: 指摘◯件（最も重いのは⟨…⟩） / 作法: 指摘◯件（最も重いのは⟨…⟩）
```

**軸をまたいで「総合的にどうか」を書かないでください。** 2つの別々の答えを、別々のまま返すのがこのスキルの仕事です。

## やってはいけないこと

- 2つの軸を1本のリストにまとめること
- 仕様が見つからないのに、推測した仕様でSpec軸を書くこと
- 承認を得る前にコードを書き換えること
- セキュリティの指摘を混ぜること、`.claude/security-reviewed` に触れること
- 指摘が0件のときに「問題ありません」だけで終わること。**どの軸で何を見たかを書いてください**
