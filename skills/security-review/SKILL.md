# セキュリティレビュー

このプロジェクトのコードを読み、**危ないところを見つけて報告してください。**

## 最初に守ること

**勝手に直さないでください。** まず報告だけをします。何を直すかはユーザーが決めます。承認を受けてから修正に入ってください。

見つからなかったときも「問題ありません」だけで終わらせないこと。**どの観点を、どのファイルのどこを見て、そう判断したのか**を書いてください。見ていないものを「問題なし」と言わないためです。

## 必ず見る観点

上から順に確認してください。この順番は「実害の出やすさ」順です。

### 1. 秘密情報がコードに書かれていないか

APIキー、パスワード、アクセストークン、接続文字列。**これが最悪です。**ファイルを他人に渡した瞬間、あるいは公開リポジトリに置いた瞬間に漏れます。

「見つけたら書き換えれば済む」ではありません。**一度でも共有・公開したものは、その値を無効化して作り直す必要がある**ことまで報告に書いてください。

### 2. ユーザーが入力した文字が、そのまま画面に埋め込まれていないか

`innerHTML`、`insertAdjacentHTML`、`document.write` に、ユーザー入力や外部から来たデータを**文字列連結で**渡している箇所を探します。入力欄に書いたものがそのままHTMLとして解釈されると、他人が仕込んだ内容を実行させられます（XSS）。

安全な形は `textContent` を使うことです。HTMLの組み立てが必要なら要素を1つずつ作ります。

> 定数だけを埋め込んでいる場合は今すぐの実害はありません。ただし**そこに変数が1つ混ざった瞬間に穴になる**ので、「今は安全だが直しておくと安心」として報告してください。

### 3. 文字列をそのまま実行していないか

`eval`、`new Function`、`setTimeout` に文字列を渡す形。ほぼ常に別の書き方があります。

### 4. 保存しているデータは、そこに置いてよいものか

`localStorage` やCookieに何を入れているかを見てください。ブラウザに保存したものは**同じPCを使う人なら誰でも読めます。**

- 名前・住所・連絡先・健康の記録など、他人に見られたくないものが入っていないか
- そもそも保存する必要があるものか

### 5. 外部への通信が入っていないか

`fetch`、`XMLHttpRequest`、外部の `<script src>` や `<link href>`、フォームの送信先。

- **どこへ、何を送っているか**を具体的に書いてください
- ユーザーが頼んでいない送信先が入っていたら、それだけで重大です
- 外部から読み込むスクリプトは、その提供元を信用することと同じ意味になります

### 6. 外部リンクの開き方

`target="_blank"` のリンクに `rel="noopener"` が付いているか。付いていないと、開いた先のページから元のページを操作できてしまいます。

### 7. このファイルを他人に渡して困らないか

最後に一度、**「これをそのまま人に見せたら困るものが残っていないか」**という目で全体を見てください。書きかけのメモ、実在の個人名、社内の情報、テスト用のアカウント。

### 8. 公開するフォルダに、公開してよいものだけが入っているか

このプロジェクトを実際にインターネットへ公開する（ホスティングサービスへアップロードする）場合、**そのフォルダの中身は全部、URLを知っている人なら誰でも取得できます。**

公開対象のフォルダ（`public/`・`dist/` など、設定ファイルで指定されているディレクトリ）を開いて、次が混ざっていないかを確認してください。

- 仕様書・やることリスト・議事録・書きかけのメモ
- 設定ファイル（`.claude/`・`.env`・`.git/`）
- 実在の個人名・連絡先・社内の情報
- テスト用のアカウントやサンプルデータ

**「アプリが読み込まないから安全」ではありません。** そこに置いてあれば、直接URLを打てば取れます。公開対象の指定が「フォルダ全体」になっていたら、それ自体を**重大度・高**として報告してください。

## 報告の形式

見つかった順ではなく、**重大度の高い順**に並べてください。

```
### [重大度] 短い見出し
- 場所: ファイル名:行番号
- 何が起きるか: 誰が、何をすると、どうなるか（具体的に）
- どう直すか: そのまま適用できる修正案
```

重大度は3段階にします。

| 重大度 | 意味 |
|---|---|
| **高** | 秘密情報の漏洩、他人のデータが読める、任意のコードが実行される |
| **中** | いまは実害がないが、少し変更が入ると穴になる |
| **低** | 作法の問題。直すと安心だが急がない |

最後に、**確認したが問題がなかった観点**を数行で書いてください。「1・3・5は該当箇所なし（外部通信のコードは1つもない）」のように、何を見たかが分かる形にします。

## やってはいけないこと

- 見ていない観点を「問題なし」に含めること
- 重大度を実態より高く盛ること。全部「高」にすると、本当に高いものが埋もれます
- 承認を得る前にコードを書き換えること

## レビューが終わったら

報告を出し終えたら、**`.claude/security-reviewed` という空ファイルを作成（touch）してください。** フォルダが無ければ作ります。

これは「このコードはセキュリティレビューを一度通った」という印です。プロジェクトによっては、`git push` や公開の直前にこの印を確認し、**無ければ処理を止める**仕組み（Hooks）が設定されています。

- 報告を出さずに印だけ作ってはいけません
- 重大度・高の指摘を出した場合も、**報告を出したこと自体は事実なので印は作ります。** 直すかどうかはユーザーが決めます
- コードが変更されると、この印は別の仕組みによって自動的に消えます。**印を消すのはこのスキルの仕事ではありません**
