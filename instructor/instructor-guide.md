# 講師・メンター用進行ガイド

参加者には配布しない。運営の判断基準と台本の要点をまとめる。

> 2026-08-23改訂。前編は「AI駆動開発の3原則（型で渡す／作る前に計画を見る／曖昧なまま作らせない）」構成。
> 旧構成（見て、直す／リカバリー3手／言語化ワーク／ライブデモ）は前編から外し、リカバリー3手は後編8に移設した。

## 体制と機材

- 講師1名＋メンター（参加者8名につき1名目安）
- **講師・メンター機は全員Maxプラン必須**（救済ペア作業で枠を貸すため）
- 会場共有タイマー（後編8の15分チェックポイント合図用）
- 提出フォーム2種: チェックポイント0（事前スクショ）、チェックポイント4（「詰めて」の結果）
- 救済タグ入りリポジトリ（このリポジトリ。配布URLは案内メールに記載）
- **事前配布のデモ動画（10分）**。前編にライブデモ枠はないので、これが唯一の「講師が作るところを見る」機会になる。未視聴者が多い回は前編2の冒頭で2分だけ画面を見せる

## 設計思想（新任メンター向け）

1. **座学は合計30分以内。** オープニング10分＋前編3のスキル解説8分＋後編7の10分でほぼ使い切る。説明したくなったら「それはコラム○番に書いてある」と言って先へ進む
2. **前編2（テトリス）は速さを見せるだけの枠。** ここで品質の話をしない。「3行で動くものが出た」という事実だけ全員に共有させて次へ行く
3. **前編3が今日の主役。** 参加者が持ち帰る最大の資産はスキルファイル1枚。ここだけは時間を削らない
4. **戻ることを正規の技術として教える。** 救済タグ利用やバックアップ復帰を「失敗」の空気にしない。声かけは常に「戻って進むのは正規の技です」
5. **利用枠はProで完走できる設計。** ただし作法（まとめ指示・当日温存）が守られている前提。乱れたら個別に軌道修正する

## 参加者構成と座席戦略（想定: 20名＝エンジニア10・Claude Code初心者の起業家10）

**テーブルは同質で分ける**（エンジニア島×2・起業家島×2）。混成ペアにしない。

- 理由: 混成にするとエンジニアが隣のキーボードを「代わりに」触り始め、起業家の手が止まる。本ワークショップの価値は自分の手で回した経験なので、これは最悪の失敗パターン
- メンター配分は起業家島に厚く（起業家島は5名に1人、エンジニア島は10名に1人目安）
- 交流は共有タイム（後編10）で設計的に起こす。発表者はエンジニア・起業家から最低1名ずつ選び、「同じ型で両方が完成した」ことを見せるのがクロージングの説得力になる

進度差の吸収は🚀拡張ミッションが担う。エンジニアは本線を速く終えるので、拡張ミッション〔Eng〕（スキルの3分割・チケット運用・Git運用・検証の自動化）へ誘導する。**本線の先回りは止める**——後続の説明が二度手間になるため。

> 注意: エンジニアはターン消費も速い。`/status` 巡回では**エンジニア島の残量をむしろ警戒**する。
> 拡張ミッションはターン消費が少ない題材（スキルの分割・計画の読み込み・チケット起票）を意図的に選んである。

## 待ち時間マイクロ解説ネタ集（コスト・ゼロの座学枠）

参加者は生成待ちで合計30〜40分アイドルする。会場全体が「待ち」に入った瞬間に1枚スライドで挟む。**1本90秒以内・手を動かし始めた人がいたら即打ち切り**が鉄則。座学30分制限の外側で解説量を稼ぐ仕掛けなので、長話にした瞬間に本末転倒になる。

| # | ネタ | 差し込みどころ | 要点 |
|---|---|---|---|
| W1 | いまClaudeは何をしているか | 前編2の最初の生成待ち | 指示→計画→ファイル操作→確認のループを回している。画面のツール実行表示の読み方 |
| W2 | 権限プロンプトの裏側 | 前編2で権限質問が出た頃 | 許可は記憶され、同種の操作は聞かれなくなる。「全部許可」モードは便利だが今日は使わない理由 |
| W3 | descriptionはいつ読まれるか | 前編3のスキル生成待ち | Claudeは会話のたびに全スキルのdescriptionだけを見て、使うものを決めている。だから「いつ使うか」を書く |
| W4 | スキルが読まれたかの見分け方 | 前編3の動作確認中 | 画面のスキル起動表示。読まれていないときの切り分け手順（置き場所・name・description の順に疑う） |
| W5 | モデルとeffort | 前編4の計画生成待ち | `/model` で切替可。計画は深く、実装は速く。★1の予告 |
| W6 | プランモードなら仕組みで止まる | 前編4の実装待ち | いまは指示文でお願いしているが、機能として強制できる。★2の予告 |
| W7 | コンテキストという概念 | 前編4の後半 | 会話が長くなると古い指示は薄れる。だから CLAUDE.md とスキルに置く。★3の予告 |
| W8 | 利用枠の仕組み | 後編開始直後の `/status` 時 | 5時間ウィンドウ＋週次の二重構造。まとめ指示が枠の節約にもなっている |
| W9 | 「幻覚したgreen」実例 | 後編8の中盤の生成待ち | 「できました」と言って確認していなかった実例を1枚見せる。後編9の検証プロンプトの伏線 |
| W10 | スキル・スペック・任せきるの3段地図 | 後編8の終盤 | 今日の型がそのまま自律開発の入力になる。クロージングの予告編 |

運用メモ: 全部やる必要はない。**W2・W3・W9は必須**（安全・スキルの核心・検証の3本柱）、残りは会場の待ちの発生に合わせて取捨。

## 事前準備期間の運営

- チェックポイント0の提出状況を前日夜に集計。未提出者には個別連絡＋当日30分前のサポートタイム招集
- 提出スクショで環境の偏り（デスクトップアプリ/CLI、OS）を把握し、メンター配置に反映
- **開催3日前**: 00-prep.md 末尾の運営メモに従い、外部情報（プラン名・価格・配布URL・CLIインストール手順・Node要件・対応OS・利用枠仕様）の変更を確認
- **開催前**: `git push origin --tags` で救済タグを公開。未pushだとZIP参加者の救済ルートが404になる（ここは毎回確認すること）

### 「詰めて」の進み具合レビュー基準（メンター用）

休憩中に全数チェックし、該当者には休憩明けに一声かける。

- **大きすぎ**: 詰めた結果、完成条件が5個以上要りそう／「管理できる」「共有できる」など動詞が複数系統 → 「後編は⟨最初の1動詞⟩だけにしよう」
- **確認できない**: 「使いやすい」「いい感じに」など目で確認できない条件 → 「画面で何が見えたらOK?」と聞いて書き直させる
- **データが外部**: 外部サービスのAPIやログインが必要 → 「今日は手入力またはダミーデータで」に誘導（★8の領域は今日は踏まない）
- **質問に答えていない**: Claudeの質問に「おまかせします」を連発している → **原則③が崩れているサイン。**「決めるのはあなた」をもう一度説明し、1問だけ一緒に答える

## 時間が押したときの切り方（優先順）

1. 9のステップ2「見た目をもう一段」を切る（→共有タイムの見栄えは下がるが本質は守られる）
2. 10の発表を3名→2名に減らす
3. 4（中級課題）の完成条件を3つ→2つに減らす
4. 3の「答え合わせ」（skills/との比較）を口頭紹介のみにする
5. **切ってはいけないもの**: 3のスキル動作確認、4の「計画を読んでから許可」、5の詰めて3問、9のステップ1（検証）、8の15分チェックポイント運用

> 3と4を削ると当日の主題（型・計画）が消える。押しているときほどここは守る。

## トラブル対応表

| 事象 | 対応 |
|---|---|
| 利用枠の上限到達（Pro） | メンター機（Max）でペア作業。本人に操作させ、メンターは枠を貸すだけ。5時間ウィンドウのローリング回復も案内 |
| スキルが読み込まれない | 置き場所（`.claude/skills/⟨名前⟩/SKILL.md`）→ フロントマターの `name` がフォルダ名と一致しているか → `description` に起動条件が書かれているか、の順で切り分ける。それでもダメなら `skills/` の完成形をコピーさせて先へ進める |
| 計画を読まずに実装させてしまった | 止めない。**そのまま進ませて詰まらせる。**詰まった時点で「計画を読んでいたら防げた」を体験させるほうが効く。時間がなければ救済タグへ |
| 中級課題が45分で終わらない | 正常。完成条件2つで合格。**全部終わらせようとさせない** |
| 「詰めて」の質問が止まらない | 3問答えたら「いったんここまで」と切ってよい。後編8の冒頭で続きができる |
| 全体的に応答が遅い（障害・混雑） | 事前配布のデモ動画に切り替え。ハンズオンは待ち時間にゴールの下書き（templates/goal-sheet.md）記入を前倒しする |
| 環境が完全に壊れた参加者 | Claude Code Web版（ブラウザ実行）に切り替えて継続 |
| アイデア乗り換えを始めた参加者 | 「メモして持ち帰る」に誘導。乗り換えは迷子の最大要因という理屈まで伝える |
| 早く終わった参加者 | 該当ハンズオンの🚀拡張ミッションへ誘導（エンジニアは〔Eng〕系）。本線の先回りは止める。メンター補助役を頼むのも可 |

## 実測データの収集（次回改善と書籍用）

各回で記録する:

- チェックポイント通過率（0〜6の各段階）
- **前編3でスキルが一発で動いた人の割合**（この回の成否を最もよく表す指標）
- 上限到達者数とその時刻・プラン内訳
- 参加者の平均ターン数の聞き取り（任意アンケート）
- 詰まりポイントのカテゴリ集計（環境／指示／スキル／計画／枠）

> 書籍の申し送り「第8〜9章はコスト・実行時間の実測値を必ず載せる」と同様、
> ワークショップも実測で改訂する。アンケートに「かかった費用感の納得度」を1問入れる。
