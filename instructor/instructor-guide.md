# 講師・メンター用進行ガイド

参加者には配布しない。運営の判断基準と台本の要点をまとめる。

## 体制と機材

- 講師1名＋メンター（参加者8名につき1名目安）
- **講師・メンター機は全員Maxプラン必須**（救済ペア作業で枠を貸すため）
- 会場共有タイマー（後編の15分チェックポイント合図用）
- 提出フォーム2種: チェックポイント0（事前スクショ）、チェックポイント3（ゴールの一文）
- 救済タグ入りスターターリポジトリ（このリポジトリ。配布URLは案内メールに記載）

## 設計思想（新任メンター向け）

1. **座学は合計30分以内。** 説明したくなったら「それはコラム○番に書いてある」と言って先へ進む
2. **タイトル回収は後編9。** 「確実にできあがる」の証明は検証パートなので、時間が押しても9のステップ1（Claudeに検証させる＋自分の目で確認）だけは絶対に切らない
3. **戻ることを正規の技術として教える。** 救済タグ利用やバックアップ復帰を「失敗」の空気にしない。メンターの声かけは常に「戻って進むのは今日教えた技です」
4. **利用枠はProで完走できる設計。** ただし作法（まとめ指示・当日温存）が守られている前提。乱れたら個別に軌道修正する

## 参加者構成と座席戦略（想定: 20名＝エンジニア10・Claude Code初心者の起業家10）

**テーブルは同質で分ける**（エンジニア島×2・起業家島×2）。混成ペアにしない。

- 理由: 混成にするとエンジニアが隣のキーボードを「代わりに」触り始め、起業家の手が止まる。本ワークショップの価値は自分の手で回した経験なので、これは最悪の失敗パターン
- メンター配分は起業家島に厚く（起業家島は5名に1人、エンジニア島は10名に1人目安）
- 交流は共有タイム（後編10）で設計的に起こす。発表者はエンジニア・起業家から最低1名ずつ選び、「同じ型で両方が完成した」ことを見せるのがクロージングの説得力になる

進度差の吸収は🚀拡張ミッションが担う。エンジニアは本線を速く終えるので、拡張ミッション〔Eng〕（CLAUDE.md・プランモード・Git運用・検証の自動化）へ誘導する。**本線の先回り（次のセクションを勝手に進める）は止める**——後続の説明が二度手間になるため。

> 注意: エンジニアはターン消費も速い。`/status` 巡回では**エンジニア島の残量をむしろ警戒**する。
> 拡張ミッションはターン消費が少ない題材（CLAUDE.md作成・diff読み・計画だけ出させる）を意図的に選んである。

## 待ち時間マイクロ解説ネタ集（コスト・ゼロの座学枠）

参加者は生成待ちで合計30〜40分アイドルする。ハンズオン中、会場全体が「待ち」に入った瞬間に1枚スライドで挟む。**1本90秒以内・手を動かし始めた人がいたら即打ち切り**が鉄則。座学30分制限の外側で解説量を稼ぐ仕掛けなので、長話にした瞬間に本末転倒になる。

| # | ネタ | 差し込みどころ | 要点 |
|---|---|---|---|
| W1 | いまClaudeは何をしているか | ①の最初の生成待ち | 指示→計画→ファイル操作→確認のループを回している。画面のツール実行表示の読み方 |
| W2 | 権限プロンプトの裏側 | ①で権限質問が出た頃 | 許可は記憶され、同種の操作は聞かれなくなる。「全部許可」モードは便利だが今日は使わない理由 |
| W3 | モデルとeffort | ②のステップ2待ち | `/model` で切替可。試作は軽く速く、難問は重く深く。★1の予告 |
| W4 | まとめ指示が効く本当の理由 | ②のステップ2の後 | ターン数節約だけでなく、方向性が一度に伝わるので手戻りが減る |
| W5 | コンテキストという概念 | ②のステップ4待ち | 会話が長くなると古い指示は薄れる。おかしくなったら会話を新しくして仕切り直すのも正規の手 |
| W6 | プランモードだったら今の指示はこうなる | ②ステップ4（壊した後） | 「先に計画だけ」なら壊れなかった。大きい変更の前は相談する。🚀〔Eng〕への布石 |
| W7 | CLAUDE.mdが読まれるタイミング | 前編5の記入中 | 毎回言うことはファイルに。🚀①〔共通〕への布石 |
| W8 | 利用枠の仕組み | 後編開始直後の `/status` 時 | 5時間ウィンドウ＋週次の二重構造。まとめ指示が枠の節約にもなっている |
| W9 | 「幻覚したgreen」実例 | ③の中盤の生成待ち | 「できました」と言って確認していなかった実例を1枚見せる。9の検証プロンプトの伏線 |
| W10 | スキル・/goal・/loopの3段地図 | ③の終盤 | 今日の型がそのまま自律開発の入力になる。クロージングの予告編 |

運用メモ: W1〜W10を全部やる必要はない。**W2・W4・W9は必須**（安全・作法・検証の3本柱）、残りは会場の待ちの発生に合わせて取捨。

## 事前準備期間の運営

- チェックポイント0の提出状況を前日夜に集計。未提出者には個別連絡＋当日30分前のサポートタイム招集
- 提出スクショで環境の偏り（デスクトップアプリ/CLI、OS）を把握し、メンター配置に反映

### ゴールの一文レビュー基準（メンター用）

休憩中に全数チェックし、該当者には休憩明けに一声かける。

- **大きすぎ**: 確認条件が5個以上要りそう／「管理できる」「共有できる」など動詞が複数系統 → 「今日は⟨最初の1動詞⟩だけにしよう」
- **確認できない**: 「使いやすい」「いい感じに」など目で確認できない条件 → 「画面で何が見えたらOK?」と聞いて書き直させる
- **データが外部**: 外部サービスのAPIやログインが必要 → 「今日は手入力またはダミーデータで」に誘導（★8の領域は今日は踏まない）

## 時間が押したときの切り方（優先順）

1. 9のステップ2「見た目をもう一段」を切る（→共有タイムの見栄えは下がるが本質は守られる）
2. 10の発表を3名→2名に減らす
3. 4のステップ3「画像で直す」を口頭紹介のみにする
4. **切ってはいけないもの**: 9のステップ1（検証）、5の言語化ワーク、8の15分チェックポイント運用

## トラブル対応表

| 事象 | 対応 |
|---|---|
| 利用枠の上限到達（Pro） | メンター機（Max）でペア作業。本人に操作させ、メンターは枠を貸すだけ。5時間ウィンドウのローリング回復も案内 |
| 全体的に応答が遅い（障害・混雑） | ライブデモを録画に切り替え。ハンズオンは待ち時間に違和感の書き出し・言語化ワークを前倒しする |
| 環境が完全に壊れた参加者 | Claude Code Web版（ブラウザ実行）に切り替えて継続 |
| アイデア乗り換えを始めた参加者 | 「メモして持ち帰る」に誘導。乗り換えは迷子の最大要因という理屈まで伝える |
| 早く終わった参加者 | 該当ハンズオンの🚀拡張ミッションへ誘導（エンジニアは〔Eng〕系）。本線の先回りは止める。メンター補助役を頼むのも可 |

## 実測データの収集（次回改善と書籍用）

各回で記録する:

- チェックポイント通過率（0〜5の各段階）
- 上限到達者数とその時刻・プラン内訳
- 参加者の平均ターン数の聞き取り（任意アンケート）
- 詰まりポイントのカテゴリ集計（環境／指示／権限／枠）

> 書籍の申し送り「第8〜9章はコスト・実行時間の実測値を必ず載せる」と同様、
> ワークショップも実測で改訂する。アンケートに「かかった費用感の納得度」を1問入れる。
