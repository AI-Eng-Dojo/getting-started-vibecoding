# 講師・メンター用進行ガイド

参加者には配布しない。運営の判断基準と台本の要点をまとめる。

## 体制と機材

- 講師1名＋メンター（参加者8名につき1名目安）
- **講師・メンター機は全員Maxプラン必須**（救済ペア作業で枠を貸すため）
- 会場共有タイマー（後半の15分チェックポイント合図用）
- ハンズオン実践用リポジトリ（教材リポジトリとは別。URLを案内メールに記載し、事前準備0.4で共有する）。**参加者は各自fork して使う。** 全員が同一リポジトリへプッシュすると衝突し、後半9の15分ごとの保存が全滅するため
- 提出フォーム3種: チェックポイント0（事前スクショ＋GitHubユーザー名＋forkしたリポジトリのURL）、チェックポイント3（`SKILL.md` 3つ＋「詰めて」で質問が返る＋`CONTEXT.md`かADRのどちらかが実際に更新されている。**ADRが0本でも不合格ではない**）、宿題提出（後半前日までの `README.md`＋`TASKS.md`。書式は `templates/spec-readme.md`・`templates/tasks.md`）
- 救済タグ入り `starters/`（教材リポジトリ側。配布URLは案内メールに記載）

## 設計思想（新任メンター向け）

1. **座学は合計20分以内。** 説明したくなったら「それはコラムに書いてある」と言って先へ進む
2. **タイトル回収は後半10（レビュー・改善）。** 「動いて終わり」ではなく「その先まで見る」ことの証明はここなので、時間が押してもレビュープロンプト1・2（テスト・セキュリティレビュー）だけは絶対に切らない
3. **戻ることを正規の技術として教える。** 救済タグ利用やバックアップ復帰を「失敗」の空気にしない。メンターの声かけは常に「戻って進むのは今日教えた技です」
4. **利用枠はProで完走できる設計。** ただし作法（まとめ指示・当日温存）が守られている前提。乱れたら個別に軌道修正する
5. **前半は「体験させる」、後半は「一人でやりきらせる」。** 前半のGrill Me Skill自作でつまずいた参加者は、後半で必ず響く。前半3〜4の理解度は特に丁寧に見る

## 参加者構成と座席戦略（想定: 20名＝エンジニア10・非エンジニア（経営者・スタートアップ志望者など）10）

**テーブルは同質で分ける**（エンジニア島×2・非エンジニア島×2）。混成ペアにしない。

- 理由: 混成にするとエンジニアが隣のキーボードを「代わりに」触り始め、非エンジニアの手が止まる。本ワークショップの価値は自分の手で回した経験なので、これは最悪の失敗パターン
- メンター配分は非エンジニア島に厚く（非エンジニア島は5名に1人、エンジニア島は10名に1人目安）
- 交流は成果共有（後半11）で設計的に起こす。発表者はエンジニア・非エンジニアから最低1名ずつ選び、「同じプロセスで両方が形にできた」ことを見せるのがクロージングの説得力になる

進度差の吸収は🚀拡張ミッションが担う。エンジニアは本線を速く終えるので、拡張ミッション〔Eng〕（差分を読む・インフラ構成・リリース自動化）へ誘導する。**本線の先回り（次のセクションを勝手に進める）は止める**——後続の説明が二度手間になるため。

> 注意: エンジニアはターン消費も速い。`/status` 巡回では**エンジニア島の残量をむしろ警戒**する。
> 本ガイドが挙げる〔Eng〕3種（差分を読む・インフラ構成・リリース自動化）はターン消費が少ない。ただし02-part2の「`/goal`で自走させる」・01-part1の「もう1個作る」は消費が大きいので、残量が細い参加者には振らない。

## 待ち時間マイクロ解説ネタ集（コスト・ゼロの座学枠）

参加者は生成待ちで合計アイドル時間が出る。ハンズオン中、会場全体が「待ち」に入った瞬間に1枚スライドで挟む。**1本90秒以内・手を動かし始めた人がいたら即打ち切り**が鉄則。

| # | ネタ | 差し込みどころ | 要点 |
|---|---|---|---|
| W1 | いまClaudeは何をしているか | 前半①の最初の生成待ち | 指示→計画→ファイル操作→確認のループを回している。画面のツール実行表示の読み方 |
| W2 | 権限プロンプトの裏側 | 前半①で権限質問が出た頃 | **参加者テキストに掲載済み**（01-part1「途中で『許可しますか?』と聞かれる」）。口頭では「2番は記憶される。最初は1番で読め」の一点だけ補強する |
| W3 | まとめ指示が効く本当の理由 | 前半①のまとめ指示後 | ターン数節約だけでなく、方向性が一度に伝わるので手戻りが減る |
| W4 | Skillはなぜ効くのか | 前半③のSkill作成中 | プロンプトは消えるがSkillは残る。「毎回言っていること」を資産化する発想 |
| W5 | descriptionが呼ばれる/呼ばれないの分かれ目 | 前半③のSkill動作確認時 | Claudeはdescriptionだけを見て使うか判断している。**症状別の直し方は参加者テキストの表にあるので、そちらを見させる**。口頭は「自分が実際に打つ言葉をdescriptionに入れる」の一点 |
| W6 | 利用枠の仕組み | 後半開始直後の `/status` 時 | 5時間ウィンドウ＋週次の二重構造。まとめ指示が枠の節約にもなっている |
| W7 | 「幻覚したgreen」実例 | 後半⑥の中盤の生成待ち | 「できました」と言って確認していなかった実例を1枚見せる。10の伏線 |
| W8 | Skillをチームに配るという発想 | 前半④の待ち | 個人の作法をリポジトリに入れるとチームの標準になる。拡張ミッションへの布石 |
| W9 | なぜHooksは確実に動くのか | 前半④のHook設定中 | SkillはAIが「使うか」を毎回判断するが、Hooksはイベント条件に合致すれば確認なしに必ず実行される。だからこそ登録は信頼できる内容だけに、という安全側の話に必ずつなげる |

運用メモ: 全部やる必要はない。**W2・W3・W7は必須**（安全・作法・検証の3本柱）、残りは会場の待ちの発生に合わせて取捨。

## 事前準備期間の運営

- チェックポイント0の提出状況を前日夜に集計。未提出者には個別連絡＋当日30分前のサポートタイム招集
- 提出スクショで環境の偏り（VS Code拡張／CLI、OS）を把握し、メンター配置に反映
- ハンズオン実践用リポジトリのURLと、教材リポジトリのURLを取り違えないよう、案内メールでは明確に分けて記載する
- **チェックポイント0でforkのURLを提出させ、前日夜に全員分そろっているか確認する。** forkし忘れ・元リポジトリをcloneした人は、後半9の最初のプッシュで必ず止まる。当日朝のサポートタイムで潰す
- **案内メールで「チェックポイント0の提出前に、forkへ1回コミット＆プッシュしておく」ことを明記する。**（00-prepの手順は0.4のcloneまでで終わっており、push認証を一度も通さないため。メール側の文面例:「**forkしたリポジトリのフォルダを開いた状態で**、README.mdに自分の名前を1行足して、Claude Codeに『コミットしてプッシュして』と頼んでください」）前日夜はfork URLをブラウザで開き、そのコミットが反映されているかで通っているか判定する。通っていない人は前日中にGitHubログイン・認証情報を洗い直させる
- **`docs/00-prep.md` のチェックポイント0「次の2点を送ってください」を「次の3点」に直す。** forkのURLが3つ目の提出項目として追加されたのに数字が古いまま。前日夜のfork確認（直前の項目）はこの3点目が前提
- **`docs/columns.md` の節番号を開催前に更新する。** ★2が「後半9（実装計画）」、★7が「後半11でやったこと」のまま旧構成を指しており、現行は後半9＝実装／後半10＝レビュー・改善で実装計画のハンズオンは存在しない。「それはコラムに書いてある」で参加者を誘導する前提の資料なので、開催前に直す
- **救済タグは開催前に作り直す。** 現在リモートにあるのは旧命名の `rescue/handson3-a`・`-b`・`-c` のみで、starters/README.md が案内する `rescue/a-pomodoro-timer` 等の新命名タグは未作成（raw.githubusercontent.com経由のURLは現状404）。開催前に各starterを完成まで作り込み、`main` 上で新命名のタグを付け直し、旧タグは整理する（詳細は starters/README.md の運営メモ）
- **CP0提出でZIP取得（gitが使えなかった申告）をした人は当日朝のサポートタイムで最優先対応する。** そのままでは後半9のコミット＆プッシュができない。**forkを改めてcloneし直し、ZIPで進めていた作業フォルダの中身をそこへコピーして移す。**（`git init` して既存のGitHubに手動で紐付けるのは、forkの履歴と繋がらず最初のpushで弾かれるため使わない）
- **Windows参加者は既知の環境問題が2つある**（00-prep.md 0.2に対処法を記載済みだが、提出スクショや当日の様子で見落としが疑われたら能動的に確認する）
  - Node.js未インストールだとClaude Code拡張がそもそも起動しない（Windows版のみの制約。Anthropicは対応しない方針で恒久的）
  - 拡張が特定バージョンで起動時にクラッシュするビルド不具合が断続的に再発している（2026年2月以降、複数バージョンで報告あり。Node.jsを入れても直らない場合はこちら）
  - **復旧策は症状で分かれる。** ①起動しない・反応しない＝Node.js未インストール→nodejs.orgのLTS版を入れてPC再起動（00-prep 0.2の3）。これで拡張自体が起動するので、CLI版への切り替えは不要。②Node.jsを入れているのに起動時クラッシュ（TypeErrorなど）＝既知のビルド不具合→VS Codeのターミナルで `npm install -g @anthropic-ai/claude-code` → `claude` コマンドでCLI版に切り替え（npmはNode.js同梱のため、Node.js導入済みが前提）。**拡張のUIが使えないだけで、今日の内容はCLI版でも支障なく進められる。** メンター側もこの2分岐と切り替え手順を把握しておく

## 宿題期間の運営

- 宿題提出は **`README.md` と `TASKS.md` の2ファイル**。後半開始の**前日中**を締切とする
- **01-part1の宿題制約表は「実装時間は55分」と書かれているが、現行の後半9は70分（旧構成の数字が残ったまま）。** 口頭では70分と案内し、参加者から質問が出たら「テキストの55分は旧版の数字」と即答する
- **チェックポイント3（3つの `SKILL.md` の中身。`~/.claude/skills/` 配下でリポジトリの外にあるため、フォームは貼り付け or アップロードで受け取る）は前半終了後〜当日夜に、担当メンター1名を決めて目を通す。**（前半の休憩は1:30〜1:45の1回のみで、ハンズオン③(提出物が出るタイミング)より前にある。チェックポイント3の提出は2:35頃なので、その後にまとまった休憩は無く、実運用はこのタイミングになる）
  - 見るのは3点: `description` に呼び出し語が入っているか／`tsumete` 本文が参照するSkill名が保存名と一致しているか／`tsumete` 末尾にREADME.md・TASKS.md書き出しの指示があるか
  - 3点目が無い人には宿題着手前に連絡するのが理想だが、6終了直後に着手する参加者もいて間に合わないことがある。**取りこぼしは後半8冒頭のTASKS.md生成プロンプト（02-part2 §7）で回収できるので必須ではなく「できれば前倒し」**
- メンターは提出物に目を通し、次のいずれかに該当するものをリストアップしておく
  - **`TASKS.md` が無い**: 自作 `tsumete` に書き出しの指示を入れ忘れている。後半8の冒頭で作らせれば追いつく（02-part2の§7表の下にあるプロンプトを使う）
  - **大きすぎる**: 後半2時間で終わらない規模。**ただし「やることが多い」こと自体は問題ではない**（後半8で線を引く）。問題なのは1つ1つが大きい場合
  - **曖昧さが残っている**: 「使いやすく」など目で確認できない表現がまだある
  - **制約違反**: ログイン・サーバー・外部サービス連携が「できること」に残っている。**後半8で発覚すると実装70分が崩れるので、前日中に必ず潰す**
  - **未提出**: 後半7（宿題ふりかえり）で個別フォローが必要
- 該当者には後半開始前、または7の時間に声をかける。頭ごなしに直させず、「今日の2時間で終わる形」に絞る手伝いをする

## 時間が押したときの切り方（優先順）

1. 前半5のSecurity Review Skillを参加者に作らせず、講師が画面共有して眺めるだけにする（**Hooksのハンズオン自体は必修のため完全カットはしない**。「他にどんなSkillが作れそうか」は01-part1側で「時間が余ったら」扱いなので、押している時点で自然に消える＝別途打ち切る必要はない）
2. 前半4で参加者が大きく遅れている場合、`ddd` は「答え合わせ用の完成例を眺めるだけ」に切り替えさせ、`tsumete` は `tsumetsume` だけを参照する簡易版（1問1答のみ、書き残しは無し）で妥協させる。**tsumetsumeを自分の言葉で書く体験だけは死守する。** この場合、チェックポイント3は「`SKILL.md` 2つ＋『詰めて』で質問が返る」までで可と全体アナウンスし、`CONTEXT.md`/ADRの確認要件は外す。ただし `tsumete` 末尾のREADME.md・TASKS.md書き出し指示だけは簡易版にも必ず入れさせる（宿題の持ち物に直結するため）
3. 後半11の発表を3名→2名に減らす
4. 前半2の「設定を開いて中を見る」を、`/permissions` と `/config` の2つだけに絞る（`/context` は飛ばし、`/clear` は必ずやらせる）
5. **切ってはいけないもの**（時間が無いときの調整はここまで。以下は削らない）
   - 後半10のレビュープロンプト1・2（テスト・セキュリティレビュー）
   - 前半4のtsumetsume自作（アイデア言語化＋Grill Me Skillの核）
   - 前半5のHooksハンズオン。**参加者が自分でHookを設定しログ1行を確認するところまでが必修＝チェックポイント4。** 時間が無いときは講師デモを先に見せて設定作業を短縮してよいが、**デモだけで終わらせない**
   - 後半9の15分チェックポイント運用
   - 後半8の線引き（飛ばすと実装が終わらない）

## トラブル対応表

| 事象 | 対応 |
|---|---|
| 利用枠の上限到達（Pro） | メンター機（Max）でペア作業。本人に操作させ、メンターは枠を貸すだけ。5時間ウィンドウのローリング回復も案内 |
| Gmailコネクタの接続でOAuth画面が進まない・2FAで止まる | 個人のスマホでの2FA完了を優先してもらう。時間がかかりそうなら先に進ませ、隣の画面を見学する側に回す |
| 会社支給のGoogleアカウントで接続が拒否される（組織ポリシー） | 個人アカウントへの切り替えを勧める。個人アカウントも持っていない・作りたくない場合は接続せず見学に回す（本線への影響なし） |
| コネクタを接続したのにClaude Codeから使えない | **新しい会話（`/clear`）を開始しているか確認。** 接続前の会話のまま操作している参加者が大半 |
| （Windows）拡張が起動しない・反応しない | Node.js未インストールが原因。LTS版を入れてPC再起動させる（00-prep.md 0.2の3）。CLI版への切り替えは不要 |
| （Windows）拡張がTypeErrorなどでクラッシュする | 既知のビルド不具合。VS Codeのターミナルで `npm install -g @anthropic-ai/claude-code` → `claude` でCLI版に切り替えさせる（Node.js導入済みが前提。00-prep.md 0.2参照） |
| 全体的に応答が遅い（障害・混雑） | ハンズオンは待ち時間に言語化ワーク・仕様の見直しを前倒しする |
| 環境が完全に壊れた参加者 | **先にいまの状態をコミット＆プッシュ（またはファイルをコピー退避）させてから**、Claude Code Web版（ブラウザ実行）に切り替えて継続。自作Skillは `~/.claude/skills/` 直下でリポジトリの外にあるため引き継がれない。`SKILL.md` の中身を貼り直させる |
| 後半9でプッシュが弾かれる（コミットは通るが push だけ失敗する） | 取得方法を先に切り分ける。①**forkではなく元リポジトリをclone/ZIP展開した人**→forkをclone し直し、作業フォルダをコピーして移す（事前準備期間の運営のZIP対応と同じ手順）。②**リモートURLは自分のforkなのに失敗する人**→前日夜のpush確認（事前準備期間の運営）を通していない＝認証未設定。ブラウザでGitHubログインを通し直させる |
| アイデア乗り換えを始めた参加者 | 「メモして持ち帰る」に誘導。乗り換えは迷子の最大要因という理屈まで伝える |
| 宿題が未着手のまま後半に来た参加者 | 前半2〜3で作ったものを種に、後半7の時間で急いで1周させる。それでも決まらなければ [starters/](../starters/) のお題を仕様として仮採用させる |
| やることが20個ある参加者 | **減らさせない。** 後半8で今日やる4つに線を引き、残りは「今回やらないこと」へ移させる。詰めた量は持ち帰る資産だと伝える |
| 早く終わった参加者 | 該当ハンズオンの🚀拡張ミッションへ誘導（エンジニアは〔Eng〕系）。本線の先回りは止める。メンター補助役を頼むのも可 |

- 宿題提出物のうち「制約違反」（ログイン・サーバー必須）の件数
