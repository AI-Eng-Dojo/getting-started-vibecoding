## ★1 モデルとeffortの使い分け — 回転数を上げる

当日オープニングで叩いた `/model` と `/effort` の、もう一歩先の話です。Claude Codeは、頭脳となるモデルと、考える深さ（effort）を切り替えられます。

- **試作・見た目の調整**（今日やったこと）: 軽めのモデル×浅いeffortで十分。応答が速い=回転数が上がる=バイブコーディングが気持ちよく回る。利用枠の消費も少ない
- **難しいバグ・設計の相談**: 賢いモデル×深いeffortに切り替える価値がある

切り替えは `/model` コマンドから。迷ったらデフォルトのままでOKですが、「なんか遅いな」と感じたら軽い方へ、「なんか浅いな」と感じたら深い方へ。この感覚が身につくと利用枠が倍長持ちします。

## ★2 プランモード — 作る前に相談する

後半9（実装計画）では会話ベースで計画を立てさせましたが、大きめの変更ほど**先に計画だけ出させる**専用の機能があります。それがプランモード（計画モード）です。オンにすると、Claudeはファイルを変更せず「こう進めます」という計画だけを提示し、あなたの承認後に実行します。

使いどころ: 「この機能を足すとしたら何が必要?」「このアプリをスマホアプリ化できる?」のような、**着手前の相談**。今日の実装計画のハンズオンが、まさにこの発想の会話版です。

## ★3 CLAUDE.mdの第一歩 — 毎回言うことをファイルにする

プロジェクトのフォルダに `CLAUDE.md` というファイルを置くと、Claude Codeは毎回それを読んでから作業します。つまり**「毎回言っていること」の置き場**です。

今日のワークショップでいえば、こんな内容が候補です:

```markdown
# このプロジェクトの約束
- アプリは1つのHTMLファイルで完結させる
- 変更のたびに、ブラウザでの確認手順を最後に一行で書く
- 派手な色使いはしない。配色は落ち着いたトーンで
```

書きすぎは禁物です。**3回同じことを言ったら1行足す**、くらいの育て方がちょうどいい。書き出し用のサンプルが [../templates/CLAUDE.md.sample](../templates/CLAUDE.md.sample) にあります。何を書き、何を書かないかの設計は書籍の第7章が詳しいです。

## ★4 権限とAuto modeの体系 — 安全装置の全体像

今日何度も出会った「〜してもよいですか?」と、前半2で開いた `/permissions`・`/config` の全体像です。

- Claude Codeの操作には**権限モデル**があり、ファイル変更・コマンド実行は原則あなたの承認が必要
- 「毎回聞かれるのが煩わしい」場合、承認を省略する動作モード（Auto mode系の設定）がありますが、**省略するのは「間違えても被害が小さい操作」だけ**にするのが原則
- さらに進むと、実行環境ごと隔離するサンドボックスという選択肢もあります

今日の範囲(自分のフォルダ内で1ファイルのアプリ)は被害半径が最小の世界でした。だから `/config` の Permission mode をデフォルトのままにしておいて何も困らなかった、という話でもあります。仕事のリポジトリで使うときは、この安全装置の設計から入ってください。書籍第7章「ガードレールを設計する」がそのための章です。

## ★5 スキル — 今日作ったGrill Meスキルの、もう一歩先

今日は「曖昧なアイデアを問い詰める」Skillを、tsumete（入口）・tsumetsume（問い詰める）・ddd（書き残す）の3つに分けて作りました。**やり方そのものをファイルとして保存し、Claudeが必要なときに自分で読み込む**仕組みがスキル（Agent Skills）です。役割ごとに小さく分け、入口が他のSkillを呼び出しながら組み合わせるのも、スキル設計の基本形の一つです。

Skill化できるのはGrill Meのような対話の作法だけではありません。テストの書き方、コードレビューの観点、READMEの体裁——「毎回同じことを言っている」工程なら何でも候補になります。**個人の作法をチームに配れる**のもスキルの強みで、書籍では第3章（使う・作る）と第8章（設計する・配る）の二段階で扱っています。

## ★6 スキルとカスタムコマンド — どっちで書くのか

自分の作法を保存する場所は、Claude Codeに2つあります。今日作った**スキル**（`~/.claude/skills/名前/SKILL.md`）と、**カスタムコマンド**（`~/.claude/commands/名前.md`）です。

カスタムコマンドのほうが先にあった機能で、いまは両方が同じ仕組みの上に載っています。`/help` の一覧にも並んで表示され、書ける設定項目（`description`・`allowed-tools`・`model` など）もほとんど共通です。残っている違いは、実質この2つだけです。

| | カスタムコマンド | スキル |
|---|---|---|
| **いつ動くか** | あなたが `/名前` と打ったときだけ | Claudeが説明文を読んで**自分から呼ぶ**。もちろん `/名前` でも呼べる |
| **形** | `.md` ファイル1つ | フォルダ1つ。参照ドキュメント・スクリプト・テンプレートを一緒に置ける |

「勝手に呼ばれると困る」なら、スキル側に `disable-model-invocation: true` と書けば自動起動だけを切れます。つまり**スキルはカスタムコマンドを含んだ上位の書き方**で、今日 `tsumete` たちをスキルとして作ったのはそのためです。

使い分けの目安: 呼ぶタイミングを完全に自分で握りたい短い定型プロンプトならカスタムコマンド、それ以外はスキル。**迷ったらスキルで構いません。**

## ★7 スペック駆動開発 — 今日やったことの正式名称

今日のワークショップの一連の流れ——曖昧なアイデアをSkillで問い詰め、仕様に育て、計画に落としてから実装する——は、**スペック駆動開発**と呼ばれる進め方そのものです。「何を作るか」を先に固め、「どう作るか」と分けて進めることで、大きなものを作るときに迷子になりにくくなります。

目安: 今日は宿題1回分の問い詰めで仕様化しましたが、機能がもっと大きく・複雑になるほど、この仕様化のプロセスに時間をかける価値が増します。Kiro、Spec Kitなどの専用フレームワークもありますが、まずは書籍第5章の「達人に学ぶスペック駆動開発」から入るのがおすすめです。

## ★8 任せきる — /goalと/loopの世界

今日は画面に張り付いて「見て、直す」を回しました。次の段階は、**見ていない間に作らせる**ことです。

- **ゴール実行（/goal）**: 完了条件を渡すと、満たすまでClaudeが自走する。今日の仕様書の「何ができればいいか」がそのまま入力になる
- **自動ループ（/loop）**: 定期的・継続的にタスクを回し続ける。監視や改修の自動化に使う

鍵は今日すでに学んでいます。**検証可能な完了条件を書けること**（後半8〜9でやったこと）と、**「できました」を鵜呑みにしない検証**（後半11でやったこと）です。任せきるとは、放置ではなく検証の自動化です。書籍第9章がこのテーマのクライマックスです。

## ★9 外部とつなぐ前の安全チェックリスト

今日のアプリは基本的に自分のPCの中で完結する構成でした。前半2でGmailのコネクタ（MCP）を1つ試しましたが、外部サービスとのつなぎ方はそれだけではありません。🚀拡張ミッションでインフラ構成やリリース自動化（GitHub Actions）に挑戦した人、あるいはこの先そこに進みたい人向けです。外部サービス接続（MCP）、GitHub連携、クラウド実行に進むときは、**信頼の境界**が変わります。最低限これだけ確認してから:

- [ ] 秘密情報（APIキー・パスワード）をプロンプトやコードに直書きしていないか
- [ ] 入れようとしている外部ツール・スキルは信頼できる提供元か
- [ ] 外部から来た文章（Webページ・Issue・メール）を「指示」として実行させていないか — 外部入力は指示ではなくデータとして扱わせる
- [ ] 自動実行には停止手段と、失敗時に戻せるバックアップがあるか

詳しくは書籍第6章（手元から離す）と第7章（信頼境界の設計）へ。
