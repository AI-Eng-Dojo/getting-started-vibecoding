## ★1 モデルとeffortの使い分け — 回転数を上げる

当日オープニングで叩いた `/model` と `/effort` の、もう一歩先の話です。Claude Codeは、頭脳となるモデルと、考える深さ（effort）を切り替えられます。

- **試作・見た目の調整**: 軽めのモデル×浅いeffortで十分。応答が速い＝回転数が上がる＝バイブコーディングが気持ちよく回る。利用枠の消費も少ない
- **難しいバグ・設計の相談**: 賢いモデル×深いeffortに切り替える価値がある

切り替えは `/model` コマンドから。
このワークショップでは、前半・後半共通で **Sonnet × medium** を推奨します。
「なんか遅いな」と感じたら軽い方へ、「なんか浅いな」と感じたら深い方へ一時的に切り替え、解決したら推奨設定に戻します。

後半8では会話ベースで「今日やる分」を決めましたが、大きめの変更ほど先に計画だけ出させる専用の機能が有効です。それがプランモード（計画モード）です。オンにすると、Claudeはファイルを変更せず「こう進めます」という計画だけを提示し、あなたの承認後に実行します。

## ★3 CLAUDE.mdの置き場所と育て方

前半3で `myapp` に置いた `CLAUDE.md` は、そのプロジェクト1つに効く約束でした（前半3）。置き場所を変えると効く範囲が変わります。エージェントスキルが、`vibecoding-0908` から `myapp` にコピーするまで `myapp` では呼べなかった（前半3）のと同じ理屈です。

| 置き場所 | 効く範囲 | 向いている中身 |
|---|---|---|
| `myapp/CLAUDE.md` | そのプロジェクトだけ。リポジトリと一緒に共有される | 今回の制約、ファイルの役割（`README.md` が仕様、`TASKS.md` がやること） |
| `~/.claude/CLAUDE.md` | 自分のPCのすべてのプロジェクト | 「返事は日本語で」「変更したら確認手順を一行添えて」のような、自分の好み |
| `myapp/CLAUDE.local.md` | そのプロジェクトで自分だけ（`.gitignore` に入れる） | 共有したくない個人的なメモ |

育て方は前半6のとおり、3回同じことを言ったら1行足す、です。増えてきたら、次の4つで整理します。

- 手順になってきた項目はエージェントスキルへ移す。`CLAUDE.md` は会話のたびに丸ごと読まれるので、長いほど毎回の会話が重くなります。目安は200行以内です
- 「必ず止めたい」ものはHooksへ。`CLAUDE.md` は約束であって強制ではありません（後半9でコミット前、11でデプロイ前の確認を足しました）
- 矛盾する2行を残さない。どちらに従うかはClaudeが決めてしまいます
- 一部のフォルダにしか関係しない決まりは、そのフォルダ側に置く。たとえばフロントエンドとバックエンドが1つのリポジトリに同居しているとき、両方の開発ルールをルートの `CLAUDE.md` に書くと、片方しか触らない人にも毎回もう片方のルールが読まれます。`backend/CLAUDE.md` のようにフォルダの中へ置いた `CLAUDE.md` は、会話の開始時ではなく、Claudeがそのフォルダのファイルを読んだときに読み込まれます。`.claude/rules/` に置いたファイルに `paths:` で対象のファイルを書いておくと、そのファイルを扱うときだけ読み込ませることもできます

すでにあるプロジェクトに後から入れるときは、`/init` と打つとClaude Codeがフォルダの中身を読んで `CLAUDE.md` の下書きを作ります。いまの会話に読み込まれているファイルは `/context` の Memory files で確認でき、`/memory` から開いて編集できます。

## ★4 権限の体系 — 安全装置の全体像

今日何度も出会った「〜してもよいですか?」と、オープニングで開いた `/permissions`、前半2で開いた `/config` の全体像です。

- Claude Codeの操作には**権限モデル**があり、ファイル変更・コマンド実行は原則あなたの承認が必要
- 今日使ったAuto Modeは、この承認の一部をAI自身のリスク判定に任せるモードです。低リスクな操作は自動で進み、破壊的な操作や踏み込んだ操作は今までどおり確認が挟まります。「省略していいのは間違えても被害が小さい操作だけ」という原則は変わりません
- さらに進むと、実行環境ごと隔離するサンドボックスという選択肢もあります

今日の範囲（自分のフォルダ内で1ファイルのアプリ）は被害範囲が最小の世界でした。だからAuto Modeで進めても何も困らなかった、という話でもあります。仕事のリポジトリで使うときは、気をつけてください。

## ★5 自作したエージェントスキルの応用

今日は、`tsumete`でアイデアを一問ずつ問い詰め、最後にREADMEとTASKSへまとめます。
決まった用語や設計上の決定をその場で残す部分は、`ddd`に分けました。
**やり方そのものをファイルとして保存し、Claudeが必要なときに自分で読み込む**仕組みがエージェントスキルです。
質問から成果物の作成までを担う`tsumete`と、記録を担う`ddd`のように、役割ごとに分けると、直したい作法を見つけやすくなります。

`tsumete`には`disable-model-invocation: true`を入れ、人間が明示的に始めます。長く走る作業ほど、開始を人間が決めることに意味があります。この行が何を切り替えているのかは、次の★6で扱います。

エージェントスキル化できるのはGrill Meのような対話の作法だけではありません。テストの書き方、コードレビューの観点、READMEの体裁など、「毎回同じことを言っている」工程なら何でも候補になります。個人の作法をチームに配れるのも、この仕組みの強みです。今日作ったものの参考元については★9で扱います。

## ★6 エージェントスキルとカスタムコマンドの使い分け

自分の作法を保存する場所は、Claude Codeに2つあります。今日作った**エージェントスキル**（`.claude/skills/名前/SKILL.md`）と、**カスタムコマンド**（`.claude/commands/名前.md`）です。

カスタムコマンドのほうが先にあった機能で、いまは両方が同じ仕組みの上に載っています。`/help` の一覧にも並んで表示され、書ける設定項目（`description`・`allowed-tools`・`model` など）もほとんど共通です。残っている違いは、実質この2つだけです。

| | カスタムコマンド | エージェントスキル |
|---|---|---|
| **いつ動くか** | あなたが `/名前` と打ったときだけ | Claudeが説明文を読んで自分から呼ぶ。もちろん `/名前` でも呼べる |
| **形** | `.md` ファイル1つ | フォルダ1つ。参照ドキュメント・スクリプト・テンプレートを一緒に置ける |

「勝手に呼ばれると困る」なら、エージェントスキル側に `disable-model-invocation: true` と書けば自動起動だけを切れます。今日の `tsumete` がまさにこれです。この1行を入れると、Claudeの判断では起動せず、`/tsumete` と打ったときだけ動く、つまりカスタムコマンドとほぼ同じ振る舞いになります。逆に言えば、**カスタムコマンドを含んだ上位の書き方**で、今日 `tsumete` たちをこの形で作ったのはそのためです。

使い分けの目安は、呼ぶタイミングを完全に自分で握りたい短い定型プロンプトならカスタムコマンド、それ以外はエージェントスキル。迷ったら後者で構いません。

## ★7 任せきる — /goalと/loopの世界

今日は画面に張り付いて「見て、直す」を回しました。次の段階は、見ていない間に作らせることです。

- **ゴール実行（/goal）**: 完了定義を渡すと、満たすまでClaudeが自走する。今日の仕様書の「何ができればいいか」がそのまま入力になる
- **自動ループ（/loop）**: 定期的・継続的にタスクを回し続ける。監視や改修の自動化に使う

今日すでに学んだことで準備はできています。検証可能な完了定義を書けること（後半8〜9でやったこと）と、「できました」を鵜呑みにしない検証（後半10でやったこと）です。**任せきるとは、放置ではなく、意図通り自動化度合いを上げることです。**

## ★8 外部とつなぐ前の安全チェックリスト

今日は後半11でアプリをCloudflareに公開し、後半12でNotionやBacklogとMCPでつなぎました。**この2つで、あなたのプロジェクトの信頼の境界は前半とは別物になっています。** さらにGitHub Actionsでの自動デプロイなどに進むときは、最低限これだけ確認してから進めてください。

- [ ] 秘密情報（APIキー・パスワード）をプロンプトやコードに直書きしていないか
- [ ] 入れようとしている外部ツール・エージェントスキルは信頼できる提供元か
- [ ] 外部から来た文章（Webページ・Issue・メール）を「指示」として実行させていないか。外部入力は指示ではなくデータとして扱わせる
- [ ] 自動実行には停止手段と、失敗時に戻せるバックアップがあるか

## ★9 エージェントスキルを役割で分ける

自作する2件と、任意課題の2件は、[mattpocock/skills](https://github.com/mattpocock/skills) などの設計をこのワークショップに合わせています。

| 教材のエージェントスキル | 参考にしたもの | 役割 |
|---|---|---|
| `tsumete` | `grill-me` | 一度に一問ずつ質問し、最後にREADMEとTASKSを書き出す |
| `ddd` | `domain-modeling` | 確定した用語と決定を残す |
| `tdd` | `tdd` | 任意課題。完了定義を自動テストにしてから実装する |
| `prototype` | `prototype` | 任意課題。捨てる前提の試作で設計の問いに答える |

`tsumete` に `disable-model-invocation: true` を付け、長い問い詰めを始めるタイミングは人間が決めます。
`ddd` は `tsumete` から記録を頼まれたときや、用語・決定を残すよう直接頼まれたときに使います。
質問の進め方と記録の書式は、それぞれのファイルで調整できます。

### 実装とレビューを組み合わせる

本線では一件ずつ実装し、人間が画面で確かめてからコミットします。
その前に、同梱の `/code-review` とセキュリティレビューのフックを用意します。
独自の `code-review` と `security-review` を同名で置くと同梱機能と競合するため、教材では配布しません。

READMEは欲しい体験と完成判定を記録し、TASKSは実装の順番と各件の完了定義を記録します。
コードレビューの指摘と、この二つに書いた基準を使った動作確認を組み合わせます。
指摘をすべて直すのではなく、現在のMVPに関わる不具合と重大なセキュリティ問題を解消し、見送るものは理由つきでTASKSに残します。
