## ★1 モデルとeffortの使い分け — 回転数を上げる

当日オープニングで叩いた `/model` と `/effort` の、もう一歩先の話です。Claude Codeは、頭脳となるモデルと、考える深さ（effort）を切り替えられます。

- **試作・見た目の調整**: 軽めのモデル×浅いeffortで十分。応答が速い=回転数が上がる=バイブコーディングが気持ちよく回る。利用枠の消費も少ない
- **難しいバグ・設計の相談**: 賢いモデル×深いeffortに切り替える価値がある

切り替えは `/model` コマンドから。迷ったらデフォルトのままでOKですが、「なんか遅いな」と感じたら軽い方へ、「なんか浅いな」と感じたら深い方へ。この感覚が身につくと利用枠が倍長持ちします。

## ★2 プランモード — 作る前に相談する

後半8では会話ベースで「今日やる分」に線を引きましたが、大きめの変更ほど**先に計画だけ出させる**専用の機能が有効です。それがプランモード（計画モード）です。オンにすると、Claudeはファイルを変更せず「こう進めます」という計画だけを提示し、あなたの承認後に実行します。

プロジェクトのフォルダに `CLAUDE.md` というファイルを置くと、Claude Codeは毎回それを読んでから作業します。つまり**「毎回言っていること」の置き場**です。

書きすぎは禁物です。**3回同じことを言ったら1行足す**、くらいの育て方がちょうどいいです。書き出し用のサンプルが [../templates/CLAUDE.md.sample](../templates/CLAUDE.md.sample) にあります。

## ★4 権限の体系 — 安全装置の全体像

今日何度も出会った「〜してもよいですか?」と、前半2で開いた `/permissions`・`/config` の全体像です。

- Claude Codeの操作には**権限モデル**があり、ファイル変更・コマンド実行は原則あなたの承認が必要
- 今日使ったAuto Modeは、この承認の一部をAI自身のリスク判定に任せるモードです。低リスクな操作は自動で進み、**破壊的な操作や踏み込んだ操作は今までどおり確認が挟まります**。「省略していいのは間違えても被害が小さい操作だけ」という原則は変わりません
- さらに進むと、実行環境ごと隔離するサンドボックスという選択肢もあります

今日の範囲(自分のフォルダ内で1ファイルのアプリ)は被害範囲が最小の世界でした。だからAuto Modeで進めても何も困らなかった、という話でもあります。仕事のリポジトリで使うときは、気をつけてください。

## ★5 スキル — 今日作ったGrill Meスキルの、もう一歩先

今日は「曖昧なアイデアを問い詰める」Skillを、tsumete（入口）・tsumetsume（問い詰める）・ddd（書き残す）の3つに分けて作りました。**やり方そのものをファイルとして保存し、Claudeが必要なときに自分で読み込む**仕組みがスキル（エージェントスキル）です。役割ごとに小さく分け、入口が他のSkillを呼び出しながら組み合わせるのも、スキル設計の基本形の一つです。

**中身を持つスキルは自動で呼ばれてよく、入口は人間が明示的に呼ぶ専用にする**——`tsumete` にだけ `disable-model-invocation: true` を入れたのがこれです。長く走る作業ほど、始めるかどうかを人間が握っておく価値があります。この行が何を切り替えているのかは、次の★6で扱います。

### 参考元のスキル

今日作った3つには参考元があります。[mattpocock/skills](https://github.com/mattpocock/skills) で公開されているスキル集です。

| 今日作ったもの | 参考元 |
|---|---|
| `tsumetsume`（問い詰める本体） | `grilling` |
| `ddd`（用語集・ADRに書き残す） | `domain-modeling` |
| `tsumete`（2つを束ねる入口） | `grill-with-docs` |

参考元の `grill-with-docs` は、本文が**たった1行**です。「`grilling` のセッションを `domain-modeling` を使って実行せよ」——それだけ。今日 `tsumete` を薄い入口にしたのは、この形に倣っています。

さらに参考元には `grill-me` という**もう1枚の入口**があります。中身は「`grilling` を実行せよ」の1行だけで、`domain-modeling` を呼びません。つまり**「記録を残さず、ただ問い詰めるだけ」の入口**です。

ここが面白いところです。**1行のラッパーを2枚用意するだけで、「記録ありで詰める」と「記録なしで詰める」を撃ち分けられます。** 中身（`grilling`・`domain-modeling`）は一切書き換えていません。用途が増えたら入口を1枚足す——これがSkillを組み合わせる旨みです。

Skill化できるのはGrill Meのような対話の作法だけではありません。テストの書き方、コードレビューの観点、READMEの体裁——「毎回同じことを言っている」工程なら何でも候補になります。**個人の作法をチームに配れる**のもスキルの強みで、書籍では第3章（使う・作る）と第8章（設計する・配る）の二段階で扱っています。

## ★6 スキルとカスタムコマンド — どっちで書くのか

自分の作法を保存する場所は、Claude Codeに2つあります。今日作った**スキル**（`~/.claude/skills/名前/SKILL.md`）と、**カスタムコマンド**（`~/.claude/commands/名前.md`）です。

カスタムコマンドのほうが先にあった機能で、いまは両方が同じ仕組みの上に載っています。`/help` の一覧にも並んで表示され、書ける設定項目（`description`・`allowed-tools`・`model` など）もほとんど共通です。残っている違いは、実質この2つだけです。

| | カスタムコマンド | スキル |
|---|---|---|
| **いつ動くか** | あなたが `/名前` と打ったときだけ | Claudeが説明文を読んで**自分から呼ぶ**。もちろん `/名前` でも呼べる |
| **形** | `.md` ファイル1つ | フォルダ1つ。参照ドキュメント・スクリプト・テンプレートを一緒に置ける |

「勝手に呼ばれると困る」なら、スキル側に `disable-model-invocation: true` と書けば自動起動だけを切れます。**今日の `tsumete` がまさにこれです。** この1行を入れると、Claudeの判断では起動せず、`/tsumete` と打ったときだけ動く——つまり**カスタムコマンドとほぼ同じ振る舞い**になります。逆に言えば、スキルはこの1行でカスタムコマンドの側に寄せられるということです。つまり**スキルはカスタムコマンドを含んだ上位の書き方**で、今日 `tsumete` たちをスキルとして作ったのはそのためです。

使い分けの目安: 呼ぶタイミングを完全に自分で握りたい短い定型プロンプトならカスタムコマンド、それ以外はスキル。**迷ったらスキルで構いません。**

## ★7 任せきる — /goalと/loopの世界

今日は画面に張り付いて「見て、直す」を回しました。次の段階は、**見ていない間に作らせる**ことです。

- **ゴール実行（/goal）**: 完了条件を渡すと、満たすまでClaudeが自走する。今日の仕様書の「何ができればいいか」がそのまま入力になる
- **自動ループ（/loop）**: 定期的・継続的にタスクを回し続ける。監視や改修の自動化に使う

今日すでに学んだことで準備はできています。**検証可能な完了条件を書けること**（後半8〜9で「目印」としてやったこと）と、**「できました」を鵜呑みにしない検証**（後半10でやったこと）です。任せきるとは、放置ではなく、意図通り自動化度合いを上げることです。

## ★9 今日のスキル7個は、どこから来たのか

今日あなたが作った・コピーした7枚のうち6枚には、元ネタがあります。公開されているスキル集（[github.com/mattpocock/skills](https://github.com/mattpocock/skills)）の設計を、日本語とこのワークショップの文脈に置き直したものです。**対応を知っておくと、英語圏の議論をそのまま読めるようになります。**

| 今日のスキル | 元ネタ | 位置づけ |
|---|---|---|
| `tsumete` | `grill-with-docs` | **入口**。下の2つを呼ぶだけの薄いラッパー |
| `tsumetsume` | `grilling` | **原理**。決定ツリーの枝を一本ずつ下り、合意まで実装させない |
| `ddd` | `domain-modeling` | 用語の曖昧さを潰し、`CONTEXT.md` に保存する |
| `tdd` | `tdd` | 目印（テスト）が先、実装が後。リファクタはここでやらない |
| `code-review` | `code-review` | Spec軸とStandards軸を**混ぜずに**報告する |
| `prototype` | `prototype` | 捨てる前提の試作で設計の質問に答える |
| `security-review` | （なし） | この教材オリジナル。ノンテク層でも読める観点順に組み直したもの |

**いちばん効く発見は、`tsumete` の正体です。** あれは単体のスキルではなく、`tsumetsume`（原理）と `ddd`（記録）を**まとめて呼ぶ入口**でしかありません。中身は下の2枚が持っています。前半4で「3つに分ける」と言われて面倒に感じた人もいるはずですが、**入口と中身を分けるのは、スキル設計の基本形**です。入口だけ差し替えれば、同じ中身を違う用途に使い回せます。

もう一つ。**`tsumete` にだけ `disable-model-invocation: true` を入れたのも、元ネタと同じ設計です。** 向こうでも `grill-with-docs` は「人が呼ぶ」側、`grilling` は「モデルが必要と判断したら呼ぶ」側に分かれています。**長く走る作業ほど、始めるかどうかを人間が握る。**

### 今日教わった「型」の名前

```
grill-with-docs → to-spec → tdd → code-review
（詰める）      （仕様化） （実装） （レビュー）
```

今日やったのはこの順番です。`to-spec` だけはスキルとして登場しませんでしたが、それは **`tsumete` の最後が `README.md` と `TASKS.md` を書き出す** ところで済ませているからです。そして書いた `README.md` は、後半10の `code-review` の Spec 軸が読みます。

この先の処理もスキル化して効率化できます。`diagnosing-bugs`（バグ診断のループ）、`handoff`（会話を別のエージェントに引き継ぐ）、`research`（一次情報に当たって調べる）など。**「毎回同じことを言っている工程」を見つけたら、まず向こうに同じものがないか探すのが速いです。**
