## ★1 モデルとeffortの使い分け — 回転数を上げる

Claude Codeは、頭脳となるモデルと、考える深さ（effort）を切り替えられます。

- **試作・見た目の調整**（今日やったこと）: 軽めのモデル×浅いeffortで十分。応答が速い=回転数が上がる=バイブコーディングが気持ちよく回る。利用枠の消費も少ない
- **難しいバグ・設計の相談**: 強いモデル×深いeffortに切り替える価値がある

切り替えは `/model` コマンドから。迷ったらデフォルトのままでOKですが、「なんか遅いな」と感じたら軽い方へ、「なんか浅いな」と感じたら深い方へ。この感覚が身につくと利用枠が倍長持ちします。

## ★2 プランモード — 作る前に相談する

今日は「いきなり作らせる」で通しましたが、大きめの変更ほど**先に計画だけ出させる**方が安全です。この目的のための機能がプランモード（計画モード）です。オンにすると、Claudeはファイルを変更せず「こう進めます」という計画だけを提示し、あなたの承認後に実行します。

使いどころ: 「この機能を足すとしたら何が必要?」「このアプリをスマホアプリ化できる?」のような、**着手前の相談**。今日の言葉で言えば「ゴールの一文を書く前の壁打ち相手」です。

## ★3 CLAUDE.mdの第一歩 — 毎回言うことをファイルにする

プロジェクトのフォルダに `CLAUDE.md` というファイルを置くと、Claude Codeは毎回それを読んでから作業します。つまり**「毎回言っていること」の置き場**です。

今日のワークショップでいえば、こんな内容が候補です:

```markdown
# このプロジェクトの約束
- アプリは1つのHTMLファイルで完結させる
- 変更のたびに、ブラウザでの確認手順を最後に一行で書く
- 派手な色使いはしない。配色は落ち着いたトーンで
```

書きすぎは禁物です。**3回同じことを言ったら1行足す**、くらいの育て方がちょうどいい。何を書き、何を書かないかの設計は書籍の第7章が詳しいです。

## ★4 権限とAuto modeの体系 — 安全装置の全体像

今日何度も出会った「〜してもよいですか?」の全体像です。

- Claude Codeの操作には**権限モデル**があり、ファイル変更・コマンド実行は原則あなたの承認が必要
- 「毎回聞かれるのが煩わしい」場合、承認を省略する動作モード（Auto mode系の設定）がありますが、**省略するのは「間違えても被害が小さい操作」だけ**にするのが原則
- さらに進むと、実行環境ごと隔離するサンドボックスという選択肢もあります

今日の範囲(自分のフォルダ内で1ファイルのアプリ)は被害半径が最小の世界でした。仕事のリポジトリで使うときは、この安全装置の設計から入ってください。書籍第7章「ガードレールを設計する」がそのための章です。

## ★5 スキル — 今日の「型」を保存して配る

後編9で使った検証プロンプト、毎回コピペするのは面倒ですよね。**やり方そのものをファイルとして保存し、Claudeが必要なときに自分で読み込む**仕組みがスキル（Agent Skills）です。

たとえば今日の検証手順をスキル化すると、次からは「検証して」の一言で、①確認条件を読み、②実際に確認し、③どう確認したか報告する、が毎回同じ品質で走ります。**個人の作法をチームに配れる**のもスキルの強みで、書籍では第3章（使う・作る）と第8章（設計する・配る）の二段階で扱っています。

## ★6 スペック駆動開発 — ゴールの一文を仕様に育てる

今日の「ゴールの一文＋確認条件3つ」は、実は仕様書の最小形です。作るものが大きくなったら、この一文を**プロダクト要求定義書（PRD）**に育て、「何を作るか」と「どう作るか」を分けて進める方法があります。スペック駆動開発と呼ばれる進め方です。

目安: 確認条件が**7個を超えたら**、バイブコーディングだけで押し切らず仕様化を考えるタイミング。Kiro、Spec Kitなどの専用フレームワークもありますが、まずは書籍第5章の「達人に学ぶスペック駆動開発」から入るのがおすすめです。

## ★7 任せきる — /goalと/loopの世界

今日は画面に張り付いて「見て、直す」を回しました。次の段階は、**見ていない間に作らせる**ことです。

- **ゴール実行（/goal）**: 完了条件を渡すと、満たすまでClaudeが自走する。今日の「ゴールの一文＋確認条件」がそのまま入力になる
- **自動ループ（/loop）**: 定期的・継続的にタスクを回し続ける。監視や改修の自動化に使う

鍵は今日すでに学んでいます。**検証可能な完了条件を書けること**（後編9でやったこと）と、**「できました」を鵜呑みにしない検証**です。任せきるとは、放置ではなく検証の自動化です。書籍第9章がこのテーマのクライマックスです。

## ★8 外部とつなぐ前の安全チェックリスト

今日のアプリは自分のPCの中で完結していました。この先、外部サービス接続（MCP）、GitHub連携、クラウド実行に進むときは、**信頼の境界**が変わります。最低限これだけ確認してから:

- [ ] 秘密情報（APIキー・パスワード）をプロンプトやコードに直書きしていないか
- [ ] 入れようとしている外部ツール・スキルは信頼できる提供元か
- [ ] 外部から来た文章（Webページ・Issue・メール）を「指示」として実行させていないか — 外部入力は指示ではなくデータとして扱わせる
- [ ] 自動実行には停止手段と、失敗時に戻せるバックアップがあるか

詳しくは書籍第6章（手元から離す）と第7章（信頼境界の設計）へ。
