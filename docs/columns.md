## ★0 AI駆動開発とは — 今日やったことの正体

今日の3原則（型で渡す／作る前に計画を見る／曖昧なまま作らせない）には名前があります。**AI駆動開発**です。

### バイブコーディングとの関係

バイブコーディングは「言葉で伝えて、動くものを見て、直す」やり方でした。今日の最初の15分（テトリス）がそれです。速い。ただし、**速さは方向を保証しません。**

AI駆動開発は、そこに一段の構造を足したものです。ひとことで言えば、**AIを主たる実装者に据え、人間は「意図・判断・検証」を担当する**開発の進め方です。手を動かす量を減らすのではなく、**人間が担当する場所を変える**のが要点です。

| 誰が | 何を担当するか |
|---|---|
| AI | 実装、調査、選択肢の提示、下書き |
| 人間 | 何を作るかの決定、計画の承認、できあがりの検証 |

### なぜ「型・計画・詰め」の3つなのか

AIに任せたときに崩れる場所が、だいたいこの3つに集まるからです。

| 崩れ方 | 何が起きるか | 打ち手 |
|---|---|---|
| **文脈が毎回途切れる** | 前回言ったことを次のセッションでは知らない。同じ説明を毎回する羽目になる | **スキル**（原則①）。指示をファイルにして持たせる |
| **合意せずに実装が始まる** | 出てきてから「そうじゃない」と気づく。作り直しになる | **計画**（原則②）。実装前に計画を読んで承認する |
| **決めていないことを勝手に決める** | AIが埋めた仮定が、あとから仕様として固定される | **詰め**（原則③）。決定は人間が明示的に下す |

3つとも「AIが賢くなれば要らなくなる」ものではありません。**どれも情報の受け渡しの問題**であって、能力の問題ではないからです。

### よくある誤解

- **「任せる＝丸投げ」ではありません。** 丸投げは、決定までAIに預けてしまうことです。AI駆動開発では、決定は最後まで人間が持ちます。今日ハンズオン④で「詰めて」が一問ずつ聞いてきたのは、**決定をあなたに返している**からです
- **「コードを読めないと無理」でもありません。** 今日あなたが判断したのは、画面と計画とチケットでした。コードは一度も読んでいません
- **ドキュメントを書くのが目的でもありません。** `CONTEXT.md` や ADR を残すのは、**次のセッションのAIに渡すため**です。人間のための書類仕事ではなく、AIへの入力です

### 今日の先

今日は最小形を一周しました。この先は3段あります（→ ★5・★6・★7）。

1. **型を増やす** — 「詰めて」以外にも、自分が毎回言っていることをスキルにしていく
2. **仕様で導く** — 詰めた結果を仕様として育て、大きなものを計画的に作る
3. **任せきる** — 完了条件と検証手順を渡して、見ていない間に作らせる

**今日ハンズオン④で作った「詰めて」の出力（用語集・決定の記録・チケット）は、そのまま3段目の入力になります。** 今日の型は、最先端の自律開発とひと続きです。

## ★1 モデルとeffortの使い分け — 回転数を上げる

Claude Codeは、頭脳となるモデルと、考える深さ（effort）を切り替えられます。

- **試作・見た目の調整**（今日やったこと）: 軽めのモデル×浅いeffortで十分。応答が速い=回転数が上がる=バイブコーディングが気持ちよく回る。利用枠の消費も少ない
- **難しいバグ・設計の相談**: 強いモデル×深いeffortに切り替える価値がある

切り替えは `/model` コマンドから。迷ったらデフォルトのままでOKですが、「なんか遅いな」と感じたら軽い方へ、「なんか浅いな」と感じたら深い方へ。この感覚が身につくと利用枠が倍長持ちします。

## ★2 プランモード — 作る前に相談する

前編3では「計画を出して。許可するまで実装しないで」と**指示文でお願いして**計画を先に出させました。同じことを**機能として**用意しているのがプランモード（計画モード）です。オンにすると、Claudeはファイルを変更できなくなり、「こう進めます」という計画だけを提示して、あなたの承認後に実行します。

指示文でのお願いは、Claudeが勢い余って実装を始めてしまうことがあります。プランモードは**仕組みとして止める**ので取りこぼしがありません。前編3のやり方に慣れたら、こちらに乗り換えてください。

使いどころ: 「この機能を足すとしたら何が必要?」「このアプリをスマホアプリ化できる?」のような、**着手前の相談**。今日の言葉で言えば、原則②「作る前に計画を見る」を機能で強制するスイッチです。

## ★3 CLAUDE.mdの第一歩 — 毎回言うことをファイルにする

プロジェクトのフォルダに `CLAUDE.md` というファイルを置くと、Claude Codeは毎回それを読んでから作業します。つまり**「毎回言っていること」の置き場**です。

今日のワークショップでいえば、こんな内容が候補です:

```markdown
# このプロジェクトの約束
- アプリは1つのHTMLファイルで完結させる
- 変更のたびに、ブラウザでの確認手順を最後に一行で書く
- 派手な色使いはしない。配色は落ち着いたトーンで
```

書きすぎは禁物です。**3回同じことを言ったら1行足す**、くらいの育て方がちょうどいい。何を書き、何を書かないかの設計は書籍の第7章が詳しいです。

## ★4 権限とAuto modeの体系 — 安全装置の全体像

今日何度も出会った「〜してもよいですか?」の全体像です。

- Claude Codeの操作には**権限モデル**があり、ファイル変更・コマンド実行は原則あなたの承認が必要
- 「毎回聞かれるのが煩わしい」場合、承認を省略する動作モード（Auto mode系の設定）がありますが、**省略するのは「間違えても被害が小さい操作」だけ**にするのが原則
- さらに進むと、実行環境ごと隔離するサンドボックスという選択肢もあります

今日の範囲(自分のフォルダ内で1ファイルのアプリ)は被害半径が最小の世界でした。仕事のリポジトリで使うときは、この安全装置の設計から入ってください。書籍第7章「ガードレールを設計する」がそのための章です。

## ★5 スキル — 今日の「型」を保存して配る

前編2で作った「詰めて」がこれです。**やり方そのものをファイルとして保存し、Claudeが必要なときに自分で読み込む**仕組みをスキル（Agent Skills）と呼びます。

今日は1つ作りましたが、価値が出るのは2つ目からです。後編9で使う検証プロンプトも、毎回コピペする代わりにスキルにできます。

たとえば検証手順をスキル化すると、次からは「検証して」の一言で、①確認条件を読み、②実際に確認し、③どう確認したか報告する、が毎回同じ品質で走ります。**個人の作法をチームに配れる**のもスキルの強みで、書籍では第3章（使う・作る）と第8章（設計する・配る）の二段階で扱っています。

完成形の3枚構成（`tsumete` が `tsumetsume` と `ddd` を呼ぶ）は、第8章で扱う「大きな型を役割で分割する」の最小例です。

## ★6 スペック駆動開発 — 詰めた結果を仕様に育てる

前編4の「詰めて」が残した用語集（`CONTEXT.md`）・決定の記録（ADR）・チケット一覧は、実は仕様書の最小形です。作るものが大きくなったら、これを**プロダクト要求定義書（PRD）**に育て、「何を作るか」と「どう作るか」を分けて進める方法があります。スペック駆動開発と呼ばれる進め方です。

目安: 完成条件が**7個を超えたら**、バイブコーディングだけで押し切らず仕様化を考えるタイミング。Kiro、Spec Kitなどの専用フレームワークもありますが、まずは書籍第5章の「達人に学ぶスペック駆動開発」から入るのがおすすめです。

## ★7 任せきる — /goalと/loopの世界

今日は画面に張り付いて、計画を読み、質問に答えていました。次の段階は、**見ていない間に作らせる**ことです。

- **ゴール実行（/goal）**: 完了条件を渡すと、満たすまでClaudeが自走する。前編4の「詰めて」が残した完成条件とチケットが、そのまま入力になる
- **自動ループ（/loop）**: 定期的・継続的にタスクを回し続ける。監視や改修の自動化に使う

鍵は今日すでに学んでいます。**曖昧さを潰して検証可能な完了条件にすること**（原則③）と、**「できました」を鵜呑みにしない検証**です。任せきるとは、放置ではなく検証の自動化です。書籍第9章がこのテーマのクライマックスです。

## ★8 外部とつなぐ前の安全チェックリスト

今日のアプリは自分のPCの中で完結していました。この先、外部サービス接続（MCP）、GitHub連携、クラウド実行に進むときは、**信頼の境界**が変わります。最低限これだけ確認してから:

- [ ] 秘密情報（APIキー・パスワード）をプロンプトやコードに直書きしていないか
- [ ] 入れようとしている外部ツール・スキルは信頼できる提供元か
- [ ] 外部から来た文章（Webページ・Issue・メール）を「指示」として実行させていないか — 外部入力は指示ではなくデータとして扱わせる
- [ ] 自動実行には停止手段と、失敗時に戻せるバックアップがあるか

詳しくは書籍第6章（手元から離す）と第7章（信頼境界の設計）へ。
