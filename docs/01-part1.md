## 1. オープニング

### バイブコーディングとは

コードを書く代わりに、「こうしたい」という内容を言葉で伝えてAIに実装させ、動くものを見て、また言葉で直す開発のやり方です。設計書も仕様書も、厳密なものは最初は書きません。やることは3つです。

1. AIに作りたいものを伝える
2. AIが作って動くようになったものを見て確認する
3. 感じた間違い・違和感をAIに指摘する

「コードが読めないのに大丈夫?」と思うかもしれませんが、大丈夫です。判断はすべて画面で確認して決めます。コードを読んで判断する必要はありません。

コードが読める人も、気になったところを自分の手で直さないでください。どんなに小さな変更も、言葉で伝えてAIに直させます。そのかわり、できたものが意図どおりかを確かめる役は妥協しません。**作るのはAI、品質を確かめるのは自分**という分担です。

バイブコーディングが向いているのは、欲しいものがまだはっきりしないときです。作って、触って、直すうちに「本当はこういうものが欲しかった」が見えてきます。欲しいものがはっきりしたら、今度は仕様に書いてから作らせるほうが確実です。前半では、この2つを順番に体験します。ハンズオン①でノリで作り、ハンズオン②〜③と宿題で、自分のアイデアを仕様に育てます。

### Claude Codeはどう動いているのか

Claude Codeはコーディングに特化したエージェントハーネスです。エージェンティックループを回しながら人間との対話を繰り返し、都度の指示に合った応答やツール利用を重ねることで、人間との協業を実現します。動かしている部品は4つあります。

#### モデル

頭脳にあたる中心部分です。**文章を受け取って、次に来る文章を返すことだけができます。**

Claude Code上で既定で使えるのは、Anthropicが提供するClaudeシリーズです。用途別に4系統あります。

| 系統 | 位置づけ |
|---|---|
| **Fable** | 最も高性能。難しい設計や長時間の自律作業向け。Pro・Maxでは、プランの利用枠ではなく追加の利用クレジットから支払う扱いになることがあり、`/model` の一覧にも注記が出ます |
| **Opus** | 高性能。複雑な実装や込み入ったデバッグ向け |
| **Sonnet** | 標準。日常の開発はこれで十分 |
| **Haiku** | 軽量・高速。単純な作業や大量の繰り返し向け |

賢いほど応答は遅く、利用枠の消費も増えがちです。**上から順に良いわけではなく、作業内容やトークン消費を考慮して選んでください。** 切り替えはこのあと `/model` で試します。

何も選ばなかったときに使われる既定のモデルは、プランで違います。**ProはSonnet、MaxはOpusです。** Maxの人は、このあとの `/model` で忘れずにSonnetへ切り替えてください。

#### ツール

モデル自体には、ドキュメントやソースコードを編集する能力はありません。編集を担当するのはハーネスの側です。モデルが「この指示なら、このツールでこうすればよい」と応答すると、Claude Codeが実際にBashなどのツールを動かしてファイルを書き換えます。チャットでやりとりするだけの状態から実世界に作用できる状態へ変わるのは、ここです。

#### コンテキスト

モデルは1問1答ができるだけで、以前のやりとりを覚えておく機能はありません。そこでClaude Codeは、セッション中のチャット内容・編集対象のファイル・コマンドの出力結果を保持し、毎回のやりとりにそれらを付け加えてモデルへ送っています。この記憶領域を**コンテキストウィンドウ**と呼びます。モデルが前回のやりとりを覚えているように見えるのは、この仕組みによるものです。

モデルごとに最大のコンテキストウィンドウが決まっており、Anthropicが提供するデフォルトではFable/Opus/Sonnetは1M（M=100万）、Haikuは200K（K=1,000）です。

#### 権限

Claude Codeは、ファイルを書き換えたりコマンドを実行したりするツールを使うたびに「実行してもよいですか?」と確認を挟みます。これが安全装置の本体です。この確認をどこまで挟むかを切り替えるのが **Permission mode** で、4つあります。

| モード | 挙動 |
|---|---|
| **Manual Mode（手動）** | ツールを使うたびに確認する |
| **Accept Edits ON（自動・編集のみ）** | ファイル編集は自動で承認し、コマンド実行など編集以外は確認する |
| **Auto Mode（自動・リスク判定）** | AIがツール実行のリスクを自動判定し、低リスクと判断したものは確認なしで進める。破壊的な操作や踏み込んだ操作は通常どおり確認・拒否される。**今日はこのモードで進めます** |
| **Plan Mode（プランモード）** | 何も変更せず、まず計画だけを提示する。確認して進めるかを判断してから実行に移る |

Pro・Maxでは、**最初からAuto Modeが既定**になっています。入力欄の下に表示されているモードを確認してください。切り替えは `/config` の Permission mode、または入力欄の Shift+Tab から。押すたびにモードが切り替わります。**以前の設定が残っていてAuto Modeになっていない人は、ここで切り替えてください。** 低リスクな操作の確認をAIが肩代わりしてくれる分、テンポよく進められます。ただし破壊的な操作や踏み込んだ操作は、Auto Modeでも変わらず確認が挟まります。そこだけは自分の目で読んでから答えてください。

### 基本的なスラッシュコマンドを試す

Claude Codeの入力欄で `/` から始まる**スラッシュコマンド**を打つと、設定の確認や変更ができます。手を動かし始める前に、6つだけ実際に確認しておきます。

それでは実際にここまで作業を進めてください。

#### ① `/help` — 何が使えるかを一覧する

```text
/help
```

Claude Codeにインストールされているコマンドの一覧が出ます。このあと出てくるコマンドを忘れても、ここから探せます。

並ぶのは組み込みのものだけではありません。あとから入れたエージェントスキルや、自分で書いたカスタムコマンドも、カスタムコマンドの一覧に表示されます。ハンズオン①で自作する `tsumete` なども、保存場所を読み込ませると `/tsumete` のようにここへ並びます。初回の手順は前半2で確認します。

> 入力欄で `/` を1文字打つだけでも、同じ候補が絞り込み付きで出ます。名前をうろ覚えのときはこちらが速いです。

#### ② `/status` — いまの状態を確認する

```text
/status
```

バージョン・いま使っているモデル・ログイン中のアカウント・接続中のMCPサーバーなどがまとめて表示されます。

#### ③ `/model` — 使うモデルを選ぶ

```text
/model sonnet
```

上のコマンドでSonnetを選びます。`/model` だけを入力すると一覧が出ます。上下キーでモデルを選び、左右キーでそのモデルのeffort（考える深さ）を変え、Enterで確定します。

- **このワークショップでは、前半・後半を通して Sonnet × medium を推奨します。** 次の④でeffortも揃えます
- 宿題でアイデアを詰めるときや、難しいバグに詰まったときは、一時的に賢いモデルに切り替えても構いません。解決したら Sonnet × medium に戻してください（Advisory Modeという設定もありますが、時間があれば説明します）

<a id="④-effort--考える深さを選ぶ任意"></a>

#### ④ `/effort` — 考える深さを選ぶ

```text
/effort medium
```

`low` / `medium` / `high` / `xhigh` / `max` から選びます。同じモデルでも、答える前にどれだけ考えるか（推論の深さ）が変わります。このワークショップでは `medium` に設定します。③の `/model` 画面でも設定できますが、このコマンドを使うとeffortだけを直接指定できます。

思考の深さの違い自体に価格の違いはありません。ただし深く思考するほどトークン消費が増える傾向があり、応答速度も遅くなる傾向があります。

#### ⑤ `/usage` — 利用枠の残量を確認する

```text
/usage
```

5時間ごとの枠と週ごとの枠、それぞれの残量が表示されます。今日はこのあとハンズオンや宿題で数時間はClaude Codeを使い続けます。途中で不安になったら、いつでもこのコマンドで確認してください。**足りなくなった場合、プランのアップグレードをする必要があることに注意してください。**

<a id="①-permissions--許可したことの一覧"></a>

#### ⑥ `/permissions` — 許可の仕組みを見る

```text
/permissions
```

一度許可した内容はルールとしてここに溜まっていき、あとから一覧で確認・取り消しができます。このあとハンズオン①で見る確認画面で「2番」（以後は聞かない）を選ぶたびに、ここへ1行ずつ追加されます。Auto Modeでは確認そのものが少ないので、今日はあまり増えないはずです。身に覚えのないものが増えていたら、ここで消してください。

## 2. ハンズオン① Claude Code基礎

ここではClaude Codeの3本柱を説明し、説明と実践を区切りながら、バイブコーディングとエージェントスキルを主線で実践します。MCPは仕組みを説明したあと、Gmail連携を早く終わった人向けの任意課題として実践します。全員で進める主線は、アプリを作る、`tsumete` の簡易版を作る、設定を開いて中を見る、の順です。

1. **バイブコーディング**してみる
2. **MCP**の仕組みを説明し、外部サービスとの連携はGmailの任意課題で試してみる
3. **エージェントスキル**に仕事のやり方を定義して、毎回決まったことを実行できるようにしてみる

### バイブコーディングしてみる

新しいリポジトリ `vibecoding-0908` をその場で作り、Claude Codeで開いて、簡単なものを1つバイブコーディングで作ります。

それでは実際にここまで作業を進めてください。

1. **VS Codeで、Claude Code(拡張)を起動する** — 今どこを開いていても問題ありません
2. **`vibecoding-0908` という名前で新しいリポジトリを作る** — 今日使うリポジトリは、ホームフォルダの下の `github` フォルダ（`~/github/`。Windowsでは `C:\Users\⟨Windowsのユーザー名⟩\github\`）にまとめて作ります。無ければClaude Codeが自動で作ります。普段使っているリポジトリの置き場所がすでにある人は、無理に合わせず、そちらに作って構いません

    **`gh` コマンドが使える場合（事前準備0.4参照）**

    Claude Codeのパネルに次を貼り付けて送信します。

    ```text
    ~/github フォルダ（無ければ作成）に移動して、
    次のコマンドでリポジトリの作成とcloneをしてください。

    gh repo create vibecoding-0908 --public --clone --add-readme
    ```

    Windowsでは `~/github` のままだと場所が見つからないことがあるので、フォルダを書き換えた次のプロンプトを使ってください。⟨Windowsのユーザー名⟩ は、エクスプローラーで `C:\Users` を開くと並んでいるフォルダ名です（Microsoftアカウントの名前が短くなっていることがあります）。

    ```text
    C:\Users\⟨Windowsのユーザー名⟩\github フォルダ（無ければ作成）に移動して、
    次のコマンドでリポジトリの作成とcloneをしてください。

    gh repo create vibecoding-0908 --public --clone --add-readme
    ```

    `gh repo create` が、GitHub上へのリポジトリ作成と手元へのcloneを1回でやってくれます。`--public` を `--private` にすれば非公開になります（今日の範囲ではどちらでも構いません）。

    認証は事前準備0.4で済んでいるので、ログインを求められることはないはずです。求められた場合やエラーが出た場合は、事前準備の「つまずき早見表」の `gh repo create` の行を参照するか、そのままエラーをClaude Codeに貼って「直してください」と頼んでください。

    **`gh` コマンドが使えない場合**

    ブラウザでGitHubを開き、右上の「+」→「New repository」から `vibecoding-0908` という名前でリポジトリを作成してください（Public/Privateどちらでも構いません）。**このとき「Add a README file」にチェックを入れてください。** 作成できたら表示されるURLをコピーし、Claude Codeに次のように貼り付けます。

    ```text
    ~/github フォルダ（無ければ作成）の中に、次のリポジトリをcloneしてください。
    ⟨コピーしたURLを貼り付ける⟩
    ```

    Windowsでは、`~/github` を `C:\Users\⟨Windowsのユーザー名⟩\github` に書き換えて頼んでください。

    どちらの方法でも、このリポジトリは今日のこのハンズオンだけで使う、使い捨てです。

3. **できたフォルダをVS Codeで開き直す** — 「ファイル」→「フォルダーを開く…」で `~/github/vibecoding-0908` を選びます。手順2の直後は、Claude Codeはまだ最初に開いていたフォルダを見ている状態のままです。ここで開き直すことで、以降の作業がこのリポジトリの中で行われるようになります。**VS Code左側のファイル一覧に `README.md` が1枚だけ表示されていれば正しい状態です**（`--add-readme` によって自動で置かれたものです）
4. **Claude Codeのパネルを開き直す** — 開き直したウィンドウでは、Claude Codeのパネルは閉じています。事前準備と同じ手順で開いてください。このフォルダで初めて開くときは、フォルダを信頼するかを聞かれるので「Yes, I trust this folder」を選びます
5. 下の「お題の例」から1つ選ぶか、自分で思いついたものをそのまま指示する
6. **できあがったものをブラウザで開いて動かす** — VS Code左側のファイル一覧でHTMLファイルを右クリックし、「Finderで表示」（Windowsは「エクスプローラーで表示」）→ 出てきたファイルをダブルクリック
7. 気になったところ（見た目・動き・言葉づかいなど）を2〜3個まとめて1回で伝えて直させる

> **どこで詰まっても、まずClaude Codeに聞いてください。** 「作ったファイルをブラウザで開く方法を教えて」でも答えてくれます。手順が分からないこと自体もAIに聞くことに慣れましょう。

### お題の例

迷ったら、そのままコピペしてください。自分のやりたいことがあれば、それを優先して構いません。

それでは実際にここまで作業を進めてください。

```text
ブラウザで遊べるテトリスを、1つのHTMLファイルで作ってください。
矢印キーの左右で移動、上キーで回転、下キーで落下を速められ、
横一列そろったら消えてスコアが増え、ブロックが天井まで積み上がったらゲームオーバー、
という基本のルールで動くようにしてください。
```

もう少し手順のある題材で試したい場合は、[starters/](../starters/) にある3種のお題（ポモドーロタイマー・診断チャート・習慣トラッカー）も使えます。使い方は [starters/README.md](../starters/README.md) を参照してください。

### 「許可しますか?」と聞かれたら

手動モードのClaude Codeは、ファイルの作成・変更やコマンドの実行の直前で必ず一度止まり、こういう確認を挟みます。

```text
Bash command

  mkdir -p tetris
  作業用のフォルダを作成します

Do you want to proceed?
❯ 1. Yes
  2. Yes, and don't ask again for mkdir commands in /Users/you/handson
  3. No, and tell Claude what to do differently (esc)
```

今日使うAuto Modeでは、この確認をAI自身が肩代わりします。リスクが低いと判定した操作（自分のフォルダの中でファイルを作る・編集するなど）は、確認なしでそのまま進みます。だから体感としては「毎回聞かれる」ではなく「ほとんど聞かれない」になります。**見える回数が減った分、出てきたときこそ普段よりよく読んでください。** 「これは自分の判断だけでは進めない方がいい」とAIが判断したサインです。

> **見た目は環境で少し変わります。** ターミナルでは上のような番号付きのリストで出て、矢印キー＋Enter（または数字キー）で選びます。VS Code拡張ではボタンとして出ることがあります。並んでいる選択肢の中身は同じなので、下の表で読み替えてください。

| 選択肢 | 意味 | 今日どう使うか |
|---|---|---|
| **1. Yes** | 今回だけ許可する | 迷ったらこれ |
| **2. Yes, and don't ask again for ...** | 同じ種類の操作を、以後は聞かずに実行してよいと記憶させる。このルールはAuto Modeの判定より優先されます | 同じ確認が何度も出て煩わしくなったらこれ。記憶される範囲は、その行に表示されているフォルダの中だけ |
| **3. No, and tell Claude ...** | 断って、代わりにどうしてほしいかを伝える。選ぶと入力欄に戻るので、そこに希望を書きます | やろうとしていることが違うと思ったとき。Escキーでも同じ |

見出しは操作の種類で変わります。`Bash command` ＝コマンド実行、`Create file` ＝ファイル作成、`Edit file` ＝ファイル変更。ファイルを作る・変えるときは、2番が `Yes, for this session`（このセッションの間は聞かない）になります。

今日の範囲では、表示された内容が「今いるフォルダの中のファイル操作」なら 1 か 2 を選んで構いません。

> **確認が出ないからといって、何もしていないわけではありません。** Auto Modeは確認を省略しているだけで、ファイルは実際に作られたり変わったりしています。都度、画面を見て確認する。これは今日やることの1番目と同じ姿勢です。何を許可したかは、あとで `/permissions` から確認・取り消しができます。

### まとめて1回で直させる

AIが作ったものを触ると、必ずといっていいほど「思ってたのと違う」ことがあります。それを1個ずつ伝えているとキリがないので、まずは2〜3個まとめて1回の指示にしてみましょう。

それでは実際にここまで作業を進めてください。

```text
3点直してください。
1. 落ちるスピードが速すぎるので、もう少しゆっくりに
2. 次に来るブロックが分かるように、プレビューを表示して
3. 全体の色合いをもう少し明るく
```

### もっと深刻な状態になったらこう直す

「想定以上に壊れて動かない」ことも起きます。そのときの手順です。

| いつ使う | 打ち手 | どうやる |
|---|---|---|
| 画面が真っ白・エラーが出た | **① エラーをそのまま貼る** | エラーメッセージや画面のスクショを説明せずそのまま貼り、「動かなくなりました。原因を調べてください」 |
| 同じ不具合を3回直させても直らない・どんどん悪化する | **② ひとつ戻す** | 「さっきの変更を取り消して、直前の動いていた状態に戻してください」 |
| 欲張った指示のせいで空中分解した | **③ 小さく指示しなおす** | 一度に複数頼んだり、複雑で壮大な指示をしていたら「まず1個だけ」に分割してからやり直す |

「直させたらもっと動かなくなった」を繰り返すと、深みにはまります。**3回直させても直らなければ、直させ続けるのをやめて戻す**と決めておきましょう。

②は、Claude Codeの**巻き戻し**でも戻せます。VS Code拡張では、戻りたい時点のメッセージにマウスを乗せると巻き戻しのボタンが出ます（ターミナルでは `/rewind`）。ただし、Claude Codeがコマンド実行で変更したファイルは巻き戻しの対象外です。戻らなかったときは、表のとおり言葉で頼んでください。

この3つを、今日は**リカバリー3手**（貼る・戻す・小さくする）と呼びます。それでもうまくいかないときは、`/model` で賢いモデルに切り替えて同じことをもう一度頼んでください。軽いモデルで的外れな応答が続くときは、これでうまくいくことがあります。解決したら、Sonnet × medium に戻してください。

### 最初のエージェントスキルを作ってみる（`tsumete`）

3本柱の最後、エージェントスキルです。「毎回同じことを言う」代わりに、**やり方そのものをファイルに保存**しておくと、以後は一言でその作法を呼び出せます。

今日この後、宿題まで繰り返し使う `tsumete` という名前のエージェントスキルを、まず簡単な形で作ってみます。**呼び出しは `/tsumete` です。** 今日はこのあと何度も使うので、名前を覚えておいてください。

それでは実際にここまで作業を進めてください。

```text
いま作ったアプリの概要を README.md に短く残してください。アプリのコードは変更しないでください。
続けて、.claude/skills/tsumete/SKILL.md というファイルを作ってください。
中身は次のとおりです。

---
name: tsumete
description: 計画や仕様を実装前に問い詰めて明確にする。
disable-model-invocation: true
---

# 詰めて

対象は、いま開いているフォルダの README.md です。まず読んでから始めてください。

この計画について、一問ずつ質問して詳しく聞いてください。
それぞれの質問には、あなたのおすすめの答えも添えてください。
```

まずはこのプロジェクト（`vibecoding-0908`）の中に置きます。`.claude/skills/` というのが、そのプロジェクトの中だけで使えるエージェントスキルの置き場所です。

今回は `.claude/skills/` 自体を新しく作ったので、Claude Codeを開き直してください。
VS Code拡張ではコマンドパレット（macOSは Cmd+Shift+P、Windowsは Ctrl+Shift+P）から `Developer: Reload Window` を実行し、Claude Codeのパネルを開きます。
CLIでは `/exit` で終了し、同じフォルダで `claude` を起動し直します。

いったん読み込まれた置き場所では、`SKILL.md` の追加や変更は会話中でも反映されます（[公式ドキュメント](https://code.claude.com/docs/en/skills#edit-a-skill-during-a-session)）。
ただし、一度呼んだ本文は会話に残るので、本文を直して試すときは `/clear` で会話を切ります。
開き直したら、次のように呼んでみてください。

それでは実際にここまで作業を進めてください。

```text
/tsumete
```

`/` を打つと候補に出てきます。一問ずつ質問が返ってくれば成功です。これがエージェントスキルの正体です。何かを頼むたびに長い説明を書く代わりに、一度ファイルに書いておけば、以後は `/tsumete` の一言で同じ振る舞いを呼び出せます。

> **`disable-model-invocation: true` という行を入れました。** 「Claudeが自分の判断で勝手に起動してはいけない。人間が `/tsumete` と打ったときだけ動く」という指定です。問い詰めは何十往復もする長い作業なので、始めるかどうかは人間が決めます。この行の意味は、ハンズオン③でもう一度扱います。

> この `tsumete` は、ハンズオン②・③でさらに育てていきます。完成ではありません。

## 3. ハンズオン② 自分が作りたいアプリを考える

ここからが前半の本題です。さっきまでは「なんでもいいからノリで動かす」体験をしました。次は「何を作りたいのか」を自分の中からしっかり引き出す番です。

まず、自分のアプリ用のリポジトリを作ります。`vibecoding-0908`（使い捨て）とは別の、新しいリポジトリです。

それでは実際にここまで作業を進めてください。

1. `vibecoding-0908` はここではいったん開いたままでも大丈夫です
2. **`myapp` という名前で新しいリポジトリを作る** — 手順はハンズオン①とまったく同じで、置き場所も同じ（`~/github/`。普段の置き場所がある人はそちら）です。違うのは **`--private`** の1箇所だけです

    ```text
    ~/github フォルダに移動して、
    次のコマンドでリポジトリの作成とcloneをしてください。

    gh repo create myapp --private --clone --add-readme
    ```

    > **非公開の理由。** あなただけのアプリのアイデアがこのリポジトリに入ります。`README.md` だけでなく、`CONTEXT.md`（用語集）や `docs/adr/`（決定記録）など重要な文書たちが保存されます。あとから公開するのは1クリックなので、迷ったら非公開にしておきましょう。

3. **できた `myapp` フォルダをVS Codeで開き直す** — 「ファイル」→「フォルダーを開く…」で `~/github/myapp` を選びます。これで、以降の作業がこのリポジトリの中で行われるようになります。VS Code左側のファイル一覧に `README.md` が1枚だけ表示されていれば正しい状態です
4. **Claude Codeのパネルを開き直す** — ハンズオン①の手順4と同じです。このフォルダで初めて開くので、フォルダを信頼するかを聞かれたら「Yes, I trust this folder」を選びます

```
~/github/myapp/   ← ここが自分のアプリの家。今日から最後までここ
└── README.md               ← いま中身を書く（ファイル自体はもうある）
```

**このリポジトリを覚えておいてください。宿題も後半も、ここを開いて始めます。**

### 開発の前提を `CLAUDE.md` に書く

壁打ちや試作に入る前に、この講座で作る範囲をファイルに残します。
ブラウザだけで動く小さなアプリにし、ログイン、課金、外部サービス連携は扱いません。
会話を切っても同じ前提で進めるために、`CLAUDE.md` を使います。

プロジェクトのフォルダ直下に `CLAUDE.md` という名前のファイルを置くと、Claude Codeは会話を始めるたびに、まずそれを読んでから作業します。
`/clear` で会話を切っても消えず、そのフォルダを開いている間はどの会話にも効きます。
前半2で作ったエージェントスキルと、前半5で試すHooksとは、役割が異なります。

| | `CLAUDE.md` | エージェントスキル | Hooks |
|---|---|---|---|
| いつ効くか | **会話を始めるたびに必ず読まれる** | Claudeが必要と判断したとき、または `/tsumete` のように人が呼んだとき | 条件が合えば必ず実行される |
| 向いている中身 | 「このプロジェクトでは常にこうする」という短い約束 | 「問い詰める」のような、手順のある作法 | 「編集したら記録する」のような、確実に動かしたい処理 |
| 置き場所 | `myapp/CLAUDE.md` | `myapp/.claude/skills/` | `myapp/.claude/settings.json` |

`tsumete` は問い詰めの手順だったので、エージェントスキルにしました。
作る範囲と文書の管理先は、このプロジェクトで常に守る約束です。
だから `CLAUDE.md` に書きます。

それでは実際にここまで作業を進めてください。

`myapp` を開いた状態で、Claude Codeに次を貼り付けてください。

```text
このフォルダの直下に CLAUDE.md を作り、次の内容をそのまま書いてください。

# このプロジェクトの約束

- プロジェクトの概要と仕様は README.md で管理する
- 開発計画とタスクは TASKS.md で管理する
- ブラウザだけで動く構成にする。HTMLファイル1つを基本とする
- ログイン・課金・外部サービス連携は今回やらない。仕様では「今回やらないこと」に理由つきで残す
- 後半の実装時間で作りきれる規模まで削る
- データを残す場合は、ブラウザ内の保存（閉じても消えない）までにする
```

同じ内容の見本が [templates/CLAUDE.md.sample](../templates/CLAUDE.md.sample) にあります。

作れたら `/clear` で会話を切り、続けて前半2で使った `/context` を打ってください。
表示の中に **Memory files** という欄があり、いまの会話に読み込まれている `CLAUDE.md` が並びます。
そこに `myapp` の `CLAUDE.md` があれば、この約束が読み込まれています。
無ければ、Claude Codeを一度終了して開き直してから確認してください。
中身を直したくなったら、`/memory` から開けます（こちらは読み込み前のファイルも候補に出るので、読み込みの確認には使いません）。

> **`CLAUDE.md` は約束であって、強制ではありません。** Claudeはこれを読んで従おうとしますが、Hooksのように機械的に止める仕組みではないので、長い会話の途中で忘れることもあります。忘れていると気づいたら、「`CLAUDE.md` を読み直してください」と言えば戻ります。コミット前のレビュー確認は、後半9でHooksとして設定します。

`CLAUDE.md` の育て方は、エージェントスキルと同じ「毎回言っていることをファイルにする」です。
ただし書きすぎは禁物で、**3回同じことを言ったら1行足す**、くらいがちょうどいいです。
毎回読まれるファイルなので、長くなるほど毎回の会話がそのぶん重くなり、Claudeが守れる精度も落ちます。
足すときは、守れたかどうかを目で確認できる形に書きます。
「いい感じに」ではなく「配色は落ち着いたトーンにする」、「ちゃんと確認して」ではなく「変更したら、ブラウザでの確認手順を最後に一行書く」です。
手順が長くなってきた項目は、`CLAUDE.md` に書き続けるのではなく、エージェントスキルへ移します。

必要な修正を済ませたら、このファイルだけを手元のGitに保存します。

それでは実際にここまで作業を進めてください。

```text
今開いている myapp リポジトリの CLAUDE.md だけをコミットしてください。
プッシュはしないでください。
```

### 壁打ちのやり方

Claude Codeとのチャットのやりとりで、自分の考えを整理します。いきなり実装させず、まずは頭の中のアイデアを広げて、言葉にすることに集中してください。

手元にあるアイデアを、まず一度そのまま出してしまいましょう。荒くて構いません。

それでは実際にここまで作業を進めてください。

```text
壁打ち相手になってほしい。まだアイデア段階なので、評価したり実装したりせず、一度に一つずつ質問して広げてほしい。

⟨作りたいものを、思いつくまま2〜3行で。箇条書きでも構いません⟩
```

このプロンプトは、Claudeに3つのことを頼んでいます。

| 頼んでいること | なぜ |
|---|---|
| **評価しない** | 良し悪しやおすすめを返されると、まだ育っていないアイデアがClaudeの案のほうへ寄っていきます。ここで育てたいのは、自分のアイデアです |
| **実装しない** | 何を作るかは、まだ決まっていません。先に作らせると、出来上がったものに考えが引っ張られます |
| **一度に一つずつ質問して広げる** | 質問がまとめて来ると、答えやすいものにだけ答えて終わりがちです。一つずつなら、自分の答えから次の質問が生まれ、アイデアが広がっていきます |

何も付けずに「壁打ちして」とだけ頼むと、Claudeは自分の案をいくつも並べ、質問もまとめて投げてきがちです。それはそれで参考になりますが、この段階では自分の考えを引き出すほうを優先します。

質問に答えながら、使う人や使う場面、似たアイデアまで広げます。
進めるアイデアを一つ選んだら、次のように伝えて4点へ絞ります。

それでは実際にここまで作業を進めてください。

```text
⟨選んだアイデア⟩で進めたい。
(1)何を作りたいのか、(2)誰が使うのか、(3)何ができればいいのか、(4)どんな体験にしたいのかを、
それぞれ1〜2行で言えるところまで、引き続き一つずつ質問してほしい。
```

次の4点を確認してください。

1. 何を作りたいのか
2. 誰が使うのか
3. 何ができればいいのか
4. どんな体験にしたいのか

ここでは細部まで詰め切らなくて構いません。ふわっとした状態で終えて大丈夫です。

壁打ちしていて「思ったより穴がある」と感じるかもしれませんが、正常です。頭の中では固まっているつもりでも、問答してみると隙間が見えます。見えた隙間は、この時間に埋めなくて構いません。

**広げるのが壁打ち、詰めるのが `tsumete` です。** 壁打ちでは評価を急がずにアイデアを広げ、進めるものを選びます。穴を埋めて仕様と設計を決めていくのは、ハンズオン③で育てる `tsumete` と宿題の役目です。ハンズオン①で作った `tsumete` の本文に「おすすめの答えも添えてください」と書いたのは、そちらが決めていくための道具だからです。工程でいえば、壁打ちが「Intent（何を作りたいのか）の明確化」に、`tsumete` が「エージェントスキルによる緻密化」にあたります。

> **アイデアが浮かばない人へ。** 無理にひねり出さなくて構いません。次のように切り出せば、Claude側から質問を始めてくれます。そのままメンターにも声をかけてください。
>
> ```text
> 作りたいものがまだ決まっていません。
> 最近困っていること・面倒だと感じていること・繰り返している手作業はないか、
> というところから一度に一つずつ質問して、一緒に見つけてください。
> ```

### READMEに書き出す

4点が言葉になったら、`README.md` として書き出します。書き込み用のワークシートは [templates/idea-readme.md](../templates/idea-readme.md) にあります。

それでは実際にここまで作業を進めてください。

```text
ここまで話した内容のうち、選んだアイデアについて README.md としてまとめてください。
- 何を作りたいか（一言で）
- 誰が使うか
- 何ができればいいか（3〜5個程度）
- どんな体験にしたいか
```

これが、頭の中のアイデア → AIとの対話 → 明文化されたIntent というプロセスの最初の成果物です。壁打ちで広げたアイデアは、ここから詰める側に渡します。このREADMEを、ハンズオン③で育てる `tsumete` で試しに問い詰め、宿題で仕様と設計を実装できるところまで詰めていきます。

### 中心の操作だけデモを試作して触ってみる

「どんな体験にしたいか」を、中心になる操作一つで確かめます。
壁打ちでは実装を止めていましたが、ここでは体験を確かめるための短いデモを作ります。

それでは実際にここまで作業を進めてください。

```text
README.md の「どんな体験にしたいか」を確かめたいです。
CLAUDE.md の条件を守り、中心になる操作を一つだけ、prototype/ 配下にHTMLのデモとして作って開いてください。
ほかの機能は実装しないでください。既存のファイルは変更しないでください。
```

画面を操作し、思っていた体験と違う点を伝えます。

```text
いま触って気づいたことを以下に書くので README.md に反映してください。
⟨違和感や、こう動いてほしいと思ったことを書く⟩
```

気づきを残したら、試作用に作ったファイルだけを削除します。
後半の実装は、これから詰める仕様を基に始めます。

```text
いまデモ用に作った prototype/ 配下のファイルだけを削除してください。
README.md、CLAUDE.md と、それ以外の既存ファイルは残してください。
```

書き出された `README.md` を読み、選んだアイデアとデモで気づいたことが反映されているか確認します。
必要な修正を済ませたら、手元のGitに保存します。

それでは実際にここまで作業を進めてください。

```text
今開いている myapp リポジトリの README.md だけをコミットしてください。
プッシュはしないでください。
```

GitHubへのプッシュは、後半10で未送信のコミット全体をセキュリティレビューしてから行います。

### `tsumete` が呼ばれない

ここで一度、さっき作った `tsumete` を試してみてください。

それでは実際にここまで作業を進めてください。

```text

```

候補にすら出てこないはずです。ハンズオン①で作った `tsumete` は `vibecoding-0908/.claude/skills/` の中にあり、そのプロジェクトの中だけで有効でした。新しく開いた `myapp` では使えません。

### `myapp` にもコピーする

`myapp` でも使えるようにするには、`myapp` の中にも同じファイルを置きます。中身は1文字も変えません。

それでは実際にここまで作業を進めてください。

```text
vibecoding-0908 の .claude/skills/tsumete/SKILL.md と同じ内容を、
このリポジトリ（myapp）の .claude/skills/tsumete/SKILL.md として保存してください。
フォルダが無ければ作ってください。
```

`myapp` にも `.claude/skills/` 自体を新しく作ったので、前半2と同じ手順でClaude Codeを開き直し、もう一度 `/tsumete` を試してください。

```
vibecoding-0908/.claude/skills/tsumete/SKILL.md   ← vibecoding-0908 の中だけで有効
myapp/.claude/skills/tsumete/SKILL.md             ← myapp の中だけで有効
```

**同じファイルでも、置いたリポジトリの中でしか使えません。** この講座では、エージェントスキルはすべて、使うリポジトリの中（プロジェクトレベル）に置きます。宿題も後半も `myapp` で作業するので、ハンズオン③で作る2つも `myapp` に置きます。後半10で `myapp` と一緒にGitHubへプッシュすれば、PCを替えても取り戻せます。

> どのプロジェクトからでも呼べる置き場所（ユーザーレベル、`~/.claude/skills/`）もあります。今日作ったものを別のプロジェクトでも使いたくなったときの話なので、[後半のクロージング](02-part2.md#継続のために)で扱います。

同じ名前のエージェントスキルが `~/.claude/skills/` にある場合は、ユーザーレベルのものが優先されます。
以前に同名のものを保存した人は、どちらを使うか確認し、今回作るものの名前を変えるなどして混同を避けてください（[公式の優先順位](https://code.claude.com/docs/en/skills#resolve-skills-that-share-a-name)）。

### ハンズオン③に入る前に、残量を見る

それでは実際にここまで作業を進めてください。

```text

```

**5時間ごとの枠が半分を切っている人は、ここで挙手してメンターに声をかけてください。**

ここからハンズオン③に入ります。エージェントスキルに何十往復も質問させる、今日いちばん枠を使う場面です。その先には宿題（自分のアイデアを問い詰めさせる）と、後半が控えています。手を動かしている最中に「枠が足りない」と分かっても、対処する時間がありません。だから③に入る前に見ます。

残りが少ない場合の手当ては3つです。

| 手当て | どうするか | 効き方 |
|---|---|---|
| **推奨設定に戻す** | `/model sonnet`、続けて `/effort medium` と入力する | **まず Sonnet × medium に戻します。** それでも残量が心配なら、`/model` でHaikuへの切り替えを検討します |
| **会話をこまめに切る** | 話題が変わるたびに `/clear` | 長い会話は毎回の消費が積み上がります |
| **プランを上げる** | Max へのアップグレード | 今日1日を通しきりたいなら、ここが判断の分かれ目です |

## 4. ハンズオン③ Grill Me系エージェントスキルを自作する

ハンズオン①で作った `tsumete` は、まだ「一問ずつ聞くだけ」の簡単なものでした。ここからもう少しレベルアップさせます。

<a id="tsumete-を3つの役割に分ける"></a>

### `tsumete` と `ddd` の二つにする

ここから育てるのは、曖昧なアイデアに一問ずつ質問し、作りたいものを明確にする「Grill Me系」のエージェントスキルです。ハンズオン①で作った `tsumete` は、すでに一問ずつ質問する簡易版です。今回は新しい問い詰め用エージェントスキルを増やさず、`tsumete` 自身に記録と書き出しの指示を加えます。

問い詰めて決まった用語や決定をファイルに残す部分だけは、`ddd` に分けます。`tsumete` が一問ずつ問い詰め、必要に応じて `ddd` を呼び、最後に `README.md` と `TASKS.md` にまとめます。

| エージェントスキル | 役割 | 呼び出し方 |
|---|---|---|
| `tsumete` | 一問ずつ問い詰め、`ddd`での記録をはさみ、最後に`README.md`と`TASKS.md`へ書き出す（**①のものを更新する**） | 自分で `/tsumete` と打つ |
| `ddd` | 決まった用語・決定を`CONTEXT.md`・ADRに書き残す（**新規に作る**） | `tsumete`から呼ぶほか、Claudeが必要に応じて呼ぶ |

質問の仕方と、決まったことを記録する手順は別々に直せます。宿題までに残すものも明確です。仕様と実装順は `README.md` と `TASKS.md` に、用語や後戻りしにくい決定は必要な場合だけ `CONTEXT.md` と ADR に残します。

書き出しの雛形は [templates/grill-me-skill-template.md](../templates/grill-me-skill-template.md) にあります。

<a id="②-ddd-を作る-決まったことを書き残す"></a>

### ① `ddd` を作る: 決まったことを書き残す

問い詰めていくと、その場その場で「決まったこと」が生まれます。それを会話の中に置き去りにせず、ファイルに書き残すエージェントスキルです。今回は最小版を作ります。

それでは実際にここまで作業を進めてください。

```markdown
---
name: ddd
description: 決まった用語をCONTEXT.mdに、後戻りしにくい決定をADR（決定記録）として書き残す。用語を確定させたいとき、決定を残したいとき、他のエージェントスキルから書き残しを頼まれたときに使う。
---

# 決まったことを書き残す

会話の中で用語の意味が確定したら、そのつど CONTEXT.md に書き足してください。
あとから変更するのが大変な決定が出たら、docs/adr/ に短い決定記録（ADR）として残してください。
まとめて後回しにせず、決まった瞬間に書くこと。ファイルが無ければ作ってください。
```

`CONTEXT.md` はプロジェクトの用語集、ADR はあとで「なぜこうしたのか」を思い出すための短い決定メモ、と思ってください。`ddd` は更新後の `tsumete` から自動で呼べるようにします。「用語集を整理して」のように直接頼んでも呼ばれます。本格的な書式・使い分けの基準は、答え合わせ用の完成例 [skills/ddd/SKILL.md](../skills/ddd/SKILL.md) にあります（今日はここまで作り込まなくて構いません）。

<a id="①-tsumetsume-を作る-一問ずつ問い詰める"></a>
<a id="③-tsumete-を更新する-2つを組み合わせる入口に育てる"></a>

### ② `tsumete` を更新する: 問い詰めから記録、書き出しまで進める

最後に、ハンズオン①で作り、ハンズオン②で `myapp` にコピーした `tsumete` を更新します。一問ずつ問い詰める動きはそのままに、確定した用語や決定を `ddd` に記録させ、最後に実装資料を書き出す指示を加えます。

それでは実際にここまで作業を進めてください。

```markdown
---
name: tsumete
description: 計画や仕様を実装前に問い詰め、README.mdとTASKS.mdにまとめる。
disable-model-invocation: true
---

# 詰めて

対象は、いま開いているフォルダの README.md です。まず読んでから始めてください。

計画や仕様のあらゆる側面について、共通理解に到達するまで徹底的に質問してください。
質問は一度に一つだけにし、回答を受け取ってから次へ進んでください。
各質問には、あなたが推奨する回答も必ず添えてください。
調べれば分かる事実は質問せず自分で確認し、決定はユーザーに委ねてください。

会話の中で用語の意味が確定したら、`ddd`を使って `CONTEXT.md` に書き足してください。
あとから変更するのが大変な決定が出たら、`ddd`を使って `docs/adr/` に短い決定記録（ADR）として残してください。
まとめて後回しにせず、決まった瞬間に書き残してください。

最後に、次の2つを書き出してください。
- 仕様を README.md に（何を作るか／誰が使うか／どんな体験にしたいか／できること／今回やらないこと〈理由も一行ずつ〉／完成判定）
- 実装する順の「やること」を TASKS.md に。「状態／やること／完了定義」の3列の表にし、
  状態はすべて「未」で始める。1つは15分以内で終わる大きさにし、
  完了定義には画面のどこを見れば終わったと分かるかを書く。
  上から順にやれば、途中で止まっても動くものが残る順番にする
```

#### `disable-model-invocation: true` — 勝手に起動せず、人間が打ったときだけ動く

この行は①からそのまま残し、`tsumete` は人間が `/tsumete` と打ったときだけ動くようにします。問い詰めは何十往復もする長い作業なので、始めるかどうかは人間が決めます。一方、`ddd` にはこの行を入れません。確定した用語や決定が出たとき、Claudeが `tsumete` から自動で呼べるようにします。

**長い作業の開始は人間が決め、作業中に必要な記録はClaudeが判断して呼ぶ。** 呼び方は①から変わらず `/tsumete` です。宿題も後半も、この呼び方でいきます。

> **最後の書き出し指示が、宿題の持ち物を決めます。** これを書かなければ、詰めた結果は会話の中に消えて、残るのは「話した記憶」だけです。書けば、宿題明けに仕様と作業手順が手元にある状態で後半に来られます。入口の `tsumete` に数行足すだけで、出てくる成果物が変わる。これが今日いちばん持ち帰ってほしい感覚です。

### 保存もClaude Codeに頼む

`tsumete` はハンズオン②で `myapp` の `.claude/skills/tsumete/SKILL.md` に置きました。`ddd`を同じ場所に新しく作り、`tsumete`の内容を更新します。自分でフォルダを掘る必要はありません。まとめてClaude Codeに保存させてください（ハンズオン①で覚えた「まとめて1回で頼む」作法です）。

それでは実際にここまで作業を進めてください。

```text
次の2つを、それぞれこのリポジトリ（myapp）の指定した場所に保存してください。
フォルダが無ければ作ってください。tsumeteはすでにあるので、中身を置き換えてください。

.claude/skills/ddd/SKILL.md:
⟨ここに、自分で書いたdddのSKILL.mdを貼る⟩

.claude/skills/tsumete/SKILL.md:
⟨ここに、更新したtsumeteのSKILL.mdを貼る⟩
```

置き場所はすでにあるので、保存した変更はそのまま反映されます。
今回は一度使った `tsumete` の本文も変更したため、`/clear` で旧版の指示が残る会話を切ってから試してください。
候補に出ない場合は `/reload-skills` を実行し、それでも出なければClaude Codeを開き直します。

二つとも `myapp` の `.claude/skills/` に揃えておいてください。宿題も後半も、`myapp` を開いて使います。

<a id="3つのskillを動かしてみる"></a>
<a id="3つのエージェントスキルを動かしてみる"></a>

### 二つのエージェントスキルを動かしてみる

二つ揃ったら、ハンズオン②で書いたREADMEに対して試しに使ってみます。

それでは実際にここまで作業を進めてください。

```text
/tsumete
```

数往復試し、一問ずつ質問が返ってくることを確認してください。
用語や記録すべき決定が確定した場合は、`CONTEXT.md` や `docs/adr/` に残ったかも確認します。確定事項がなければ、まだファイルがなくても構いません。最後に `README.md` と `TASKS.md` が更新されたことも確認します。
思ったとおりに動かなければ、該当する `SKILL.md` を直し、`/clear` で会話を切ってから試します。本格的に問い詰めるのは宿題です。

#### 呼ばれないときは

| 症状 | 原因の大半 | 直し方 |
|---|---|---|
| 「詰めて」と言葉で書いても何も起きない | **これは正常です。** `disable-model-invocation: true` を入れてあるので、`tsumete` は言葉では起動しません | `/tsumete` と打つ（`/` を打つと候補に出ます） |
| `/` を打っても `tsumete` が候補に出てこない | 保存場所がまだ読み込まれていない、またはパスが違う | `/reload-skills`、再起動の順に試す。それでも出なければ、開いているのが `myapp` か、`.claude/skills/tsumete/SKILL.md` に保存したかを確認する。コマンド名はフォルダ名から決まる |
| 用語や記録すべき決定が確定しても、`CONTEXT.md` や ADR に残らない | `ddd` が呼ばれていないか、記録の指示が守られていない | `ddd` を使って記録するよう頼む。本文で参照した名前と保存先の名前も確認する |
| 質問が浅い・すぐ終わる | `tsumete` の本文の指示が足りない | 「一度に一つだけ聞く」「共通理解に到達するまで続ける」など、続ける条件を `tsumete` に書き足す |
| `README.md` や `TASKS.md` が書き出されない | `tsumete` の最後の指示が足りない | 書き出すファイルと、それぞれに含める項目を `tsumete` に書き足す |

### 🚀 拡張ミッション②（早く終わった人向け・任意）

それでは実際にここまで作業を進めてください。

- 〔共通〕**質問の質を上げる**: 一度使ってみて「聞いてほしかったのに聞かれなかったこと」があれば、`description` や本文に書き足して再挑戦する
- 〔Eng〕**`ddd` を育てる**: 答え合わせ用の [skills/ddd/SKILL.md](../skills/ddd/SKILL.md) を見て、複数コンテキスト対応やADRを提案する基準など、自分の版に足りない部分を1つ足してみる

## 5. ハンズオン④ エージェントスキルとHooksで開発工程を拡張する

Grill Meを入口として、開発工程そのものをエージェントスキルやHooksで拡張できるという考え方につなげます。

### エージェントスキルには弱点がある

さっき作ったエージェントスキルには、「呼ばれないときは」で触れた弱点があります。**使うかどうかは、最終的にClaudeが判断します。** `description` の書き方が甘いと、呼ばれないまま素通りされます。

「AIの判断に任せず、条件に合ったら必ず実行してほしい」という場面もあります。そのための仕組みが **Hooks** です。

### Hooksとは

Claude Codeの特定の動作（イベント）をきっかけに、シェルコマンドを自動実行する仕組みです。「ファイルを編集した直後」「セッションを開始したとき」といったタイミングで、あなたが決めた処理を挟み込めます。

| | エージェントスキル | Hooks |
|---|---|---|
| 誰が実行を決めるか | **Claudeが判断する**（descriptionを読んで使うか決める） | **条件が合えば必ず実行される**（判断を挟まない） |
| 中身 | Claudeへの指示文（Markdown） | シェルコマンド |
| 向いていること | 「詰め詰め」のような、状況に応じた振る舞いの指示 | 「編集したら必ずログを残す」のような、確実に動かしたい処理 |

> **Hooksは確認なしに自動実行されます。** さっきの権限プロンプト（「実行してもよいですか?」）を経由しません。登録するコマンドは、自分が中身を理解できるものだけにしてください。

### Hookを動かしてみる

VS Codeで、ハンズオン②で作った `myapp` を開いていることを確認してください。
やることは1つだけです。「ファイルを編集したら、いつ・どのファイルを触ったかを記録に残す」Hookを、Claude Codeに作ってもらいます。

それでは実際にここまで作業を進めてください。

```text
このプロジェクトの .claude/settings.json に、次のHookを設定してください。
- タイミング: ファイルを編集・作成した直後（PostToolUse、対象はEditとWrite）
- 内容: 日時とファイル名を1行、.claude/edit-log.txt に追記する
settings.json や必要なフォルダが無ければ作成してください。
.gitignore に .claude/edit-log.txt を追加し、ログはコミットしないでください。
ログがすでにGitで追跡されている場合は、git rm --cached .claude/edit-log.txt で、
手元のログを残したまま追跡だけ外してください。
```

設定できたら `/clear` で一度会話を切ってください。
Hooksの設定は新しい会話で読み込み直し、登録したイベントが起きたときに実行されるか確認します。
そのうえで、今開いている `myapp` の `README.md` に一行書き足すようClaude Codeに頼んでください。
そのあと `.claude/edit-log.txt` を開いて、**指示していないのに1行増えている**ことを確認してください。
それがHooksです。
今回登録した内容は `/hooks` でも一覧確認できます。
ログは手元だけに残します。Gitの対象にすると、編集のたびにレビュー対象が変わり、後半11の未コミット変更の確認でも止まってしまいます。

> **反映されないときは** `/hooks` で登録内容がちゃんと入っているか確認してください。入っているのに動かないときは、Claude Codeを一度終了して開き直してから再確認してください。

> 後半9では、コミット前に同梱の `/code-review` の起動を促すフックと、セキュリティを確認するエージェントフックを設定します。
> コードレビューの起動記録は、合格や指摘の解消を示すものではありません。後半10で `/security-review` を使い、未送信のコミット全体を確認します。
> 同名のエージェントスキルを自作すると同梱版より優先されるため、`code-review` と `security-review` という名前では作りません。
> テストから実装する `tdd` は、早く終わった人向けの任意課題として使えます。

### 他にどんなエージェントスキルが作れそうか（時間が余ったら）

自分の仕事や作業の中で、「毎回同じことを言っている」工程がないか考えてみてください。

それでは実際にここまで作業を進めてください。

- テストを書かせるときの観点をまとめる
- READMEやドキュメントの書き方を統一する
- コードレビューの観点をまとめる

思いついたものがあれば、時間の許す範囲でエージェントスキルにしてみましょう。完成させられなくても、アイデアをメモしておけば後半・宿題後に育てられます。

## 6. 前半まとめ・宿題の説明

### 前半でやったこと

- バイブコーディングで「頼んだら本当に動いた」を体験した
- 任意課題でMCPを使い、外部サービス（Gmail）とつないだ
- 開発の前提を `CLAUDE.md` に残した
- 自分が作りたいものを対話で選び、デモを触った気づきまでREADMEに残した
- 曖昧なアイデアを問い詰め、決まったことを記録し、実装資料に書き出すエージェントスキルを `tsumete` と `ddd` の二つに育てた
- エージェントスキルとHooksで開発工程を拡張していく考え方に触れた（前者はClaudeの判断を介し、後者は条件が合えば確実に動く）

### 宿題

後半で実装するものを決めてください。多くの場合、ハンズオン②で書いたREADMEがそのまま候補になります。

#### 宿題の前提（これを外すと後半で作れません）

前半3で `CLAUDE.md` に残した条件を、宿題を始める前に再確認します。

| 制約 | なぜ |
|---|---|
| **ブラウザだけで動く構成にする**（HTMLファイル1つが基本） | 後半の実装時間は限られています。サーバーを用意する時間はありません |
| **ログイン・課金・外部サービス連携は今回やらない** | 鍵の管理と動作確認だけで実装時間が終わってしまいます。「今回やらないこと」として仕様に書き残せば、持ち帰って続けられます |
| **後半の実装時間で作りきれる規模まで削る** | 削るのは失敗ではありません。今日の目的は**完成させきる**体験です |

データを残したい場合は、ブラウザに保存する（閉じても消えない）までが今日の範囲です。そう仕様に書けば対応してくれます。

#### どこで作業するか

**ハンズオン②で作った `myapp` のフォルダを、VS Codeで開いて始めてください。** メニューの「ファイル」→「フォルダーを開く…」で、そのフォルダを直接選びます。`README.md` はすでにここにあるはずです。`CONTEXT.md` やADRも、この直下に増えていきます。

<a id="前提を-claudemd-に書いておく"></a>

#### `CLAUDE.md` の前提を再確認する

前半3で作った `myapp/CLAUDE.md` を開き、上の条件とREADME／TASKSの管理先が残っているか確認します。
まだ無ければ、[前半3の作成手順](#開発の前提を-claudemd-に書く)で作ってください。

それでは実際にここまで作業を進めてください。

`/clear` で会話を切ってから `/context` を開き、「Memory files」に `myapp` の `CLAUDE.md` があることを確認してください。
見つからない場合は、Claude Codeを開き直して再確認します。
書き換えた場合は、宿題の最後にほかの変更とまとめてコミットします。
プッシュは後半10のセキュリティレビュー後に行います。

#### `tsumete` で問い詰める

前半3ではアイデアを一つ選び、デモを触って体験を確かめました。ここから、そのREADMEを仕様と設計へ詰めます。

`CLAUDE.md` が読み込まれた状態で、自作した `tsumete` を呼び出し、前半3で書いた `README.md` を出発点に、仕様と設計が後半で実装できるレベルまで具体化されるまで問い詰めさせてください。「詰めて」ではなくスラッシュコマンドです（`disable-model-invocation: true` を入れてあるため）。

それでは実際にここまで作業を進めてください。

```text
/tsumete
```

用語や記録すべき決定が確定すると、`CONTEXT.md` やADRが作られます。提出するのは、このあとのREADMEとTASKSだけで構いません。

#### 「アプリにAIの応答を入れたい」と思ったら

いい反応です。前半でClaude Codeを触った直後にそう思うのは、この講座が狙ったとおりの反応です。ただし後半の実装時間には入りません。理由は鍵（APIキー）です。

APIキーは、持っている人が誰でもあなたのアカウントで課金できてしまう文字列です。ブラウザだけで動くアプリに書けば、そのページを開いた全員から読めます。安全に扱うにはサーバー側が必要で、それを用意して動作確認するだけで実装時間が終わってしまいます。

今日は次のどれかで進めてください。どれを選んでも、持ち帰る「型」は同じです。

| ルート | どうするか | 今日できるか |
|---|---|---|
| **A. ルールベースで作る**（おすすめ） | AIが返しそうな答えを、表とルールで組む。入力→出力の対応を自分で設計する | ✅ できる |
| **B. 手で貼る** | 生成部分だけは、Claude Codeに聞いた結果を自分でコピペして貼り込む | ✅ できる |
| **C. あとで足す** | 「AIで生成する」を `README.md` の「今回やらないこと」に書き、後半12でNotion／Backlogへ引き渡す | ✅ 持ち帰る |

**Aは妥協ではありません。** 「AIに何をさせたいのか」を表とルールに落とす作業は、そのままプロンプトの設計になります。どんな入力に対して、どんな出力が返ってほしいのか。それが書けないうちは、AIに頼んでも同じものは返ってきません。今日Aで作った表は、明日そのままプロンプトに変換できます。

> **持ち帰ってAIを入れるときの道筋も、一応ここに置いておきます。** 鍵をリポジトリに書かず、サーバー側（Cloudflare Workersなど）に預けて、そこ経由で呼ぶ。これが基本形です。今日の後半11で触るCloudflareが、そのまま置き場所になります。
>
> もう1つ、忘れやすいほうを先に言っておきます。鍵を隠しても、その画面を誰でも開ける状態なら、他人があなたのお金でAIを使えます。**鍵を隠すことと、使える人を絞ることは別の作業です**（後半11の🚀拡張ミッション④で扱います）。今日はどちらもやりませんが、「無理」ではなく「今日の時間には入らない」だけだと覚えておいてください。

#### 「実装できるレベル」とは — 宿題の合格ライン

次の4つが満たせたら宿題は完了です。後半7で自己判定します。

- [ ] **曖昧な言葉が残っていない** — 「使いやすく」「いい感じに」など、目で見て確認できない言葉がゼロ
- [ ] **できることが箇条書きで並んでいる** — 3〜5個。それぞれ「自分が操作して目で確認できること」の形
- [ ] **今回やらないことが、理由つきで書いてある** — Grill Meの過程で出た「それは今回は作らない」を、外す理由の一行ごと残す
- [ ] **`TASKS.md` がある** — やることが実装する順に並び、それぞれに**完了定義**（画面のどこを見れば終わったと分かるか）が書いてある

#### 後半に持ってくるもの

自作した `tsumete` で詰めた内容は、次のファイルに残します。
`CONTEXT.md` とADRは、記録する用語や決定が確定した場合だけ作られます。

| ファイル | 誰が書くか | ワークシート |
|---|---|---|
| `README.md` — 仕様 | `tsumete` の最後の指示 | [templates/spec-readme.md](../templates/spec-readme.md) |
| `TASKS.md` — やることの一覧 | 同上 | [templates/tasks.md](../templates/tasks.md) |
| `CONTEXT.md` — 用語集 | `ddd` が詰めながら書く | — |
| `docs/adr/` — 決定記録 | 同上 | — |
| `CLAUDE.md` — このプロジェクトの約束 | 自分（前半3で置く） | [templates/CLAUDE.md.sample](../templates/CLAUDE.md.sample) |

**必須は上の2つです。** `CONTEXT.md` と ADR は、詰めた深さに応じて出たり出なかったりします。ADRが0本でも失敗ではありません（「あとから変えるのが大変な決定」が無ければ書かれないのが正しい動きです）。

出てこなかったら、最後にこう頼んでください。

それでは実際にここまで作業を進めてください。

```text
ここまで詰めた内容を、README.md と TASKS.md に書き出してください。

README.md: 何を作るか／誰が使うか／どんな体験にしたいか／できること（3〜5個・目で確認できる形で）／
           今回やらないこと（1件ずつ、今回のスコープから外す理由も一行で）／完成判定
TASKS.md:  やることを実装する順に、「状態／やること／完了定義」の3列の表にする。
           状態はすべて「未」で始める。1つは15分以内で終わる大きさにし、
           完了定義には画面のどこを見れば終わったと分かるかを書く。
           上から順にやれば途中で止まっても動くものが残る順番にする
```

やることが10個を超えても構いません。多いこと自体は問題ではなく、後半の冒頭で「今日やる分」を決めます。詰めた量は、そのまま持ち帰る資産になります。

曖昧な言葉が残っていたら、エージェントスキルに指摘させて書き直しましょう。

#### 手元のGitに保存する

問い詰めを区切るたびに、変更したファイルをコミットして手元のGitに残します。
コミットはPC内の履歴への保存で、GitHubへ送るプッシュとは別です。
後半10で未送信のコミット全体をセキュリティレビューするまで、プッシュはしません。

それでは実際にここまで作業を進めてください。

```text
今開いている myapp リポジトリで、宿題で増えたり変わったりしたファイル
（README.md、TASKS.md、作られていれば CONTEXT.md と docs/adr/、CLAUDE.md、.claude/、.gitignore）だけをコミットしてください。
.gitignore の対象である .claude/edit-log.txt は含めないでください。
ログの追跡を外した場合は、その削除がステージされていることと、手元にログが残っていることを確認してからコミットしてください。
プッシュはしないでください。
```

ブランチを分ける必要はありません。1人で作っているうちは、`main` にそのまま保存して構いません。コミット後は、Claude Codeにコミットの内容と残っている変更を確認してもらってください。宿題は同じPCの `myapp` に残っています。

次に会うのは後半、ハンズオン⑤です。

### ✅ 宿題提出（後半前日までに）

案内された提出フォームへ、自分のアプリのフォルダにある **`README.md` と `TASKS.md` の2つ**を提出してください。`CONTEXT.md` やADR、`CLAUDE.md` は提出不要です（手元に残しておいてください。後半で効きます）。メンターが後半開始前に目を通し、大きすぎる・曖昧さが残っているものには当日冒頭で個別に声をかけます。

宿題期間中に、アイデアの壁打ちや技術的な詰まりの相談の場が用意されることがあります。日時と参加方法は運営からの案内を確認し、1人で詰まったら遠慮なく使ってください。
