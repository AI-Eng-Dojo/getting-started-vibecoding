## 1. オープニング

### バイブコーディングとは

コードを書く代わりに、**「こうしたい」を言葉で伝え、動くものを見て、また言葉で直す**開発のやり方です。設計書も仕様書も、最初は書きません。今日の前半でやることは3つだけです。

1. 作りたいものを伝える
2. 動いたものを**見て確認する**
3. 感じた間違い・違和感を指摘する

「コードが読めないのに大丈夫？」— 大丈夫です。判断はすべて**画面確認**して決めます。コードを読んで判断する場面はありません。

### 今日の予定

冒頭の「やること」をひととおり説明します。**今日は「自分のアイデアをソフトウェアとして実装する土台づくり」**です。**この前半さえ乗り切れば後半はひたすらやるだけ**状態にできます。

### Claude Codeはどう動いているのか？

- Claude Codeはコーディングに特化したエージェントハーネスです。
- エージェンティックループし続けながら、人間と対話を繰り返し、都度指示にあった応答・ツール利用を繰り返すことで、人間との協業を実現します。

#### モデル
頭脳にあたる部分です。**文章を受け取って、次に来る文章を返すことだけができます。** 今日の `/model` で選ぶのは、この部分です。

Claude Codeが既定で使うのは、Anthropicが提供する**Claudeシリーズ**です。用途別に4系統あります。

| 系統 | 位置づけ |
|---|---|
| **Fable** | 最も高性能。難しい設計や長時間の自律作業向け |
| **Opus** | 高性能。複雑な実装や込み入ったデバッグ向け |
| **Sonnet** | 標準。日常の開発はこれで十分 |
| **Haiku** | 軽量・高速。単純な作業や大量の繰り返し向け |

賢いほど応答は遅く、利用枠の消費も増えがちです。**上から順に良いわけではなく、作業内容やトークン消費を考慮して選んでください。**

#### ツール
モデル自体にドキュメントやソースコードを編集する能力はありません。Claude Codeというハーネスには、モデルが応答した「人間の指示内容からすると、このツールを使ってこういうことをすればよい」という内容に応じて、実際にBashなどのコマンドツールを動かしてファイルを編集することで、チャットでやりとりする以上に、実世界に作用することができます。

### 基本的なスラッシュコマンド

Claude Codeの入力欄で `/` から始まる**スラッシュコマンド**を打つと、設定の確認や変更ができます。手を動かし始める前に、6つだけ実際に確認しておきます。

#### ① `/help` — 何が使えるかを一覧する

```text
/help
```

Claude Codeに**インストールされているコマンドの一覧**が出ます。**このあと出てくるコマンドを忘れても、ここから探せます。**

並ぶのは組み込みのものだけではありません。**あとから入れたエージェントスキルや、自分で書いたカスタムコマンドも、カスタムコマンドの一覧に表示されます。** ハンズオン③で自作するGrill系スキルも、保存して会話を切り直せば `/tsumete` のようにここへ並びます。

> 入力欄で `/` を1文字打つだけでも、同じ候補が絞り込み付きで出ます。名前をうろ覚えのときはこちらが速いです。

#### ② `/status` — いまの状態を確認する

```text
/status
```

バージョン・**いま使っているモデル**・ログイン中のアカウント・接続中のMCPサーバーなどがまとめて表示されます。

#### ③ `/model` — 使うモデルを選ぶ

```text
/model
```

一覧が出るので矢印キーで選んでEnter。

> **この画面では左右キーでeffort（考える深さ）も一緒に切り替えられます。** 上下キーでモデルを選び、左右キーでそのモデルのeffortを変え、Enterで確定します。

- **これからやる前半は、SonnetやHaikuで十分です。** 応答が速い＝バイブコーディングが気持ちよく捗ります。利用枠の消費も少なくて済みます。
- 宿題でアイデアを詰めるときや、難しいバグに詰まったときは、賢いモデルに切り替える価値があります。(Advisory Modeという設定もありますが時間があれば説明します)

#### コンテキスト

モデル自体は1問1答できるだけで、以前やりとりした内容を覚えておく機能はありません。そのため、Claudeには人間とClaudeがやりとりしているセッション中の、チャット内容、編集対象のファイル内容、コマンドの出力結果などを記憶しておき、毎回のやりとりに以前のやりとりを付加して毎回モデルに送信しています。それらのセッションごとの記憶をしておく領域をコンテキストウィンドウと呼びます。これにより、毎回さも前回のやりとりをモデルが覚えているかのようにやりとりができるのです。

**モデルごとに最大のコンテキストウィンドウが決まっており、Anthropicが提供するデフォルトではFable/Opus/Sonnetは1M(M=100万)、Haikuは200K(K=1,000)です。**


#### ④ `/effort` — 考える深さを選ぶ（任意）

```text
/effort
```

`low` / `medium` / `high` / `xhigh` / `max` から選びます。同じモデルでも、**答える前にどれだけ考えるか(推論の深さ)** が変わります。前半は `medium` で十分です。

ちなみに③の `/model` 画面でも左右キーで設定できますが、このコマンドを使うとeffortだけを直接指定できます。

この思考の深さの違い自体に価格の違いはありません。ただしより深い思考は、その分より多くトークン消費する傾向が高いことにくわえ、応答速度が遅くなる傾向があります。

#### ⑤ `/usage` — 利用枠の残量を確認する

```text
/usage
```
**5時間ごとの枠**と**週ごとの枠**、それぞれの残量が表示されます。

今日はこのあとハンズオンや宿題で数時間はClaude Codeを使い続けます。途中で不安になったら、いつでもこのコマンドで確認してください。**足りなくなった場合、プランのアップグレードをする必要があることに注意してください**

#### ⑥ `/permissions` — 許可の仕組みを見る

```text
/permissions
```

Claude Codeは、ファイルを書き換えたりコマンドを実行したりする**ツールを使うたび**に、「実行してもよいですか?」と確認を挟みます。これが安全装置の本体です。一度許可した内容はルールとしてここに溜まっていき、あとから一覧で確認・取り消しができます。

#### 権限

この「毎回確認する/しない」の挙動を切り替えるのが **Permission mode** です。4つあります。

| モード | 挙動 |
|---|---|
| **Manual Mode（手動）** | ツールを使うたびに確認する |
| **Accept Edits ON（自動・編集のみ）** | ファイル編集は自動で承認し、コマンド実行など編集以外は確認する |
| **Auto Mode（自動・リスク判定）** | AIがツール実行のリスクを自動判定し、低リスクと判断したものは確認なしで進める。破壊的な操作や踏み込んだ操作は通常どおり確認・拒否される。**今日はこのモードで進めます** |
| **Plan Mode（プランモード）** | 何も変更せず、**まず計画だけ**を提示する。確認して進めるかを判断してから実行に移る |

切り替えは `/config` の Permission mode、または入力欄の **Shift+Tab** から。押すたびにモードが切り替わります。**今日はAuto Modeで進めます。まだAuto Modeになっていない人は、ここで切り替えてください。** 低リスクな操作の確認をAIが肩代わりしてくれる分、テンポよく進められます。**ただし、破壊的な操作や踏み込んだ操作は、Auto Modeでも変わらず確認が挟まります。** そこだけは今までどおり自分の目で読んでから答えてください。

### やること

新しいリポジトリ **`vibecoding-0908`** をその場で作り、Claude Codeで開いて、簡単なものを1つ、バイブコーディングで作ります。ここではあえて**仕様を厳密にしすぎません**。「こういうものが欲しい」を思いつくまま伝え、出てきたものを見て、直したいところを指示する——このリズムを体で覚えるのが目的です。

1. **VS Codeで、Claude Code(拡張)を起動する** — 今どこを開いていても問題ありません
2. **`vibecoding-0908` という名前で新しいリポジトリを作る** — 今日使うリポジトリは、ホームフォルダの下の `github` フォルダ（`~/github/`。Windowsでは `C:\Users\⟨自分の名前⟩\github\`）にまとめて作ります。無ければClaude Codeが自動で作ります。**普段使っているリポジトリの置き場所がすでにある人は、無理に合わせず、そちらに作って構いません。**

   **`gh` コマンドが使える場合（事前準備4参照）**

   Claude Codeのパネルに次を貼り付けて送信します。

   ```text
   ~/github フォルダ（無ければ作成）に移動して、
   次のコマンドでリポジトリの作成とcloneをしてください。

   gh repo create vibecoding-0908 --public --clone --add-readme
   ```

   `gh repo create` が、GitHub上へのリポジトリ作成と手元へのcloneを1回でやってくれます。`--public` を `--private` にすれば非公開になります（今日の範囲ではどちらでも構いません）。

   `gh` コマンドの認証は事前準備4で済んでいるので、ログインを求められることはないはずです。**求められた場合、またはエラーが出た場合は**、事前準備の「つまずき早見表」の `gh repo create` の行を参照するか、そのままエラーをClaude Codeに貼って「直してください」と頼んでください。

   **`gh` コマンドが使えない場合（事前準備4でうまくいかなかった人）**

   ブラウザでGitHubを開き、右上の「+」→「New repository」から `vibecoding-0908` という名前でリポジトリを作成してください（Public/Privateどちらでも構いません）。**このとき「Add a README file」にチェックを入れてください。** 作成できたら表示されるURLをコピーし、Claude Codeに次のように貼り付けます。

   ```text
   ~/github フォルダ（無ければ作成）の中に、次のリポジトリをcloneしてください。
   ⟨コピーしたURLを貼り付ける⟩
   ```

   どちらの方法でも、**このリポジトリは今日のこのハンズオンだけで使う、使い捨てです。**
3. **できたフォルダをVS Codeで開き直す** — 「ファイル」→「フォルダーを開く…」で、`~/github/vibecoding-0908`（Windowsでは `C:\Users\⟨自分の名前⟩\github\vibecoding-0908`）を選びます。**ここが重要です。** 手順2の直後は、Claude Codeはまだ最初に開いていたフォルダを見ている状態のままです。ここで開き直すことで、以降の作業がこのリポジトリの中で行われるようになります

   **VS Code左側のファイル一覧に `README.md` が1枚だけ表示されていれば正しい状態です。**（`--add-readme` によって自動で置かれたものです）
4. 下の「お題の例」から1つ選ぶか、自分で思いついたものをそのまま指示する
5. **できあがったものをブラウザで開いて動かす** — VS Code左側のファイル一覧でHTMLファイルを右クリックし、「Finderで表示」（Windowsは「エクスプローラーで表示」）→ 出てきたファイルをダブルクリック
6. 気になったところ（見た目・動き・言葉づかいなど）を**2〜3個まとめて1回**で伝えて直させる

> **どこで詰まっても、まずClaude Codeに聞いてください。** 「作ったファイルをブラウザで開く方法を教えて」でも答えてくれます。**手順が分からないこと自体もAIに聞く**ことに慣れましょう。

### お題の例

迷ったら、そのままコピペしてください。自分のやりたいことがあれば、それを優先して構いません。

```text
ブラウザで遊べるテトリスを、1つのHTMLファイルで作ってください。
矢印キーの左右で移動、上キーで回転、下キーで落下を速められ、

```

もう少し手順のある題材で試したい場合は、[starters/](../starters/) にある3種のお題（ポモドーロタイマー・診断チャート・習慣トラッカー）も使えます。使い方は [starters/README.md](../starters/README.md) を参照してください。

### 「許可しますか?」と聞かれたら

Claude Codeは手動モードの場合、ファイルの作成・変更やコマンドの実行の直前で必ず一度止まり、こういう確認を挟みます。

```text
Bash command

  mkdir -p tetris
  作業用のフォルダを作成します

Do you want to proceed?
❯ 1. Yes
  2. Yes, and don't ask again for mkdir commands in /Users/you/handson
  3. No, and tell Claude what to do differently (esc)
```

今日使う**Auto Modeでは、この確認をAI自身が肩代わりします。** リスクが低いと判定した操作（自分のフォルダの中でファイルを作る・編集するなど）は、確認なしでそのまま進みます。だから体感としては「毎回聞かれる」ではなく「**ほとんど聞かれない**」になります。

**それでも、破壊的な操作や踏み込んだ操作のときは、Auto Modeでも変わらずこの確認が出ます。** 見える回数が減った分、**出てきたときこそ普段よりよく読んでください。** 「これは自分の判断だけでは進めない方がいい」とAIが判断したサインです。

> **見た目は環境で少し変わります。** ターミナルでは上のような番号付きのリストで出て、矢印キー＋Enter（または数字キー）で選びます。VS Code拡張ではボタンとして出ることがあります。**並んでいる選択肢の中身は同じ**なので、下の表で読み替えてください。

| 選択肢 | 意味 | 今日どう使うか |
|---|---|---|
| **1. Yes** | 今回だけ許可する | 迷ったらこれ |
| **2. Yes, and don't ask again for ...** | **同じ種類の操作を、以後は聞かずに実行してよい**と記憶させる。このルールはAuto Modeの判定より優先されます | 同じ確認が何度も出て煩わしくなったらこれ。記憶される範囲は、その行に表示されているフォルダの中だけ |
| **3. No, and tell Claude ...** | 断って、代わりにどうしてほしいかを伝える。選ぶと入力欄に戻るので、そこに希望を書きます | やろうとしていることが違うと思ったとき。Escキーでも同じ |

見出しは操作の種類で変わります。`Bash command` ＝コマンド実行、`Create file` ＝ファイル作成、`Edit file` ＝ファイル変更。ファイルを作る・変えるときは、2番が `Yes, for this session`（このセッションの間は聞かない）になります。

**今日の範囲では、表示された内容が「今いるフォルダの中のファイル操作」なら 1 か 2 を選んで構いません。**

> **確認が出ないからといって、何もしていないわけではありません。** Auto Modeは確認を省略しているだけで、ファイルは実際に作られたり変わったりしています。**都度、画面を見て確認する**——これは今日やることの1番目と同じ姿勢です。何を許可したかは、あとで `/permissions` から確認・取り消しができます。

```text
3点直してください。

2. 次に来るブロックが分かるように、プレビューを表示して

```

### 詰まったら: リカバリー3手

高確率でどこかで「動かなくなった」「思わぬ方向に壊れた」が起きます。そのときの手順です。

| いつ使う | 打ち手 | どうやる |
|---|---|---|
| 画面が真っ白・エラーが出た | **① エラーをそのまま貼る** | エラーメッセージや画面のスクショを**説明せずそのまま**貼り、「動かなくなりました。原因を調べてください」 |
| 直る気配がない・どんどん悪化する | **② ひとつ戻す** | 「さっきの変更を取り消して、直前の動いていた状態に戻してください」 |
| 欲張った指示のせいで空中分解した | **③ 小さく指示しなおす** | 一度に複数頼んだり、複雑で壮大な指示をしていたら「まず1個だけ」に分割してからやり直す |

それでもうまくいかないときは、次を試してください。

- **賢いモデルに切り替える** — `/model` で賢いモデルに切り替え、同じことをもう一度頼む。軽いモデルで的外れな応答が続くときはこれでうまくいくことがあります

### MCPでGmailとつなげてみる（20分）

ここまではファイルの中だけで完結する作業でした。Claude Codeは、**MCP（Model Context Protocol）**という仕組みを使うと、Gmail・カレンダー・社内ツールのような**外部のサービスとも直接やりとりできます。** MCPで何につなぐかは人によって全く違うので、今日は**ほぼ全員が持っているGmail**を共通のお題にします。

つなぐ作業はClaude Codeの外、**claude.aiの画面**で行います。

1. ブラウザで [claude.ai](https://claude.ai) を開く
2. 左側メニューの「**カスタマイズ**」→「**コネクタ**」を開く（`claude.ai/customize/connectors`）
3. 一覧から **Gmail** を探し、「**接続/連携させる**」を押す
4. Googleアカウントでログインし、表示された許可画面で内容を確認して許可する

![claude.aiのカスタマイズ＞コネクタ画面。Figma・freee・GitHub・Gmailなどが接続済みで並んでいる](images/claude-connectors-gmail.png)

> **この接続はネイティブ統合といって厳密にはMCPとは少し違う仕組みですが、今は気にしなくてよいです。一度設定すると claude.ai の設定に保存され、チャット/Cowork/Claude Codeいずれからも使えます。** 外し方は [後半のクロージング](02-part2.md#今日つないだものの外し方)にあります。

### 動かしてみる

接続できたら、**Claude Codeを一度終了して、開き直してください。** `/clear` だけでは足りません。**SkillやHooksは新しい会話から読み込まれますが、MCPの接続はClaude Codeの起動時に確立される**という違いがあります。claude.ai側で接続したタイミングでClaude Codeがすでに起動していた場合、会話を切るだけでは気づけません。

開き直したら、一度 `/mcp` を開いて、**Gmailが接続済み（Connected）になっているか確認してください。**

>      claude.ai
>      claude.ai Gmail · ✔ connected · 29 tools

次に以下のように下書き作成を頼んでみましょう。

```text
自分宛てに、件名「Claude Codeワークショップ」、
本文に今日ここまでやった作業を書いた下書きメールを作成してください。
```

初めてGmailを操作するときは、**いつもの「実行してもよいですか?」という確認**が出るはずです。外部サービスへの初めてのアクセスは、Auto Modeでも踏み込んだ操作として扱われやすいためです。今日の範囲（下書きを1通作るだけ）なら許可して構いません。実行できたら、実際にGmailの「下書き」フォルダを開いて、**指示した内容が本当に反映されているか**を自分の目で確認してください。

### 最初のエージェントスキルを作ってみる（`tsumete`・20分）

3本柱の最後、**エージェントスキル**です。「毎回同じことを言う」代わりに、**やり方そのものをファイルに保存**しておくと、以後は一言でその作法を呼び出せます。

今日この後、宿題まで繰り返し使う `tsumete` という名前のSkillを、まず簡単な形で作ってみます。**呼び出しは `/tsumete` です。今日はこのあと何度もこのSkillに戻ってくるので、名前を覚えておいてください。**

```text
.claude/skills/tsumete/SKILL.md というファイルを作ってください。
中身は次のとおりです。

---
name: tsumete
description: 計画や仕様を実装前に問い詰めて明確にする。
disable-model-invocation: true
---

# 詰めて

この計画について、一問ずつ質問して詳しく聞いてください。
それぞれの質問には、あなたのおすすめの答えも添えてください。
```

**まずはこのプロジェクト(`vibecoding-0908`)の中に置きます。** `.claude/skills/` というのが、そのプロジェクトの中だけで使えるSkillの置き場所です。

保存できたら `/clear` で会話を切ってください。**Skillは新しい会話から読み込まれます。** そのうえで、次のように呼んでみてください。

```text
/tsumete
```

`/` を打つと候補に出てきます。一問ずつ質問が返ってくれば成功です。**これがエージェントスキルの正体です。** 何かを頼むたびに長い説明を書く代わりに、一度ファイルに書いておけば、以後は `/tsumete` の一言で同じ振る舞いを呼び出せます。

> **`disable-model-invocation: true` という行を入れました。** これは**「Claudeが自分の判断で勝手に起動してはいけない。人間が `/tsumete` と打ったときだけ動く」**という指定です。問い詰めは何十往復もする長い作業なので、**始めるかどうかは人間が決めます。** この行の意味は、ハンズオン③でもう一度扱います。

> この `tsumete` は、ハンズオン②・③でさらに育てていきます。完成ではありません。

### 設定を開いて中を見る

ひととおり動かしたところで、**さっきの許可がどう溜まっているか**と、**重要な設定項目**を見ておきます。

#### ① `/permissions` — 許可したことの一覧

```text
/permissions
```

さっき「2番」を選ぶたびに、ここへルールが1行ずつ追加されています。**自分が何を許可したのかをあとから一覧で確認でき、取り消しもできます**。身に覚えのないものがあれば、ここで消しておいてください。

#### ② `/config` — 設定を開く

```text
/config
```

設定パネルが開きます。矢印キーで項目を移動し、中身を眺めてみてください。

| 項目 | 何が変わるか |
|---|---|
| **Model** | オープニングで選んだモデル。ここからでも変えられます |
| **Permission mode** | 許可の求め方。**今日はAuto Modeになっているはずです** |
| **Theme** | 画面の配色。目が疲れる人はここで変える |
| **Editor mode** | 入力欄のキー操作（Vimキーバインドなど） |
| **Notifications** | 生成が終わったときの通知 |
| **Auto-update channel** | 本体の更新の受け取り方 |

> **Permission modeはオープニングで設定したAuto Modeのままにしてください。** 確認を省略するモードは、**省略していいのは「間違えても被害が小さい操作」だけ**が原則です。今日は自分のフォルダの中で1ファイルのアプリを作るだけなので、Auto Modeで不便はありません。仕事のリポジトリで使うときは、ここの設計から入ってください。

#### ③ `/context` — 会話がどれだけ溜まったか見る

```text
/context
```

いまの会話がどれだけの量になっているかが表示されます。会話は長く続けるほど毎回の消費が増えます。**話題が変わるときに会話を切る**のが、利用枠のいちばん確実な節約です。

#### ④ `/clear` — 会話を切って次へ

```text
/clear
```

いまの会話を終えて、まっさらな状態から始めます。**次のハンズオン②はまったく別の話題（自分のアイデアの壁打ち）です。ここで一度 `/clear` してから進んでください。**

> **消えるのは会話だけで、作ったファイルは消えません。** さっき作ったアプリはフォルダにそのまま残ります。安心して/clearしてください。

### 🚀 拡張ミッション①（早く終わった人向け）

- 〔共通〕**もう1個作る**: まったく別のお題で、同じリズム（頼む → 見る → まとめて直す）をもう一周してみましょう。2回目はきっと1回目より速く・正確になります。

## 3. ハンズオン② 自分が作りたいアプリを考える（30分）

ここからが前半の本題です。**さっきまでは「なんでもいいからノリで動かす」体験をしました。次は「何を作りたいのか」を自分の中からしっかり引き出す番です。**

**まず、自分のアプリ用のリポジトリを作ります。** `vibecoding-0908`（使い捨て）とは別の、新しいリポジトリです。

1. **`vibecoding-0908` はここではいったん開いたままでも大丈夫です。**
2. **`myapp` という名前で新しいリポジトリを作る** — ハンズオン①と同じ場所（`~/github/`。普段の置き場所がある人はそちらで構いません）にまとめます

   **`gh` コマンドが使える場合**

   ```text
   ~/github フォルダに移動して、
   次のコマンドでリポジトリの作成とcloneをしてください。

   gh repo create myapp --private --clone --add-readme
   ```

   ハンズオン①と1箇所だけ違います。**`--private` です。**

   > **非公開の理由** あなただけのアプリのアイデアがこのリポジトリに入ります。`README.md` だけでなく、`CONTEXT.md`（用語集）や `docs/adr/`（決定記録）など**重要な文書**たちが保存されます。
   > **あとから公開するのは1クリックなので、** 迷ったら非公開にしておきましょう。

   **`gh` コマンドが使えない場合**

   ブラウザのGitHubで `myapp` という名前のリポジトリを作成します。**Visibility は Private を選び、「Add a README file」にチェックを入れてから**作成してください。表示されたURLをコピーして、Claude Codeに次のように貼り付けます。

   ```text
   ~/github フォルダ（無ければ作成）の中に、次のリポジトリをcloneしてください。
   ⟨コピーしたURLを貼り付け⟩
   ```

3. **できた `myapp` フォルダをVS Codeで開き直す** — 「ファイル」→「フォルダーを開く…」で、`~/github/myapp`（Windowsでは `C:\Users\⟨自分の名前⟩\github\myapp`）を選びます。これで、以降の作業がこのリポジトリの中で行われるようになります。**VS Code左側のファイル一覧に `README.md` が1枚だけ表示されていれば正しい状態です。**

```
~/github/myapp/   ← ここが自分のアプリの家。今日から最後までここ
└── README.md               ← いま中身を書く（ファイル自体はもうある）
```

**このリポジトリを覚えておいてください。宿題も後半も、ここを開いて始めます。**

### 壁打ちのやり方

Claude Codeとの**チャットのやりとり**で、自分の考えを整理します。いきなり実装させず、まずなにを作るか計画を明確にすることに集中してください。

**手元にあるアイデアを、まず一度そのまま出してしまいましょう。** 荒くて構いません。

```text
作りたいものがあります。まだ粗いので、質問しながら一緒に固めましょう。

⟨作りたいものを、思いつくまま2〜3行で。箇条書きでも構いません⟩

いきなり実装はしないでください。
まず私の考えを引き出す質問を、一度に一つずつしてください。
質問には、あなたのおすすめの答えも添えてください。必要ならリサーチもお願いします。
```

Claudeからの質問に答えながら、次の4点が言葉にできるところまで進めます。

1. **何を作りたいのか**
2. **誰が使うのか**
3. **何ができればいいのか**
4. **どんな体験にしたいのか**

**壁打ちしてて「思ったより穴がある」と感じるかもしれませんが、正常です。** 頭の中では固まっているつもりでも、問答してみると隙間が見えます。その隙間を埋めるのがこの30分です。

> **アイデアが浮かばない人へ。** 無理にひねり出さなくて構いません。次のように切り出せば、Claude側から質問を始めてくれます。**そのままメンターにも声をかけてください。**
>
> ```text
> 作りたいものがまだ決まっていません。
> 最近困っていること・面倒だと感じていること・繰り返している手作業はないか、
> というところから質問して、一緒に見つけてください。
> ```

### READMEに書き出す

4点が言葉になったら、`README.md` として書き出します。書き込み用のワークシートは [templates/idea-readme.md](../templates/idea-readme.md) にあります。

```text
ここまで話した内容を、README.mdとしてまとめてください。
- 何を作りたいか（一言で）
- 誰が使うか
- 何ができればいいか（3〜5個程度）
- どんな体験にしたいか
```

これが、**頭の中のアイデア → AIとの対話 → 明文化されたIntent**というプロセスの最初の成果物です。宿題ではこのREADMEを、自作するGrill Me Skillでさらに深く問い詰めて仕様に育てます。

### `tsumete` が呼ばれない

ここで一度、さっき作った `tsumete` を試してみてください。

```text
/tsumete
```

**候補にすら出てこないはずです。** ハンズオン①で作った `tsumete` は `vibecoding-0908/.claude/skills/` の中にあり、**そのプロジェクトの中だけで有効**でした。新しく開いた `myapp` では使えません。

### ユーザーレベルに置き直す

`myapp` でも使えるようにするには、**置き場所を変えます。** 中身は1文字も変えません。

```text
vibecoding-0908 の .claude/skills/tsumete/SKILL.md と同じ内容を、
~/.claude/skills/tsumete/SKILL.md として保存してください。
フォルダが無ければ作ってください。
```

保存できたら `/clear` で会話を切り、もう一度 `/tsumete` を試してください。**今度は候補に出ます。**

```
<プロジェクト>/.claude/skills/tsumete/SKILL.md   ← そのリポジトリの中だけで有効
~/.claude/skills/tsumete/SKILL.md                ← どのプロジェクトでも有効
```

**同じファイルが、置き場所だけで「使える／使えない」が変わりました。** ハンズオン③で作る2つも、宿題でも後半でも使うので、最初からユーザーレベルに置きます。

### 休憩に入る前に、残量を見る

```text
/usage
```

**5時間ごとの枠が半分を切っている人は、休憩中に挙手してください。**

ここから休憩を挟んでハンズオン③に入ります。**Skillに何十往復も質問させる、今日いちばん枠を使う場面です。** その先には宿題（自分のアイデアを問い詰めさせる）と、後半2時間55分が控えています。

残りが少ない場合の手当ては3つです。

| 手当て | どうするか | 効き方 |
|---|---|---|
| **軽いモデルに落とす** | `/model` で Haiku か Sonnet を選ぶ | ハンズオン③④は軽いモデルで十分こなせます。**まずこれ** |
| **会話をこまめに切る** | 話題が変わるたびに `/clear` | 長い会話は毎回の消費が積み上がります |
| **プランを上げる** | Max へのアップグレード | 今日1日を通しきりたいなら、ここが判断の分かれ目です |

> **手を動かしている最中に「枠が足りない」と分かっても、対処する時間がありません。** だから休憩の前に見ます。**ここで分かれば、休憩中に手当てできます。**



## 4. ハンズオン③ Grill Me系エージェントスキルを自作する（35分）

ハンズオン①で作った `tsumete` は、まだ「一問ずつ聞くだけ」の簡単なものでした。ここから**もう少しレベルアップさせます**。

### Skillとは何か（おさらい）

**タスクのやりかたそのものをファイルに保存し、Claudeが必要なときに自分で読み込む**仕組みです。プロンプトを毎回書くのではなく、「いつ・何をするか」を1つのファイルにまとめておくと、以後は一言でその作法を呼び出せます。ここまでは①で体験済みです。

### `tsumete` を2つの役割に分ける

ここから作るのは、**ユーザーの曖昧なアイデアに対してAIが徹底的に質問し、作りたいものを明確化する**仕組みです。ジャンルとして「Grill Me系」と呼びます。①の `tsumete` は1つのファイルに全部書いた簡易版でしたが、**育てる過程で役割ごとに3つの小さなSkillへ分け、入口が組み合わせて使う**という形にします。

**なぜ2つに分けるのか。** ①の `tsumete` は質問を返すだけで、**答えた内容はその会話の中に消えていました。** 画面を閉じたら終わりです。ここで足す `ddd` が、その差を埋めます。**問い詰めながら、決まった用語を `CONTEXT.md` に、後戻りしにくい決定を ADR に、その場で書き残す。** 壁打ちで終わるか、明日も読める資産が残るかの分かれ目がここです。

宿題ではこの差がそのまま効いてきます。**1日以上あけて後半に来たとき、手元に残っているのは「話した記憶」ではなく `README.md` と `TASKS.md`** ——それを作るのが、これから足す2つです。

| Skill | 役割 | 呼び出し方 |
|---|---|---|
| `tsumetsume` | 一問ずつ問い詰める（グリルの本体・**新規に作る**） | Claudeが自分で判断して呼ぶ |
| `ddd` | 決まった用語・決定を`CONTEXT.md`・ADRに書き残す（**新規に作る**） | Claudeが自分で判断して呼ぶ |
| `tsumete` | 上の2つを組み合わせて実行する入口（**①のものを更新する**） | **自分で `/tsumete` と打つ** |

**小さな役割に分けて、入口(Skill)が他のSkillを呼び出しながら組み合わせる**——これもSkill設計の基本形です。名前は自分で決めて構いません。書き出しの雛形は [templates/grill-me-skill-template.md](../templates/grill-me-skill-template.md) にあります。

### ① `tsumetsume` を作る: 一問ずつ問い詰める

まずグリルの本体です。以下は一つの完成例です。

```markdown
---
name: tsumetsume
description: 計画や仕様を実装前に徹底的に問い詰めて磨き上げる。実装前に計画を揺さぶりたいとき、「詰め詰め」と頼まれたとき、他のSkillが問い詰めを行うときに使う。
---

# 詰め詰め

この計画のあらゆる側面について、共通理解に到達するまで徹底的にインタビューしてください。
質問は一度に一つだけにし、回答を受け取ってから次へ進んでください。
各質問には、あなたが推奨する回答も必ず添えてください。
調べれば分かる**事実**は質問せず自分で確認し、**決定**はユーザーに委ねてください。
```

冒頭の `description` は、Claudeが「今このSkillを使うべきか」を判断する材料です。**いつ使うかが書かれていないSkillは、置いてあっても呼ばれません。** ここには、自分が実際に打ちそうな言葉をそのまま入れておきます。

自分の言葉で、このSkillを書いてみてください。「何を聞くか」「どんな順番で聞くか」「どこまで厳しく詰めるか」は自由です。

> **答え合わせ用の完成例が [skills/tsumetsume/SKILL.md](../skills/tsumetsume/SKILL.md) にあります。** ただし**まずは見ないで書いてください。** 自分の言葉で書いたものでないと、宿題で自分が欲しい質問をしてくれません。詰まったとき、または書き終えてから開いてください。

### ② `ddd` を作る: 決まったことを書き残す

問い詰めていくと、その場その場で「決まったこと」が生まれます。それを会話の中に置き去りにせず、ファイルに書き残すSkillです。今回は最小版を作ります。

```markdown
---
name: ddd
description: 決まった用語をCONTEXT.mdに、後戻りしにくい決定をADR（決定記録）として書き残す。用語を確定させたいとき、決定を残したいとき、他のSkillが書き残しを必要とするときに使う。
---

# 決まったことを書き残す

会話の中で用語の意味が確定したら、そのつど CONTEXT.md に書き足してください。
あとから変更するのが大変な決定が出たら、docs/adr/ に短い決定記録（ADR）として残してください。
まとめて後回しにせず、決まった瞬間に書くこと。ファイルが無ければ作ってください。
```

`CONTEXT.md`＝プロジェクトの用語集、`ADR`＝あとで「なぜこうしたのか」を思い出すための短い決定メモ、と思ってください。**このSkillは `tsumete` から使われますが、「用語集を整理して」のように直接頼んでも呼ばれます。** 本格的な書式・使い分けの基準は、答え合わせ用の完成例 [skills/ddd/SKILL.md](../skills/ddd/SKILL.md) にあります（今日はここまで作り込まなくて構いません）。

### ③ `tsumete` を更新する: 2つを組み合わせる入口に育てる

最後に、①で作った `tsumete` を、上の2つを束ねる入口に育てます。**中身は「呼ぶだけ」まで削ります。**

```markdown
---
name: tsumete
description: 計画や設計を実装前に問い詰め、決まったことを記録に残す。
disable-model-invocation: true
---

# 詰めて

`tsumetsume` のセッションを、`ddd` を併用しながら実行してください。
確定した用語や決定は、質問を続けながらその場で書き残していきます。

最後に、次の2つを書き出してください。
- 仕様を README.md に（何を作るか／誰が使うか／できること／今回やらないこと／完成判定）
- 実装する順の「やること」を TASKS.md に。1つは15分以内で終わる大きさにし、
  それぞれ「画面のどこを見れば終わったと分かるか」を書く。
  上から順にやれば、途中で止まっても動くものが残る順番にする
```

`tsumetsume` ・`ddd` という名前の部分は、**自分がつけたSkill名に合わせて書き換えてください。**

#### `disable-model-invocation: true` — 入口だけは人間が呼ぶ

`disable-model-invocation: true` は①からそのまま残します。**「Claudeが自分の判断で勝手に起動してはいけない。人間が `/tsumete` と打ったときだけ動く」**という指定でした。

いま3つに分けたことで、この行の意味がはっきりします。**中身は `tsumetsume` と `ddd` に移りました。** 中身を持つ側は、Claudeが状況を見て自分で呼べたほうが便利です。だから今回作る2つには、この行を**入れません**。一方で入口は、**話の流れでうっかり全体が走り出すと困ります。** 問い詰めは何十往復もする長い作業だからです。

**中身のあるSkillは自動で呼ばれてよい。入口は人間が明示的に呼ぶ専用にする。**——これがSkillを組み合わせるときの定番の形です。呼び方は①から変わらず **`/tsumete`** です。宿題も後半も、この呼び方でいきます。

> **最後の3行が、宿題の持ち物を決めます。** これを書かなければ、詰めた結果は会話の中に消えて、残るのは「話した記憶」だけです。書けば、宿題明けに**仕様と作業手順が手元にある**状態で後半に来られます。**入口のSkillに数行足すだけで、出てくる成果物が変わる**——これが今日いちばん持ち帰ってほしい感覚です。

### 保存もClaude Codeに頼む

`tsumete` はハンズオン②で `~/.claude/skills/tsumete/SKILL.md`（ユーザーレベル）に置きました。**`tsumetsume`・`ddd` も同じ場所に揃えます。** 自分でフォルダを掘る必要はありません。まとめて、Claude Codeに保存させてください（ハンズオン①で覚えた「まとめて1回で頼む」作法です）。

### 動かしてみる

3つ揃ったSkillを、ハンズオン②で書いたREADMEに対して試しに使ってみます。**呼び方は①から変わらずスラッシュコマンドです。**

```text

```

Claudeが一問ずつ質問を返してくるはずです。数往復だけ試して、質問の合間に `CONTEXT.md` や `docs/adr/` が実際に作られている（更新されている）か確認してください（本格的にやり込むのは宿題です）。**思った通りに動かなければ、該当する `SKILL.md` の中身を直して再挑戦して構いません。** Skillもコードと同じで、直しながら育てるものです。

#### 呼ばれないときは

| 症状 | 原因の大半 | 直し方 |

| **「詰めて」と言葉で書いても何も起きない** | **これは正常です。** `disable-model-invocation: true` を入れてあるので、`tsumete` は言葉では起動しません | `/tsumete` と打つ（`/` を打つと候補に出ます） |

## 5. ハンズオン④ SkillとHooksで開発工程を拡張する（20分）

Grill Meを入口として、**開発工程そのものをSkillやHooksで拡張できる**という考え方につなげます。

### Skillには弱点がある

さっき作ったSkillには、ハンズオン③の「呼ばれないときは」で触れた弱点があります。**Skillを使うかどうかは、最終的にClaudeが判断します。** `description` の書き方が甘いと、呼ばれないまま素通りされます。

「AIの判断に任せず、条件に合ったら必ず実行してほしい」という場面もあります。そのための仕組みが**Hooks**です。

### Hooksとは

**Claude Codeの特定の動作（イベント）をきっかけに、シェルコマンドを自動実行する仕組み**です。「ファイルを編集した直後」「セッションを開始したとき」といったタイミングで、あなたが決めた処理を挟み込めます。

| | Skill | Hooks |
|---|---|---|
| 誰が実行を決めるか | **Claudeが判断する**（descriptionを読んで使うか決める） | **条件が合えば必ず実行される**（判断を挟まない） |
| 中身 | Claudeへの指示文（Markdown） | シェルコマンド |
| 向いていること | 「詰め詰め」のような、状況に応じた振る舞いの指示 | 「編集したら必ずログを残す」のような、確実に動かしたい処理 |

> **Hooksは確認なしに自動実行されます。** さっきの権限プロンプト（「実行してもよいですか?」）を経由しません。登録するコマンドは、自分が中身を理解できるものだけにしてください。

### 動かしてみる

やることは1つだけです。**「ファイルを編集したら、いつ・どのファイルを触ったかを記録に残す」Hookを、Claude Codeに作ってもらいます。**

```text
このプロジェクトの .claude/settings.json に、次のHookを設定してください。
- タイミング: ファイルを編集・作成した直後（PostToolUse、対象はEditとWrite）
- 内容: 日時とファイル名を1行、.claude/edit-log.txt に追記する
settings.json や必要なフォルダが無ければ作成してください。
```

設定できたら `/clear` で一度会話を切ってください。**Hookも、さっきのSkillと同じく新しい会話から確実に読み込まれます。** そのうえで何かファイルを1つ編集させてください（ハンズオン①のアプリの色を変える、など何でも構いません）。そのあと `.claude/edit-log.txt` を開いて、**指示していないのに1行増えている**ことを確認してください。それがHooksです。今回登録した内容は `/hooks` でも一覧確認できます。

> **反映されないときは** `/hooks` で登録内容がちゃんと入っているか確認してください。入っているのに動かないときは、Claude Codeを一度終了して開き直してから再確認してください。

> **開発工程はほかにもSkillとして切り出せます。** 後半では、実装の進め方そのものをスキルにした `tdd`、仕様と作法を別々に見る `code-review`、危ないところを点検する `security-review` の3枚を使います（自分で書かず、用意されたものをコピーして使います）。さらにHooksと組み合わせて、**セキュリティレビューを「AIの判断任せ」から「必ず実行される」に変える**のが後半10の狙いです。

### 他にどんなSkillが作れそうか（時間が余ったら）

自分の仕事や作業の中で、「毎回同じことを言っている」工程がないか考えてみてください。

- テストを書かせるときの観点をまとめたSkill
- READMEやドキュメントの書き方を統一するSkill
- コードレビューの観点をまとめたSkill

思いついたものがあれば、時間の許す範囲でSkillにしてみましょう。完成させられなくても、アイデアをメモしておけば後半・宿題後に育てられます。

## 6. 前半まとめ・宿題の説明（5分）

### 前半でやったこと

- バイブコーディングで「頼んだら本当に動いた」を体験した
- MCPで外部サービス（Gmail）とつないだ
- 自分が作りたいものを、対話を通じて言葉にした（README）

- SkillとHooksで開発工程を拡張していく考え方に触れた（Skillは判断を介する、Hooksは条件が合えば確実に動く）

### 宿題

**後半で実装するもの**を決めてください。多くの場合、ハンズオン②で書いたREADMEがそのまま候補になります。

#### どこで作業するか

**ハンズオン②で作った `myapp` のフォルダを、VS Codeで開いて始めてください。**

- メニューの「ファイル」→「フォルダーを開く…」で、**そのフォルダを直接**選びます（`~/github/myapp`。普段の置き場所を使った人はそちらです）
- `README.md` はすでにここにあるはずです。`CONTEXT.md` やADRも、この直下に増えていきます

開いたら、自作した `tsumete` を呼び出し、**自分のアイデアが後半で実装できるレベルまで具体化されるまで**問い詰めさせてください。**「詰めて」ではなくスラッシュコマンドです**（`disable-model-invocation: true` を入れてあるため）。

```text
/tsumete
```

問い詰めながら、このフォルダの中に `CONTEXT.md` やADRが増えていきます。**これは想定どおりです。** 提出するのはこのあとの2ファイルだけで構いません。

#### 宿題の前提（これを外すと後半で作れません）

**この3つは、Grill Meを始める前にSkillへ伝えておいてください。**

| 制約 | なぜ |
|---|---|
| **ブラウザだけで動く構成にする**（HTMLファイル1つが基本） | 後半の実装時間は70分です。サーバーを用意する時間はありません |
| **ログイン・課金・外部サービス連携は今回やらない** | 鍵の管理と動作確認だけで70分が終わります。「今回やらないこと」として仕様に書き残せば、持ち帰って続けられます |
| **後半の実装70分で作りきれる規模まで削る** | 削るのは失敗ではありません。今日の目的は**完成させきる**体験です |

データを残したい場合は、**ブラウザに保存する（閉じても消えない）**までが今日の範囲です。そう仕様に書けば対応してくれます。

#### 「自分のアプリにもAIを入れたい」と思ったら

**いい反応です。** 前半でClaude Codeを触った直後にそう思うのは、この講座が狙ったとおりの反応です。
ただし**今日の70分の中には入りません。** 理由は鍵（APIキー）です。

APIキーは、**持っている人が誰でもあなたのアカウントで課金できてしまう文字列**です。
ブラウザだけで動くアプリに書けば、**そのページを開いた全員から読めます**（後半10のセキュリティレビューが必ず指摘します）。
安全に扱うにはサーバー側が必要で、それを用意して動作確認するだけで70分が終わります。

今日は次のどれかで進めてください。**どれを選んでも、持ち帰る「型」は同じです。**

| ルート | どうするか | 今日できるか |
|---|---|---|
| **A. 決定論版を作る**（おすすめ） | AIが返しそうな答えを、**表とルール**で組む。入力→出力の対応を自分で設計する | ✅ できる |
| **B. 手で貼る** | 生成部分だけは、Claude Codeに聞いた結果を**自分でコピペして貼り込む** | ✅ できる |
| **C. あとで足す** | 「AIで生成する」を `TASKS.md` の**今回やらないこと**に書き、後半12でNotion／Backlogへ引き渡す | ✅ 持ち帰る |

**Aは妥協ではありません。** 「AIに何をさせたいのか」を表とルールに落とす作業は、**そのままプロンプトの設計になります。**
どんな入力に対して、どんな出力が返ってほしいのか——**それが書けないうちは、AIに頼んでも同じものは返ってきません。**
今日Aで作った表は、明日そのままプロンプトに変換できます。

> **持ち帰ってAIを入れるときの道筋も、一応ここに置いておきます。** 鍵をリポジトリに書かず、**サーバー側（Cloudflare Workersなど）に預けて、そこ経由で呼ぶ**——これが基本形です。今日の後半11で触るCloudflareが、そのまま置き場所になります。
> **もう1つ、忘れやすいほうを先に言っておきます。** 鍵を隠しても、**その画面を誰でも開ける状態なら、他人があなたのお金でAIを使えます。** 鍵を隠すことと、使える人を絞ることは別の作業です（後半11の🚀拡張ミッション④で扱います）。
> **今日はどちらもやりません**が、「無理」ではなく「今日の時間には入らない」だけだと覚えておいてください。

> **「外部サービス連携なし」と、後半11のデプロイは矛盾しません。** 後半では作ったものをCloudflareに公開しますが、**変わるのは置き場所だけで、アプリ自体は静的なまま**です。ログインもサーバーへのデータ送信も増えません。

#### 「実装できるレベル」とは — 宿題の合格ライン

次の3つが満たせたら宿題は完了です。後半7で自己判定します。

- [ ] **曖昧な言葉が残っていない** — 「使いやすく」「いい感じに」など、**目で見て確認できない言葉**がゼロ
- [ ] **できることが箇条書きで並んでいる** — 3〜5個。それぞれ「自分が操作して目で確認できること」の形
- [ ] **今回やらないことが書いてある** — Grill Meの過程で出た「それは今日はやらない」を、捨てずに残す
- [ ] **`TASKS.md` がある** — やることが実装する順に並び、それぞれに「画面のどこを見れば終わったと分かるか」が書いてある

#### 後半に持ってくるもの

自作した `tsumete` を一周させると、**自分のアプリのフォルダの中に、次の4つが自然に残ります。**

| ファイル | 誰が書くか | ワークシート |
|---|---|---|
| `README.md` — 仕様 | `tsumete` の最後の指示 | [templates/spec-readme.md](../templates/spec-readme.md) |
| `TASKS.md` — やることの一覧 | 同上 | [templates/tasks.md](../templates/tasks.md) |
| `CONTEXT.md` — 用語集 | `ddd` が詰めながら書く | — |
| `docs/adr/` — 決定記録 | 同上 | — |

**必須は上の2つです。** `CONTEXT.md` と ADR は、詰めた深さに応じて出たり出なかったりします。**ADRが0本でも失敗ではありません**（「あとから変えるのが大変な決定」が無ければ書かれないのが正しい動きです）。

出てこなかったら、最後にこう頼んでください。

```text
ここまで詰めた内容を、README.md と TASKS.md に書き出してください。

README.md: 何を作るか／誰が使うか／できること（3〜5個・目で確認できる形で）／
           今回やらないこと／完成判定
TASKS.md:  やることを実装する順に一覧化。1つは15分以内で終わる大きさにし、
           それぞれ「画面のどこを見れば終わったと分かるか」を書く。
           上から順にやれば途中で止まっても動くものが残る順番にする
```

**やることが10個を超えても構いません。** 多いこと自体は問題ではなく、後半の冒頭で「今日やる分」に線を引きます。**詰めた量は、そのまま持ち帰る資産になります。**

曖昧な言葉が残っていたら、Skillに指摘させて書き直しましょう。次に会うのは後半、ハンズオン⑤です。
