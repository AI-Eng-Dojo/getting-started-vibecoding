# 前編（2時間）AIに「型」を渡して、狙ったものを作る

前編のゴール: **バイブコーディングの速さを体験したうえで、それを「狙ったものになる」やり方に載せ替えること。** 具体的には、スキル・計画・詰めの3つを自分の手で1周します。

> 開始前の儀式: Claude Codeで `/status` と入力し、利用枠の残量を確認してください。
> 全員が満タン近くで始められているか、ここで揃えます。（打ち方は事前準備0.3で練習済みです）

---

## 1. オープニング（10分）

### バイブコーディングとは

コードを書く代わりに、**「こうしたい」を言葉で伝え、動くものを見て、また言葉で直す**開発のやり方です。設計書も仕様書も書きません。速い。びっくりするほど速い。

これは今日の最初の15分で体験します。

### ただし、速いことと「狙ったものになる」ことは別です

バイブコーディングだけで進めると、こうなります。

> ノリで機能を足す → だんだん指示が雑になる → どこかが壊れる → 直させると別の場所が壊れる → 何が「正解の状態」だったか自分でも分からなくなる → 終了

原因は能力でも運でもありません。**AIに渡している情報が毎回その場限り**だからです。今日はそこを3つの手で埋めます。

### 今日の3原則

| 原則 | 意味 | 今日どこで使うか |
|---|---|---|
| **① 型で渡す** | 毎回言っていることは、その場で言わずに**スキル**にしてAIに持たせる | ハンズオン②で「詰めて」と「セキュリティレビュー」の2つを作る |
| **② 作る前に計画を見る** | いきなり実装させない。**計画を出させ、読んでから許可する** | ハンズオン③で中級課題を計画から作る |
| **③ 曖昧なまま作らせない** | 決めていないことは決めてから作る。**決定は自分がする** | ハンズオン④で自分のアプリを詰める |

この3つは、そのまま「AI駆動開発」と呼ばれているやり方の最小形です（→ [★コラム0](columns.md)）。今日はその最小形を、4時間で一周します。

## 2. ハンズオン① まずはポン出し（15分）

理屈の前に、速さを体験します。

### やること

1. デスクトップに空のフォルダ `vibe-tetris` を作り、Claude Codeで開く
2. 次の指示をそのまま貼り付ける

```text
ブラウザで遊べるテトリスを、1つのHTMLファイルで作ってください。
キーボードで操作でき、そろった行が消えて、スコアが表示されるようにしてください。
ゲームオーバーになったら、もう一度遊べるようにしてください。
```

3. できあがったHTMLファイルをブラウザで開いて遊ぶ

### ✅ チェックポイント1

テトリスがブラウザで遊べていること。**細かい不満があってもそのまま次へ。**

### いま起きたことを一言で

指示は3行でした。仕様書も設計書もありません。それでも動くものが出ました。**これがバイブコーディングです。**

そして同時に、こうも思ったはずです。「**次に何か作るときも、また同じ説明を最初からするのか?**」——そこがハンズオン②の入口です。

### 🚀 拡張ミッション①（早く終わった人向け・任意）

- 〔共通〕**1回だけ欲張ってみる**: 「次のブロックの予告表示と、レベルが上がると落下が速くなる仕組みを足して」と1回で頼む。まとめて頼むと何が起きるかを見ておく
- 〔Eng〕**履歴を持つ**: `git init` してここまでを最初のコミットにする。以降 `git diff` でClaudeの変更を追える

## 3. ハンズオン② エージェントスキルを作る（40分）

**今日いちばん持ち帰る価値があるパートです。** ここで**2つ**作ります。

### スキルとは

毎回言っていることを、**ファイルにしてAIに持たせる**仕組みです。置いておくだけで、Claudeが「今これを使う場面だ」と自分で判断して読みに行きます。

形はこれだけです。

```
.claude/skills/⟨スキル名⟩/
└── SKILL.md
```

`SKILL.md` の先頭には**フロントマター**を置きます。

```markdown
---
name: tsumete
description: Interrogate a plan or design until both sides genuinely agree... Use when the user says "詰めて", ...
---

# 詰めて

（ここに、AIにやってほしいことを普通の文章で書く）
```

| 項目 | 役割 | コツ |
|---|---|---|
| `name` | スキルの識別子 | 小文字とハイフンだけ。**フォルダ名と一致させる** |
| `description` | **いつ使うか**の判定に使われる | 「何をするか」だけでなく「**どういうときに使うか**」を必ず書く |
| 本文 | AIへの指示そのもの | 箇条書きより、普通の文章で「こうしてほしい」と書くほうが効く |

> **description がスキル作りの9割です。** Claudeはここを読んで起動を決めます。
> 「計画をレビューする」だけでは起動しません。「ユーザーが**『詰めて』と言ったとき**に使う」まで書いて初めて起動します。

### ステップ1: 1つ目 —「詰めて」スキル（25分）

実装に入る前に、AIに計画を一問ずつ問い詰めさせるスキルです。今日の午後、あなた自身がこれに助けられます。

1. ハンズオン①のフォルダ（または新しいフォルダ）をClaude Codeで開く
2. 次の指示を貼り付けて、**Claudeにスキルを書かせる**

```text
Claude Code のエージェントスキルを作ってください。置き場所は .claude/skills/tsumete/SKILL.md です。

このスキルにやってほしいことは:
- 私が「詰めて」と言ったら起動する
- 実装に入る前に、計画について質問を一度に一つだけ投げる
- 各質問には、あなたのおすすめの回答も添える
- コードを見れば分かることは質問せず、自分で確認する。ただし「決めること」は必ず私に聞く
- 私が「合意した」と言うまで実装を始めない

フロントマターには name と description を書いてください。
description は英語の文で、「いつ使うか」（私が「詰めて」と言ったとき）が分かるように書いてください。
```

3. できた `SKILL.md` を**自分の目で読む**。読めない用語はその場でClaudeに聞く
4. 動作確認: Claude Codeに「**この計画を詰めて**」と言ってみて、質問が一つずつ返ってくればスキルが効いています

> まとめて3つ質問が返ってきたら、スキルが読まれていないか、本文の指示が弱いかのどちらかです。
> 「質問は一度に一つだけ」をもっと強く書いて、もう一度試してください。**スキルを直すのもバイブコーディングです。**

### ステップ2: 2つ目 —「セキュリティレビュー」スキル（10分）

ここからが本番です。**1つ目で25分かかったものが、2つ目は数分で作れます。** 型が身についたかどうかは、そこで分かります。

作るのは、**コードの危ないところを見つけて報告させる**スキルです。今日作っているのは自分のPCの中で動く小さなアプリですが、この先あなたが作るものは、いずれ人に渡ります。**渡す前に一度かけるものを、いま持っておきます。**

同じ手順で、指示だけ変えます。

```text
もう1つエージェントスキルを作ってください。置き場所は .claude/skills/security-review/SKILL.md です。

このスキルにやってほしいことは:
- 私が「セキュリティレビュー」と言ったら起動する
- このプロジェクトのコードを読んで、危ないところを重大度（高・中・低）をつけて報告する
- 必ず見る観点は: 秘密情報（APIキー・パスワード）の直書き / ユーザーが入力した文字をそのまま画面に埋め込んでいないか / 文字列をそのまま実行していないか / ブラウザに保存しているデータの中身 / 外部への通信 / 他人に渡して困る情報が残っていないか
- 各指摘には「どこ」「何が起きるか」「どう直すか」を書く
- 勝手に直さない。まず報告だけして、私が承認してから直す
- 問題が見つからなかった観点についても、何を確認してそう判断したのかを書く

フロントマターには name と description を書いてください。
description は英語の文で、「いつ使うか」（私が「セキュリティレビュー」と言ったとき）が分かるように書いてください。
```

**動作確認**: ハンズオン①のテトリスに向けて「**セキュリティレビューして**」と言ってみてください。重大度つきの報告が返り、**勝手にコードが書き換わっていなければ**成功です。

> **「勝手に直さない」がこのスキルの肝です。** 何を直すかを決めるのはあなたです（原則③）。
> 報告せずに直し始めたら、本文の「まず報告だけ」をもっと強く書いてやり直してください。

> テトリスは自分のPCの中だけで動くので、おそらく重大な指摘は出ません。**それでいいです。**
> ここで確かめたいのは「危ないアプリを見つけること」ではなく、**2つ目のスキルが数分で作れて、ちゃんと起動すること**です。

### ✅ チェックポイント2

- `.claude/skills/tsumete/SKILL.md` があり、「詰めて」と言うと**質問が一つだけ**返ってくる
- `.claude/skills/security-review/SKILL.md` があり、「セキュリティレビューして」と言うと**重大度つきの報告**が返り、**コードは書き換わっていない**

### 答え合わせ（5分）

完成形をこのリポジトリの [skills/](../skills/) に置いてあります。自分のものと見比べてください。**違っていて構いません。**見るべきは「description に『いつ使うか』が書けているか」の一点です。

「詰めて」の完成形は3つに分かれています。入口の `tsumete` が、進め方の `tsumetsume` と、書き残し方の `ddd` を呼びます。**スキルは別のスキルを呼べます。**大きな型を1枚に詰め込まず、役割で分けるのが育てやすい形です。一方「セキュリティレビュー」は1枚で完結しています。**役割が1つなら1枚でいい**——この使い分けが分かれば十分です。

### 🚀 拡張ミッション②（早く終わった人向け・任意）

- 〔共通〕**書き残させる**: 完成形の `tsumete` を読み、「決まったことを `CONTEXT.md` と `docs/adr/` に書き残す」指示を自分のスキルにも足す。詰めた結果が会話の中に消えなくなる
- 〔共通〕**自分の癖をスキルにする**: 「配色は落ち着いたトーン」「説明は短く」など、自分が毎回言っていることを3つ目のスキルにする
- 〔共通〕**レビューを厳しくする**: `security-review` に「重大度を実態より高く盛らない」「見ていない観点を問題なしに含めない」を足す。**甘い報告より、範囲が正直な報告のほうが役に立ちます**
- 〔Eng〕**3枚に割る**: 自分の「詰めて」を入口・進め方・書式の3つに分割し、入口から相対リンクで呼ぶ形に組み替える

## 4. ハンズオン③ 中級課題を「計画から」作る（40分）

ハンズオン①は3行の指示でした。今度は**課題仕様が与えられた状態から、計画を立てて作ります。**

### やること

1. [starters/](../starters/) から中級課題を1つ選ぶ（迷ったらA）
2. 選んだフォルダをClaude Codeで開く
3. **まず計画だけ出させます。** 次の指示を貼り付ける

```text
このフォルダの README.md を読んで、実行計画を立ててください。
どの順番で何を作るか、それぞれの完了条件は何かが分かるように書いてください。
計画を私が読んで許可するまで、実装は始めないでください。
```

4. **出てきた計画を自分の目で読む。** 読むポイントは3つだけです
   - 順番は「動くものが先」になっているか（いきなり全機能ではないか）
   - 各ステップに「何ができたら完了か」が書いてあるか
   - README に書いていないことを勝手に足していないか
5. 直したいところがあれば言う（例:「3番目は今日はやらなくていい」「1番目をもっと小さく割って」）
6. 納得したら「**この計画で実装してください。1番目が動いたら一度止めてください**」と伝える
7. 1つ動くたびに自分の目で確認し、次へ進ませる
8. **できあがったら「セキュリティレビューして」と1回言う。** ハンズオン②で作った2つ目のスキルを、ここで初めて実戦投入します

> ステップ8で出てくる報告は、たいてい「低」が数件です。**それが正常です。**
> 見るべきは指摘の数ではなく、**報告の最後に「何を確認したか」が書いてあるか**。
> そこが書けているスキルだけが、この先あなたの役に立ちます。書けていなければスキル本文に足してください。

### 中級課題

| 課題 | フォルダ | こんな人に |
|---|---|---|
| A: ポモドーロタイマー | [starters/a-pomodoro-timer/](../starters/a-pomodoro-timer/) | 迷ったらこれ |
| B: 診断チャート | [starters/b-shindan-chart/](../starters/b-shindan-chart/) | コンテンツを作るのが好き |
| C: 習慣トラッカー | [starters/c-habit-tracker/](../starters/c-habit-tracker/) | データが残るアプリを作りたい |

### ✅ チェックポイント3

- 課題READMEの「できあがりの条件」のうち、**2つ以上**が自分の目で確認できている
- **セキュリティレビューを1回かけた**（指摘が0件でも可。かけたことが大事）

### なぜ計画を先に読ませたのか

ハンズオン①では、出てきたものを見て初めて「思ってたのと違う」が分かりました。計画を先に読むと、**作る前に「思ってたのと違う」が分かります。** 直すコストが桁で違います。

これが原則②「作る前に計画を見る」です。

### 🚀 拡張ミッション③（早く終わった人向け・任意）

- 〔共通〕**残りの条件を仕上げる**: 課題READMEの条件を全部満たしきる
- 〔共通〕**計画に詰めてを効かせる**: 計画が出た直後に「**詰めて**」と言い、ハンズオン②で作ったスキルを計画レビューに使う
- 〔Eng〕**チケットに割る**: 計画を `docs/tickets/` 配下の個別ファイルに起票させ、一覧を `docs/tickets/README.md` に作らせる。実装は1チケットずつ

## 5. ハンズオン④ 自分のアプリを「詰める」（10分）

後編で作るのは**あなた自身のアイデア**です。前編の最後は、その仕様と設計を始めるところまで進めます。

### やること

1. 新しい空フォルダを作り、Claude Codeで開く
2. ハンズオン②で作った `tsumete` スキルをこのフォルダにコピーする

```bash
mkdir -p .claude/skills
cp -r ⟨ハンズオン②のフォルダ⟩/.claude/skills/tsumete .claude/skills/
```

3. 作りたいものを、**分かっている範囲で**伝える。完璧でなくて構いません（下書き用紙: [templates/goal-sheet.md](../templates/goal-sheet.md)）

```text
⟨作りたいものを2〜3行で⟩

これから作ります。詰めてください。
```

4. あとは**質問に答えるだけ**です。一問ずつ来ます。答えに迷ったら、Claudeが添えてくる「おすすめの回答」を採用して構いません

### ここで起きること

- 自分でも決めていなかったことに気づきます（「その2つは同じもの? 別もの?」）
- 決めたことがファイルに残り始めます（用語集・決定の記録・やることリスト）
- **後編は、ここで残ったものを入力にして実装から始められます**

### ✅ チェックポイント4（提出）

「詰めて」の質問に**3問以上答えた**状態。この時点のやりとりのスクリーンショット（または決まったことのメモ）を提出してください。メンターが休憩中に全員分に目を通し、危ないもの（大きすぎる・確認できない）には休憩明けに一声かけます。

### 🚀 拡張ミッション④（早く終わった人向け・任意）

- 〔共通〕**書き残しまで進める**: 「ここまで決まったことを `CONTEXT.md` と `docs/adr/` に書いて」と頼み、リポジトリの中に残す
- 〔Eng〕**完成条件をチケットにする**: 詰めた結果を実装チケットに割り、後編は1チケットずつ消化する形で始める
