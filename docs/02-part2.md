## 7. 宿題ふりかえり

まず、宿題で使った `myapp` のフォルダをVS Codeで開いてください。メニューの「ファイル」→「フォルダーを開く…」から選びます（`~/github/myapp`。普段の置き場所を使っている人はそちら）。

```
~/github/myapp/   ← これを開く
├── CLAUDE.md      前半3で置いた開発の約束
├── README.md      宿題で詰めた仕様
├── TASKS.md       宿題で作ったやることリスト
├── CONTEXT.md     用語集（あれば）
├── docs/adr/      決定記録（あれば）
└── .claude/       自作したエージェントスキル3つ（skills/）と、前半5のHook（settings.json）
```

次に `/usage` で利用枠の残量を、`/status` でいま選んでいるモデルを確認します。

**後半も、このワークショップの推奨は Sonnet × medium です。**
`/model sonnet`、続けて `/effort medium` と入力して、設定を揃えてください。
難しいバグに詰まったときは一時的にモデルを切り替え、解決したらこの設定に戻します。

**残量が半分を切っている人は、推奨設定に戻したうえで、必要に応じてHaikuへの切り替えやプランのアップグレードを検討してください。**

そのうえで、宿題がどこまでできているかを、前半6の合格ライン4つで確認してください。

| 手元にあるもの | このあとどうするか |
|---|---|
| `README.md` から曖昧な言葉が消えていて、`TASKS.md` もある | このまま8へ |
| `README.md` は詰め終わっているが、`TASKS.md` が無い | `TASKS.md` を作る（下のプロンプト） |
| `README.md` に曖昧な言葉が残っている、または宿題に着手できなかった | 下の「詰めきれていない人向け」の見本を丸ごと使う |

どの場合も、`myapp` に `CLAUDE.md`（前半3で置いた開発の約束）が無ければ、[前半3の手順](01-part1.md#開発の前提を-claudemd-に書く)で置いてから9へ進んでください。後半9の実装と後半10のレビューは、この約束が読まれている前提で進みます。

`TASKS.md` がまだ無い人は、以下のようにして作成してください。

```text
README.md を読んで、実装する順に「やること」の一覧を TASKS.md に書き出してください。
1つは15分以内で終わる大きさにし、それぞれに完了定義（画面のどこを見れば終わったと分かるか）を書いてください。
上から順にやれば、途中で止まっても動くものが残る順番にしてください。
```

### 詰めきれていない人向け

`README.md` に「使いやすく」のような曖昧な言葉が残っている人と、宿題に着手できなかった人は、題材「習慣トラッカー」を `tsumete` で詰め切った状態の見本を、`myapp` に丸ごと写して進めます。中身は、宿題で持ってくるものと同じ5つです。

```
starters/c-habit-tracker/homework/   ← 教材リポジトリの中
├── CLAUDE.md      このプロジェクトの約束（前半3で置いたものと同じ6行）
├── README.md      詰め終わった仕様
├── TASKS.md       実装する順のやることと完了定義
├── CONTEXT.md     用語集（ddd が書き残したもの）
└── docs/adr/      決定記録（2本）
```

自分で書いたものは消さずに、先に `myidea/` フォルダへ退避します。今日は使わなくても、持ち帰って再開できます。写し方は3通りあり、どれでも結果は同じです。

**Claude Codeに頼む（本線）**

```text
いまこのフォルダにある CLAUDE.md・README.md・TASKS.md・CONTEXT.md・docs/ を、
消さずに myidea/ フォルダへ移動してください（無いものは飛ばしてください）。
myidea/ フォルダがすでにあるときは退避済みなので、この移動は飛ばし、
myidea/ の中は一切上書きしないでください。

そのあと、次のコマンドで教材の見本をこのフォルダの直下に展開してください。
Windows では curl.exe で main.zip を保存してから tar -xf で展開する形に読み替えてください。

curl -fsSL https://github.com/AI-Eng-Dojo/getting-started-vibecoding/archive/refs/heads/main.tar.gz | tar -xz --strip-components=4 getting-started-vibecoding-main/starters/c-habit-tracker/homework

展開できたら、CLAUDE.md・README.md・TASKS.md・CONTEXT.md・docs/adr/ が
このフォルダの直下に揃っていることを確認して、一覧を見せてください。
```

**手で写す**

1. ブラウザで [教材リポジトリ](https://github.com/AI-Eng-Dojo/getting-started-vibecoding) を開き、緑の「Code」ボタンから「Download ZIP」を選ぶ
2. 解凍してできたフォルダの中の `starters/c-habit-tracker/homework/` を開く
3. `myapp` にある `CLAUDE.md`・`README.md`・`TASKS.md`・`CONTEXT.md`・`docs/` を、`myapp/myidea/` の中へ移す（無いものは飛ばす。`myidea/` がすでにあるなら退避済みなので、この手順ごと飛ばす）
4. `homework/` の中身5つを、`myapp` の直下へコピーする

**ターミナルで直接やる〔エンジニア向け〕**

VS Codeのターミナルで、`myapp` の直下にいることを確認してから実行します。

macOS / Linux:

```text
test ! -e myidea && mkdir myidea && mv CLAUDE.md README.md TASKS.md CONTEXT.md docs myidea/ 2>/dev/null; curl -fsSL https://github.com/AI-Eng-Dojo/getting-started-vibecoding/archive/refs/heads/main.tar.gz | tar -xz --strip-components=4 getting-started-vibecoding-main/starters/c-habit-tracker/homework
```

Windows（PowerShell）:

```text
if (-not (Test-Path myidea)) { New-Item -ItemType Directory myidea | Out-Null; Move-Item CLAUDE.md, README.md, TASKS.md, CONTEXT.md, docs myidea -ErrorAction SilentlyContinue }; curl.exe -fsSL -o main.zip https://github.com/AI-Eng-Dojo/getting-started-vibecoding/archive/refs/heads/main.zip; tar -xf main.zip --strip-components=4 getting-started-vibecoding-main/starters/c-habit-tracker/homework; Remove-Item main.zip
```

どちらも、`myidea/` がすでにあれば退避を飛ばして展開だけをやり直します。2回実行しても、退避したものは上書きされません。

どの方法でも、終わったらVS Code左側のファイル一覧に5つが並び、`myidea/` の中に自分の書いたものが残っていることを確認してください。見本でも、8のMVP選定から14まで同じ手順で進められます。`CONTEXT.md` と `docs/adr/` は、実装中に用語や決定を確かめるときに参照します。仕様どおりに動くかは、完了定義と完成判定に沿って自分で操作して確かめます。

## 8. ハンズオン⑤ MVPを決める

宿題で詰めた人ほど、`TASKS.md` のタスクが多くなっているはずです。減らす必要はありません。ここで今日やる分を決めましょう。可能な限り、アプリとして価値の高い最低限の実装（MVP）に収めます。

<a id="ステップ1-粒度を揃える5分"></a>

### ステップ1: 粒度を揃える

まず、大きすぎるタスクがあれば分割します。

```text
TASKS.md を読んで、次を指摘してください。
- 15分では終わらなさそうな大きさのタスク
- 完了定義（画面のどこを見れば終わったと分かるか）が書かれていないタスク

指摘だけしてください。まだ直さないでください。
```

指摘を確認し、納得したものだけ反映させます。

```text
1と3を反映してください。2は今日は対象外にします。
```

<a id="ステップ2-mvpに絞り込む10分"></a>

### ステップ2: MVPに絞り込む

今日実装するのは、アプリとして価値がいちばん高い部分だけです。それが動けば「このアプリは何をするものか」が画面で伝わる。その最小の組み合わせがMVPです。

```text
TASKS.md のやることを、「MVP」（今日やる分）と「持ち帰る分」の見出しに分けてください。

MVPの条件は次の2つです。
- それだけで「このアプリが何をするものか」が画面で伝わること
- 入力・処理・表示がつながって、動くものが1本通ること

MVPに入らないものは TASKS.md の「持ち帰る分」という見出しにまとめてください。
完了定義は消さずに残したまま、今日やらない理由を一行ずつ書き足してください。

「今回やらないこと」（詰めるときに今回のスコープから外すと決めたもの）は、
別の見出しのままにしてください。README.md にしか書かれていない場合は、
TASKS.md にも同じ見出しで写してください。理由が書いてあれば、それも一緒に写してください。
```

タスク1つは15分以内。後半の実装時間に入りきらないなら、MVPでない可能性があります。

> **迷ったら、いったん減らしてください。** 中途半端に多く作るより、少なくても動くものになっているほうが良いです。削った分は後日対応してください。

> **見出しを分けるのはなぜか。** 中身の性質が違うからです。
>
> | 見出し | 何が入るか | 明日どうするか |
> |---|---|---|
> | **MVP** | 今日、入力から表示まで動く形にするもの | 上から一件ずつ実装する |
> | **持ち帰る分** | やることとして書き出したが、今日の時間に入らなかったもの | 完了定義があるので、そのまま次の1つとして始められる |
> | **今回やらないこと** | 詰めるときに今回のスコープから外すと決めたもの | 戻すなら仕様（`README.md`）から変える |
>
> 混ぜると、決めたはずのことが「あとで戻す候補」に並びます。**どちらも12でNotionのページやBacklogの課題になる**ので、今日やらない理由はどちらにも一行書いてください。

### ✅ チェックポイント5

- [ ] `TASKS.md` の今日やる分がMVP分に絞られている
- [ ] 入力・処理・表示の処理がつながっていて、動くものができるタスク一覧になっている
- [ ] MVP構築は後半の実装時間に収まる分量である
- [ ] それぞれに完了定義（画面のどこを見れば終わったと分かるか）が書いてある
- [ ] **「持ち帰る分」に、完了定義と「今日やらない理由」がそろって残っている**（全部MVPに入ったなら空で構いません）
- [ ] 今回のスコープから外したものが、「今回やらないこと」に理由つきで残っている
- [ ] **最初の1つが何かがはっきりしている**

### 実装前にコミットのレビューを用意する

コードレビューには、Claude Codeに同梱された `/code-review` を使います。
実装時の会話とは別のサブエージェントが、未プッシュのコミットと未コミットの変更を読み、不具合や簡素化できる点を報告します。
`--fix` を付けなければ、ファイルは変更しません。
完了定義を満たしたかは、このあと自分で画面を操作して確かめます。

```text
/code-review
```

> **同名の自作エージェントスキルは置きません。** `.claude/skills/code-review/` や `~/.claude/skills/code-review/` があると、同梱のものよりそちらが優先されます。
> 以前の教材でコピーした人は、既存の内容を確認して別の場所に退避し、同梱の `/code-review` を使える状態にしてください。

自分で打ち忘れたときに備えて、次のフックも設定します。

| 動くとき | すること |
|---|---|
| コミットの直前 | 前回のコードレビューより新しいファイルがあれば、一度止めて `/code-review` の実行をClaudeに指示する（Markdownの文書は判定から除く） |
| コミットの直前 | 別のサブエージェントがセキュリティレビューを実行し、CriticalかHighの指摘があれば止める |
| 自分で `/code-review` と打ったとき | コードレビューの制御ファイルを更新する |

コミット前の二つは並行して動きます。
設定とスクリプトは [hooks/README.md](../hooks/README.md) にあります。
以前の教材のフックが残っている人は、同ページの「以前の教材から移行する場合」も確認してください。
フックは自分のユーザーアカウントの権限で動くため、登録する前に、何を読み、何を変更するかを確認してください。

```text
コミット前にレビューするフックを、このプロジェクト（myapp）に設定してください。
次のURLから、同名のファイルを .claude/hooks/ に保存してください。
- https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/pre-commit-code-review.mjs
- https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/mark-code-reviewed.mjs
- https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/security-review-prompt.md

次の設定例を読み、hooks を .claude/settings.json に追加してください。
既存の設定は残し、同じフックを重複して登録しないでください。
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/settings.review.json

.gitignore に .claude/code-reviewed を追加してください。
各フックが何を読み、何を変更し、いつコミットを止めるかを短く説明してください。
まだコミットしないでください。
```

設定例はNode.jsを使い、BashとPowerShellの両方を対象にします。
`/hooks` を開き、PreToolUseに四つ、UserPromptExpansionに一つの登録があることを確認してください（前半のフックが残っていれば、その分も表示されます）。
表示されなければClaude Codeを開き直し、メンターと設定を確認します。

**`.claude/code-reviewed` は、レビューの合格証明ではありません。**
フックが一度止めたときか、自分で `/code-review` と打ったときに更新されます。
結果が届く前でも次のコミットは通り得るので、指摘が届くまで待ち、内容を読んでから再試行してください。

### 止まることを自分の目で確認する

実在しないテスト用の値を使い、セキュリティレビューでコミットが止まるかを確かめます。
実際のAPIキーは使いません。

```text
フックの動作確認をします。hook-test.js というファイルを作り、
const API_KEY = "sk-test-0000000000000000"; の1行だけを書き、hook-test.js だけをステージしてコミットを試してください。
止められたら、表示された理由をそのまま報告し、フックの指示に従ってください。
プッシュはしないでください。
```

1. コミットが止まり、コードレビューの指示とセキュリティの指摘が出ることを確認します。
   `/code-review` が始まらなければ、自分で打ちます
2. 指摘が届いたら、「このままもう一度コミットを試してください」と指示します。
   コードレビューの確認は通っても、セキュリティレビューで再び止まることを確認します
3. 確認できたら、テスト用ファイルを消します

```text
hook-test.js を削除してください。まだコミットしないでください。
```

止まらずコミットされた場合はメンターを呼びます。
プッシュせず、そのテスト用コミットだけを取り消してファイルを削除させ、`/hooks` の登録と会話の「hook error」を確認してください。

エージェントフックは実験的な機能で、エラーや見落としで止められない場合があります。
使えない環境では、コミットの前に [レビューの代替プロンプト](../templates/verify-prompt.md) で同じ観点を確認して進めます。
CriticalとHighの指摘は、直すか、該当機能をMVPから外してください。

確認できたら、設定を保存します。

```text
.claude/settings.json、.claude/hooks/、.gitignore の変更をコミットしてください。
フックに止められたら、理由とレビューの指摘を報告して止まってください。
プッシュはしないでください。
```

### 実装の進めかた

次の一件だけを指示します。
初回用の例は [templates/first-instruction.md](../templates/first-instruction.md) にもあります。

```text
TASKS.md の「MVP」の次のやること1件だけを実装してください。
- 実装する前に、その1件の完了定義をそのまま読み上げてください。
  書かれていない、または画面で判断できない場合は、実装せずに案を出してください
- 完了定義を満たすためだけのコードを書き、次の1件で必要になりそうなものは先に作らないでください
- 実装したら、どのファイルかURLをブラウザで開き、何を操作し、どこを見ればよいかを短く伝えて止まってください。
  私が確認するまで、終わったと宣言しないでください
```

ブラウザを自分で操作し、いま作った一件と、それまでに作った機能を確かめます。
動かなければ、「追加を押しても一覧に増えない」のように見たままを伝えて直させてください。
確認できたら、次のように指示します。

```text
確認できました。TASKS.md を更新してコミットしてから、次のやることに進んでください。
コミットがフックに止められたら、次へ進まずに、理由とレビューの指摘を報告してください。
プッシュはしないでください。
```

コードレビューの指摘が届いたら、いま作った機能や以前に動いていた機能に関わる不具合を直します。
簡素化など、今日の動作に支障のない改善は持ち帰って構いません。
セキュリティのCriticalとHighは解消してからコミットします。
直した場合はもう一度ブラウザで確かめ、コミットを指示してください。

```text
直さなかった指摘を、TASKS.md の「レビューで残した指摘」に書き足してください。
それぞれに今回直さない理由を、セキュリティの指摘には重大度も書いてください。
```

コードレビューは未プッシュのコミットも読みます。
すでに理由つきで残した指摘が再び出た場合は、同じものを重複して書き足す必要はありません。
セキュリティのエージェントフックは、MediumとLowだけなら指摘を報告せずに通ります。
それらも知りたいときは、10のセキュリティレビューで確認します。

<a id="このエージェントスキルのルール"></a>

#### 一件ずつ進める理由

| ルール | なぜ |
|---|---|
| 一回に一件だけ実装する | 動かなくなったときに、原因になった変更を絞れるため |
| 完了定義を画面で判断できる形にする | コードが読めなくても、自分で操作して確かめられるため |
| 完了と判断するのは人間 | 実装したClaudeの報告だけでは、完了定義の読み違いに気づけないため |

### よくある状況と対処

| 状況 | 対処 |
|---|---|
| 一件が15分経っても動かない | メンターと、さらに小さい一件に分ける |
| 前の機能が動かなくなった | 「前の機能も動くように、いまの実装を直してください」と、見たままを伝える |
| 同じ不具合を3回直させても直らない | いったん止め、残したい変更を確認してから、最後に動いていた状態へ戻す |
| コードレビューが始まらない | 自分で `/code-review` と打ち、結果を待つ |
| コミットに時間がかかる | セキュリティレビューに数分かかる場合がある。結果を待つ。先に自分で `/code-review` を打って結果を読むと、同じコミットを試し直す回数を減らせる |
| 利用枠が少ない | 挙手してメンターに相談する。コードレビューの負担を減らすなら、一度 `/code-review low` と打つ |
| 途中で別のアイデアを思いついた | 仕様の範囲内なら完了定義つきで「持ち帰る分」へ。仕様を変える話なら、理由つきで「今回やらないこと」へ残す |
| `CONTEXT.md` と違う言葉で実装されている | 「`CONTEXT.md` の用語に合わせて」と伝える |
| どの案でいくか決められない | 捨てる前提の小さい試作で決めてから本実装に戻る |
| どうしてもMVP全部が動かない | 動く画面を残し、未完了の項目を理由つきで「持ち帰る分」へ移す。動く範囲で10以降へ進む |

### フックが止められない操作

フックが対象にするのは、Claude CodeのBashかPowerShellによる `git commit` です。
自分のターミナルからのコミット、`git -C myapp commit` のような別の書き方は対象外です。
スクリプトが無い、Node.jsが動かない、レビューが見落とすなどの場合も、止まらないことがあります。

コードレビューの確認はファイルの更新日時を比べるため、手編集やシェルからの変更も扱います。
ただし、ファイルを削除しただけの変更とMarkdownだけの変更はこの判定に入りません。
セキュリティレビューは、その場合もコミットの差分を読みます。
対象外の操作をした場合は、コミット前にレビューを手動で指示してください。

### 任意でテスト駆動を試す

動くMVPができて時間が余った人は、[tddの完成例](../skills/tdd/SKILL.md) を `.claude/skills/tdd/SKILL.md` に保存して使えます。
準備とテストの書き方は、そのファイルにまとまっています。
Playwrightはアプリのコードではなく、操作を自動で確かめる道具です。

```text
次のURLの中身を .claude/skills/tdd/SKILL.md に保存し、必要なテスト環境を準備してください。
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/skills/tdd/SKILL.md

```

テストが通っても、最後は自分で画面を確かめます。
見た目の読みやすさなどを無理に自動テストにせず、何を手で確かめるかを残してください。
テスト環境の取得で止まる場合はメンターを呼び、解決しなければ手動確認で進めます。

## 10. ハンズオン⑦ 全体を確かめてプッシュする

9では一件ずつ完了定義を確かめました。
ここでは `README.md` の完成判定に沿って、MVP全体を通して使います。
その後、フックを入れる前のコミットも含めてレビューし、GitHubにプッシュします。

### 完成判定に沿って通しで確認する

```text
README.md の完成判定を読み上げてください。まだ直さないでください。
```

読み上げられた項目を順に、自分でブラウザを操作して確かめます。
思っていた動きや見た目と違う箇所はメモし、互いに影響しない修正を二つか三つまとめて指示してください。

```text
3点直してください。
1. 追加したあとに入力欄を空にして
2. 一覧を新しい順に並べて
3. 全体の文字を少し大きく
```

完了定義そのものを変える修正なら、先に `README.md` と `TASKS.md` を直し、9の一件ずつの流れに戻ります。
どちらの場合も、直したあとは完成判定をもう一度たどって確認し、コミットを指示します。

### コードレビューの指摘を整理する

MVPがまとまったところで、同梱のコードレビューを呼びます。

```text
/code-review
```

結果が届いたら、動作に関わる不具合を直します。
再利用や簡素化などの改善は、今回のMVPに支障がないかで選んでください。
作法の指摘が読めない場合はメンターに相談し、持ち帰るものには理由を付けます。
`CLAUDE.md` の約束に反する変更は、その約束を確認して対応します。

```text
1と2を直してください。3は今回は対象外にします。
直さなかった指摘は、TASKS.md の「レビューで残した指摘」に、今回直さない理由つきで残してください。
```

直したら、ブラウザで完成判定を確かめ直してコミットします。
`/code-review` が使えない場合は [templates/verify-prompt.md](../templates/verify-prompt.md) を使います。

### 初回プッシュの前にセキュリティレビューする

フックを設定する前のコミットは、コミット時のレビューを通っていません。
組み込みの `/security-review` で、現在のブランチと `origin` の既定ブランチとの差分をまとめて確認します。

```text
/security-review
```

以前の教材で `.claude/skills/security-review/` や `~/.claude/skills/security-review/` を置いた人は、同名の自作エージェントスキルを退避してから使ってください。
すでに途中でプッシュしていた場合は、比較元の変更だけでは過去の内容を見切れないことがあります。
次のように、現在のアプリと初回コミット以降の全変更を明示して確認させます。

```text
すでに一部をプッシュしています。
.claude/hooks/security-review-prompt.md の観点で、現在のアプリ全体と最初のコミット以降の変更を
セキュリティレビューしてください。コードは変更せず、MediumとLowも含めて報告してください。
```

CriticalとHighは、直すか、その機能をMVPから外します。
直したら再レビューし、残した指摘には重大度と今回直さない理由を書きます。

```text
直さなかったセキュリティ指摘を、TASKS.md の「レビューで残した指摘」に、
重大度と今回直さない理由つきで書き足してください。
```

`ambiguous argument` などで比較元が見つからない場合は、エラーを貼ってメンターに相談してください。
解決できなければ、上の全体レビューのプロンプトで確かめます。

### GitHubへプッシュする

レビュー後に直したコードや、指摘を残した `TASKS.md` も先にコミットします。
コミットが止まったら指摘に対応し、コードを直した場合は動作確認とセキュリティレビューをやり直してください。

```text
レビューで直した変更と TASKS.md の記録をコミットしてください。
フックに止められたら、理由と指摘を報告して止まってください。まだプッシュしないでください。
```

コミットと必要な再レビューが済んだら、次を指示します。

```text
コミットしていない変更が無いことを確認してから、GitHubへプッシュしてください。
```

自分でターミナルからコミットした変更も、フックを通っていません。
その場合もプッシュの前にセキュリティレビューしてください。
GitHubの `myapp` を開き、ここまでのコミットが見えることを確認します。

## 11. ハンズオン⑧ Cloudflareに公開する

ここまで作ったアプリを、自分のCloudflareアカウントから公開し、URLで開けるようにします。
この講座の本線はブラウザだけで動くアプリなので、HTMLなどの静的アセットだけを公開します。

### なぜCloudflareなのか

Cloudflare Workersは、ブラウザに配るファイルを静的アセットとして公開できます。
コマンドはClaude Codeに任せ、自分は公開先と公開する内容を確認します。
アカウントの作成は事前準備0.1④の手順で済ませてください。

<a id="ステップ1-公開するフォルダを分ける全員5分"></a>

### ステップ1: 公開するフォルダを分ける（全員）

`myapp` には仕様や設定など、公開する必要のないファイルもあります。
ブラウザに配るものだけを `public/` に分けます。

```text
公開用に public/ フォルダを作り、ブラウザに配るファイルだけをそこに移動してください。
- 移動するもの: ブラウザで読み込むHTML・CSS・JavaScript・画像
- 移動しないもの: README.md、TASKS.md、CONTEXT.md、CLAUDE.md、docs/、myidea/、.claude/、.git/、.gitignore、
  テストや開発用の設定、node_modules/、秘密情報、サーバー側の処理のファイル
- アプリの入口は public/index.html にしてください。ファイル名や場所を変えたら、参照も直してください
- tests/app-url.js があれば public/index.html を開くように直し、既存のテストを全部実行してください
```

移動したら、`public/index.html` をブラウザで開き、`README.md` の完成判定をもう一度たどります。
移動した変更は、次に作る公開用の設定と一緒に、デプロイする前にコミットします。

<a id="ルートa-cloudflare-drop-にドラッグドロップする全員本線"></a>

### ステップ2: 公開する

まず、Wrangler（Cloudflareのコマンドラインツール）の設定とログインまでを指示します。

```text
このアプリを Cloudflare Workers の静的アセットとして公開したいです。
1. wrangler.jsonc を作り、assets の directory を ./public/ に向けてください。Workerのスクリプトは不要です。
   .gitignore に .wrangler/、.dev.vars*、.env* が無ければ追加してください
2. npx wrangler login でログインしてください。ブラウザが開くので私が許可します
3. npx wrangler whoami でログイン先を確認してください。
   「You are not authenticated」と出たら、そのまま先へ進まずに教えてください
4. まだデプロイしないでください。アカウント名と wrangler.jsonc の全文を見せてください
```

ログイン操作が進まないときは、VS Codeのターミナルで自分で `npx wrangler login` を実行し、続きを頼みます。
ブラウザが開いただけではログイン成功とは判断せず、`whoami` に表示されたアカウントを確認してください。

設定の例です。
`assets.directory` の中身が配信されるので、`./public/` を指していることを自分の目で確認します。

```jsonc
{
  "name": "myapp",
  "compatibility_date": "2026-08-29",
  "assets": {
    "directory": "./public/"
  }
}
```

`.wrangler/` はWranglerの作業用フォルダです。
手元で使ったデータなどが置かれるため、コミット対象から外します。

#### デプロイ前にコミット済みか確かめる

`wrangler deploy` は、コミット前の変更もそのまま公開します。
未コミットの変更があれば止めるフックを足し、9のコミット前レビューを通してから公開します。

```text
次のスクリプトを .claude/hooks/pre-deploy-check.mjs に保存してください。
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/pre-deploy-check.mjs

次の設定例の hooks を、既存の .claude/settings.json に追加してください。
前半と後半9のフックを残し、同じ設定は重複させないでください。
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/settings.deploy.json

ここまでの変更（public/、wrangler.jsonc、.gitignore、.claude/settings.json、.claude/hooks/ と、
移動に合わせて直した参照やテスト）をコミットしてください。
コミットがフックに止められたら、理由と指摘を報告して止まってください。
```

このコミットでは、セキュリティレビューが公開設定と `public/` の中身も見ます。
CriticalとHighを解消し、残す指摘は理由つきで `TASKS.md` に記録してください。
フックを使えない環境では、同じ観点を手動でレビューし、`git status --short` で変更が残っていないことを確認します。

アカウントと公開するフォルダを確認し、コミットできたら、デプロイを指示します。

```text
npx wrangler deploy を実行し、発行されたURLを教えてください。
workers.dev のサブドメインを登録できないというエラーが出たら、自分で解決しようとせずに止まって、
エラーに出ている dash.cloudflare.com のURLを教えてください。
```

公開URLは `https://⟨Worker名⟩.⟨サブドメイン⟩.workers.dev` の形です。
作ったばかりのアカウントでサブドメインが無い場合は、表示されたダッシュボードのURLを開き、他の人と重ならない名前を登録します。
登録後に設定ファイルが変わっていれば、それもコミットしてからデプロイし直してください。

> **フックが対象にするのは `npx wrangler deploy` です。** `npm run deploy` やCloudflareの画面からの公開は対象外です。
> Autoモードでデプロイが拒否された場合は、理由を確認し、Manualに切り替えて自分で許可するか、ターミナルから実行します。
> その場合も、先にレビューとコミットを済ませてください。

会社のネットワークなどで公開できない場合は深追いせずメンターを呼び、講師の公開手順を見て12へ進みます。

<a id="ステップ3-自分の目で確認する5分"></a>

### ステップ3: 自分の目で確認する

発行されたURLを、想定する利用者が使う別の端末か、別のブラウザプロファイルで開きます。
スマートフォン向けなら、自分のスマートフォンで確かめてください。

- 意図した画面が表示されるか
- 手元と同じ操作ができるか
- 見せたくない情報が表示されていないか

隣の人にもURLを渡して開いてもらいます。
登録した直後に開けなければ、少し待って開き直してください。
確認できたら、公開URLを残します。

```text
公開URLを README.md の先頭に1行追記してください。
デプロイで書き足された wrangler.jsonc があれば、それも一緒にコミットしてからプッシュしてください。
コミットがフックに止められたら、理由と指摘を報告して止まってください。
```

`README.md` だけの変更ではコードレビューの確認は省かれますが、セキュリティレビューは動きます。

URLを知っている人は誰でも開けます。
URLを知らせていなくても、秘密にはなりません。
`localStorage` のデータは、別のブラウザや公開URLへ自動で引き継がれませんが、HTMLに埋め込んだ情報や外部へ送信するデータは別です。
保存先だけで判断せず、公開ファイルと通信も確認してください。

- **独自ドメインをつなぐ**：持っているドメインを、Cloudflareのカスタムドメインとして設定します
- **プッシュ後の公開を自動化する**：GitHub Actionsで、`main` へのプッシュ後にデプロイする設定を作ります。ローカルのフックはActionsでは動かないので、レビューや公開対象の確認も別に組み込みます
- **見せる相手を絞る**：Basic認証を試します。サーバー側の処理を追加するので、`README.md` と `TASKS.md` の範囲を見直してから進めます

    ```text

    - IDとパスワードは wrangler secret に置き、リポジトリにも公開ファイルにも含めないでください

    - HTTPSで配信し、静的ファイルもAPIもすべて認証の対象にしてください
    - トップページとCSS、JavaScript、APIがあれば各URLを直接開き、認証なしと誤った認証で401、
      正しい認証で利用できることを確認する手順を教えてください
    ```

    静的アセットは通常Workerの処理より先に返るため、認証を先に通す設定が必要です。
    パスワードの値は会話に貼らず、自分のターミナルで `npx wrangler secret put ⟨名前⟩` を実行して登録します。
    トップページだけの401を、全ファイルが守られている証拠にしないでください。

- **サーバー側が必要になる線を引く**：APIキーを使う外部APIやデータ共有を足す場合、ブラウザ用の `public/` とWorker用の `src/` を分け、手元では `npx wrangler dev` で試します。秘密情報は `.dev.vars`、公開先ではシークレットに置き、コードにも会話にも値を書きません。これは持ち帰り課題にして構いません

### MCPをつなぐ

どちらか片方で構いません。迷ったらネイティブ統合されているNotionがよいでしょう。

#### Notion — ネイティブ統合あり、つなぐだけ

前半2の任意課題のGmailと同じ手順です。

1. ブラウザで [claude.ai](https://claude.ai) を開く
2. 左側メニューの「カスタマイズ」→「コネクタ」を開く
3. 一覧から Notion を探して「接続」を押す
4. Notionアカウントでログインし、許可画面の内容を確認して許可する

難しい設定は不要です。個人のNotionを使いたくない人は、この場では接続せず手順を見るだけで構いません。

#### Backlog — ネイティブ統合なし、自分でMCPサーバーを設定する

Backlogはclaude.aiのコネクタ一覧にはありません。自分でMCPサーバーを追加します。

> このルートはNode.jsを使います（MCPサーバーを `npx` で起動するため）。事前準備0.2で全員入れているので、そのまま進めて構いません。ターミナルで `node -v` を実行してバージョンが出ない場合だけ、Notion側を選んでください。

**APIキーは、Claude Codeとの会話には一度も書きません。** チャット欄に貼った文字は会話履歴としてそのまま手元に残るので、秘密情報をそこに通さないのが原則です（→10でレビューした「秘密情報がコードに書かれていないか」と同じ観点です）。ここだけは自分の手でターミナルを操作します。

1. `myapp` の `.gitignore` に `.env` を追加します（`.gitignore` が無ければ作成）

    ```bash
    echo ".env" >> .gitignore
    git check-ignore .env
    ```

    2行目の結果に `.env` と表示されれば入っています。何も表示されないときは、`.env` が正しく書き込まれていません（最後の行に改行が無くて `.env` が前の行にくっついた、など）。エディタで `.gitignore` を開き、`.env` が単独の1行になっているか確かめて直し、保存してから、もう一度 `git check-ignore .env` を実行してください

2. Backlogの「個人設定」→「API」からAPIキーを発行します
3. エディタで `myapp` 直下に `.env` を新規作成し、次の2行を書いて保存します。⟨⟩の中だけ自分の値に置き換えてください

    ```
    BACKLOG_DOMAIN=⟨自分のスペース⟩.backlog.com
    BACKLOG_API_KEY=⟨発行したAPIキー⟩
    ```

4. Claude Codeを起動しているのと同じターミナルタブで、`.env` を読み込んでからMCPサーバーを登録します。**`${...}` の部分はシングルクォートのまま**書き換えずに実行してください（展開させてしまうと、キーの値そのものが設定ファイルに書き込まれます）

    **macOS / Linux / WSL**

    ```bash
    set -a && source .env && set +a
    claude mcp add --env BACKLOG_DOMAIN='${BACKLOG_DOMAIN}' --env BACKLOG_API_KEY='${BACKLOG_API_KEY}' --scope user backlog -- npx -y backlog-mcp-server@0.18.0
    ```

    **Windows（PowerShell）**

    ```powershell
    Get-Content .env | ForEach-Object { if ($_ -match '^(.*?)=(.*)$') { [Environment]::SetEnvironmentVariable($Matches[1], $Matches[2]) } }
    claude mcp add --env BACKLOG_DOMAIN='${BACKLOG_DOMAIN}' --env BACKLOG_API_KEY='${BACKLOG_API_KEY}' --scope user backlog -- npx -y backlog-mcp-server@0.18.0
    ```

> **`${...}` のまま登録するのが重要です。** ここで実際のAPIキーの値を渡すと、値がそのまま設定ファイル（`~/.claude.json`）に平文で書き込まれます。`${BACKLOG_API_KEY}` という参照だけを渡せば、設定ファイルにはこの参照文字列しか残りません。実際の値はClaude Code起動時に、いま読み込んだ環境変数から解決されます。設定ファイルを覗かれても、Claude Codeとの会話履歴を覗かれても、実際のAPIキーは出てきません。

> **バージョンを固定しているのは意図的です。** `npx backlog-mcp-server` のようにバージョンを書かないと、そのとき最新のものが取ってきて実行されます。何が動くかが日によって変わるということなので、中身を確認したものだけを動かすために番号まで書きます。前半5でHooksについて言ったこと（「中身を理解できるものだけを登録する」）と同じ考え方です。

> **`.env` はコミットしないでください。** `myapp` は10でGitHubにプッシュし、11でアプリを公開したリポジトリです。手順1で `.gitignore` を先に整えているのはそのためです。念のため `git status` で `.env` が追跡対象になっていないか確認してから次に進んでください。スコープを `project` にすると設定自体が `.mcp.json` としてリポジトリに書き込まれてしまうため、スコープは必ず `user` にしてください。

#### どちらの場合も: Claude Codeを開き直す

設定できたら、Claude Codeを開き直してください。MCPの接続はClaude Codeの起動時に確立されるため、`/clear` だけでは反映されません。

- **Notionを選んだ人**: VS Code拡張なら、前半2と同じくコマンドパレット（macOSは Cmd+Shift+P、Windowsは Ctrl+Shift+P）で `Developer: Reload Window` を実行し、Claude Codeのパネルを開きます
- **Backlogを選んだ人**: 上の手順4を実行したターミナルタブで、そのまま `claude` と入力して起動します。`.env` から読み込んだ値はそのタブにしか入っていないので、VS Code拡張やほかのタブで開くと接続できません

開き直したら `/mcp` で接続状態（Connected）を確認します。

## 14. クロージング

### 今日やったこと

```
バイブコーディング = Intent（何を作りたいのか）の明確化 → エージェントスキルによる緻密化 → 仕様化 → 計画 → 実装 → レビュー → 公開
```

**いちばん持ち帰ってほしいのは、エージェントスキルに数行足しただけで宿題の持ち物が変わった、という体験です。** 仕組みを設計すると、出てくるものが変わる。今日いじったのは、AIの振る舞いそのものでした。

レビューは、コミットの前にフックで実行する形にしました。
公開する範囲は `public/` に分け、未コミットの変更はデプロイ前に止めます。
フックが見ている操作と対象外の操作を区別し、動かなかった場合は手動レビューで補うところまで持ち帰ってください。

仕様を詰めるエージェントスキル、コードを見る同梱の `/code-review`、コミット前のセキュリティレビュー、画面で完了を判断する人間に、役割を分けました。

1. ブラウザで [claude.ai](https://claude.ai) を開く
2. 左側メニューの「カスタマイズ」→「コネクタ」を開く（`claude.ai/customize/connectors`）
3. 対象のコネクタの行から接続を解除する
