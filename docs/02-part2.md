# 後編（2時間）狙ったものに確実に仕上げる

後編のゴール: **前編で書いた「ゴールの一文」を、検証済みの完成品にして持ち帰ること。**

> 開始前の儀式（前編と同じ）: `/status` で残量確認。半分を切っている人は挙手してください。
> メンターが進め方（まとめ指示の徹底・メンター機ペア作業）を個別に調整します。

---

## 7. 「確実に」の正体（10分・今日最後の座学）

前編の終わりに触れたとおり、バイブコーディングの弱点は**迷子**です。典型的な失敗はこう進みます。

> ノリで機能を足す → だんだん指示が雑になる → どこかが壊れる → 直させると別の場所が壊れる → 何が「正解の状態」だったか自分でも分からなくなる → 終了

原因は能力でも運でもなく、**3つの不足**です。

| 不足 | 症状 | 処方（=3原則） |
|---|---|---|
| ゴールがない | 「もっと良く」を無限に繰り返す | ① ゴールは一文で。**一文にないものは今日は作らない** |
| 確認がない | できたつもりで先に進み、後で崩壊 | ② 確認条件を1つ満たすたびに目で確認 |
| 戻り先がない | 壊れた地点まで手探りで後退 | ③ 動く状態を保つ。**15分ごとにチェックポイント** |

これから60分、この処方をそのまま運用します。タイマーは会場全体で共有します（15分ごとに合図が鳴ります）。

## 8. ハンズオン③ 自分のアイデアを作る（60分・メイン）

### 進め方

1. **開始（最初の5分）**: 新しいフォルダをClaude Codeで開き、最初の指示を出す。テンプレはこれです（コピペ用: [templates/first-instruction.md](../templates/first-instruction.md)）:

```text
これから小さなWebアプリを作ります。ゴールは:
「⟨あなたのゴールの一文⟩」

完成の確認条件は次の3つです。
1. ⟨確認条件1⟩
2. ⟨確認条件2⟩
3. ⟨確認条件3⟩

まず、確認条件1だけを満たす最小版を、1つのHTMLファイルで作ってください。
2と3はまだ作らないでください。
```

> ポイントは最後の2行です。**いきなり全部作らせない。** 最小版が動いてから積み上げるのが、③「動く状態を保つ」の実践です。

2. **15分ごとのチェックポイント運用**: 会場の合図が鳴ったら、手を止めて次を実行:
   - 今、アプリは動いているか? → 動いていれば**その状態を保存**（Gitが分かる人は `git commit`、分からない人はフォルダごと複製して `backup-1430` のような名前を付けるだけでOK）
   - 動いていなければ → **リカバリー3手**（貼る・戻す・小さくする）で動く状態に戻してから保存
   - 保存したら次の確認条件へ進む

3. **回し方は前編のリズムで**: 違和感は2〜3個まとめて1回で。画像で伝えられるものは画像で。

### 詰まったときのエスカレーション順

1. リカバリー3手（貼る・戻す・小さくする）— まず自分で2回試す
2. 挙手 → メンターが巡回します
3. それでも詰まったら**救済ルート**: 直近のバックアップ（または救済タグの参考実装）から再開。恥ずかしいことではありません。**「戻って進む」は今日教えた正規の技術です**

### よくある divergence と対処

| 状況 | 対処 |
|---|---|
| 確認条件1が15分経っても動かない | ゴールが大きすぎるサイン。メンターと一緒に一文を小さく割る |
| 予定より早く3条件を満たした | おめでとう。9を先取りして検証まで済ませ、その後「見た目をもう一段」へ |
| 途中でもっと良いアイデアを思いついた | **今日は乗り換えない。** メモして持ち帰る（乗り換えは迷子の最大要因） |
| 利用枠の上限に当たった | 挙手 → メンター機（Max）でペア作業に切り替え |

### ✅ チェックポイント4

確認条件3つのうち**2つ以上**が動いている状態で9へ。（3つ揃っていなくても大丈夫です。仕上げの時間で追い込みます）

### 🚀 拡張ミッション③（3条件を満たして時間が余った人向け・任意）

- まず9（仕上げと検証）を先取りして完了させる。そのうえで:
- 〔共通〕**4つ目の条件を足す**: 「今後やりたいこと」から1つ選び、今日の型（一文→最小版→確認）でもう一周。同じ型が2周目は倍速で回ることを体感する
- 〔Eng〕**計画→実装の2段で足す**: 4つ目の機能をプランモードで計画させ、計画を読んでから実装を許可する。バイブコーディングとスペック駆動（★コラム6）の中間地点
- 〔Eng〕**チェックポイントをGitに格上げ**: 15分保存をコミット運用にし、わざと1機能壊してから `git checkout`（または「この変更を取り消して」）で戻る訓練をしておく

## 9. ハンズオン④ 仕上げと検証（25分）

「確実にできあがった」と言い切るための締めの工程です。

### ステップ1: Claudeに検証させる（10分）

自分の目に加えて、Claude自身に確認条件をチェックさせます（コピペ用: [templates/verify-prompt.md](../templates/verify-prompt.md)）。

```text
このアプリの完成条件は次の3つです。
1. ⟨確認条件1⟩
2. ⟨確認条件2⟩
3. ⟨確認条件3⟩

それぞれについて、実際にどう確認したかを説明した上で、満たしているか判定してください。
満たしていないものがあれば、直してから再度確認してください。
```

> **「できました」を鵜呑みにしない。** Claudeは実際には確認せず「できています」と答えてしまうことがあります。
> 「どう確認したかを説明した上で」の一文がそれを防ぐ仕掛けです。
> 最後は必ず**あなたの目**で3条件を触って確認してください。あなたの確認が最終権限です。

### ステップ2: 見た目をもう一段（10分）

残り時間で、共有タイムに向けて磨きます。まとめ指示1回分だけ:

```text
発表用に見た目を仕上げてください。
1. アプリ名をタイトルとして目立つ場所に表示
2. 全体の配色とフォントを統一して、素人っぽさをなくす
3. スマホの画面幅でも崩れないように
```

### ステップ3: READMEを書かせる（5分）

```text
このアプリのREADME.mdを作ってください。内容は:
- アプリ名と一言説明（ゴールの一文をもとに）
- 使い方（開き方と操作手順）
- できること（確認条件3つをもとに）
- 今後やりたいこと(あれば)
```

### ✅ チェックポイント5（完成判定）

- [ ] 確認条件3つを**自分の目**で確認した
- [ ] Claudeの検証報告と自分の確認が一致した
- [ ] READMEがある

3つチェックが付いたら、それが「確実にできあがった」の定義です。

### 🚀 拡張ミッション④（完成判定後・任意）

- 〔共通〕**マイ検証テンプレを持ち帰る**: 9で使った検証プロンプトを `my-verify.md` として保存し、⟨確認条件⟩部分を空欄のテンプレにしておく（雛形は [templates/verify-prompt.md](../templates/verify-prompt.md)）。次に何か作るとき、これがあなたの「型」の第1号になる（スキル化の入口。★コラム5）
- 〔Eng〕**検証を自動にする**: 「確認条件3つを自動でチェックする簡単なテストを書いて、実行して結果を見せて」と指示する。人の目→Claudeの検証→自動テストという検証の3段活用。第9章「任せきる」の最小体験

## 10. 共有タイム（15分）

3〜4名にデモしてもらいます。見どころは作品そのものより**プロセス**です。発表者は次の3点を30秒ずつ:

1. ゴールの一文（何を作ると宣言したか）
2. いちばん詰まった瞬間と、どの手で抜けたか
3. いちばん効いた指示（実際の文言を画面で見せる）

聞く側は「その指示、もらった」と思ったらメモしてください。**今日の最大のお土産は、他人の指示の語彙です。**

## 11. クロージング（10分）

### 今日やったこと

- 指示→見る→直すのループ（バイブコーディング）
- ゴールの一文＋確認条件＋チェックポイントで**確実に**作りきる型
- 壊れても戻れるリカバリー3手

### 今日の先にある世界

今日のやり方には、まだ伸びしろが3段あります。

| 段階 | 何ができるようになるか | 入口 |
|---|---|---|
| **型を教える** | 今日の「まとめ指示」や検証手順を**スキル**として保存し、毎回言わなくて済むようにする | ★コラム5 |
| **仕様で導く** | ゴールの一文を**仕様書**に育て、大きなものを計画的に作る | ★コラム6 |
| **任せきる** | 完了条件と検証を渡して、**自分が見ていない間に**作らせる（ゴール実行・自動ループ） | ★コラム7 |

今日書いた「ゴールの一文＋確認条件」は、実はそのまま「任せきる」ときの完了条件になります。**今日の型は、最先端の自律開発とひと続きです。**
