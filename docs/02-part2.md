# 後半（2時間）自分で定義したIntentを、実際のソフトウェアにする

後半のゴール: **宿題で詰めた仕様とやることリストを、「今日やる分」に線を引き、上から順に動かして、検証済みのソフトウェアにして持ち帰ること。**

## 今日の全体地図

3パート構成の最後です。

```
前半 → 【宿題】 → 後半（今ここ）
```

- **前半（済）**: Vibe Codingを体験し、自分が作りたいものを言葉にし、`tsumetsume`・`ddd`・`tsumete` の3つのSkillを自分で作った
- **宿題（済）**: 自作の `tsumete` に自分のアイデアを問い詰めさせ、**仕様（`README.md`）とやることリスト（`TASKS.md`）**まで具体化した
- **後半（今ここ）**: やることに線を引き、上から順に実装し、最後にレビュー・改善させる

前半と宿題の成果が、そのまま後半の入力になります。**宿題が思うように進まなかった人も後半は進められます**（→ 7. 宿題ふりかえり）。

| 0:20–1:30 | **9. ハンズオン⑥ 実装**（メイン） — 上から1つずつ。15分ごとに動く状態を保存する | 動くアプリ本体 |

## 7. 宿題ふりかえり（5分）

まず、**宿題で使った自分のアプリのフォルダ**（`0901-yamada-app` など）をVS Codeで開いてください。メニューの「ファイル」→「フォルダーを開く…」から、**そのフォルダを直接**選びます。

```
⟨forkした実践用リポジトリ⟩/0901-yamada-app/   ← ここを開く
├── README.md      宿題で詰めた仕様
├── TASKS.md       宿題で作ったやることリスト
├── CONTEXT.md     用語集（あれば）
└── docs/adr/      決定記録（あれば）
```

開いたら `/usage` で利用枠の残量を、`/status` でいま選んでいるモデルを確認します。**残量が半分を切っている人は挙手してください。** このあと実装（9）に70分使うので、足りないことはここで分かったほうが手当てできます。

そのうえで、宿題の状態を3段階のどれかに位置づけてください。

| 状態 | 手元にあるもの | このあとどうするか |
|---|---|---|
| **揃っている** | `README.md` と `TASKS.md` の両方 | このまま8へ |
| **仕様だけある** | `README.md` はあるが `TASKS.md` が無い | 8の冒頭で `TASKS.md` を作るところから始める（下のプロンプト） |
| **そもそも決まっていない** | 宿題に着手できなかった | 挙手してください。前半2〜3で作ったものを種に、メンターと一緒に急いで固めます |

`TASKS.md` が無い人は、8の冒頭でこれを貼ってください。

```text
README.md を読んで、実装する順に「やること」の一覧を TASKS.md に書き出してください。
1つは15分以内で終わる大きさにし、それぞれ「画面のどこを見れば終わったと分かるか」を書いてください。
上から順にやれば、途中で止まっても動くものが残る順番にしてください。
```

**どの状態でも後半は進められます。** 焦って乗り換えず、今持っているものを育てる方向で進んでください。

## 8. ハンズオン⑤ 今日やる分に線を引く（15分）

宿題で詰めた人ほど、`TASKS.md` のやることは多くなっているはずです。**それは正しい状態です。** 減らす必要はありません。ここでやるのは、**今日触る分と、持ち帰る分に線を引くこと**だけです。

### なぜ線を引くのか

実装は70分です。やることが10個あれば1つ7分。**丁寧に詰めた人ほど1つあたりの時間が短くなって終わらない**——これを防ぎます。

### ステップ1: 粒度を揃える（5分）

まず、大きすぎるものを割ります。

```text
TASKS.md を読んで、次を指摘してください。
- 15分では終わらなさそうな大きさのもの
- 「画面のどこを見れば終わったと分かるか」が書かれていないもの
- 順番を入れ替えたほうが、途中で止まっても動くものが残るもの

指摘だけしてください。まだ直さないでください。
```

指摘を**自分の言葉で読み**、納得したものだけ反映させます。全部を鵜呑みにする必要はありません。

```text
1と3を反映してください。2は今日は対象外にします。
```

### ステップ2: 今日やる4つを選ぶ（10分）

ここが後半の勝負どころです。

```text
TASKS.md のやることを、今日やる4つと、持ち帰る分に分けてください。

今日の4つは、それだけで「動くものが1本通る」組み合わせにしてください。
残りは TASKS.md の「今回やらないこと」に移し、なぜ今日やらないかを一行ずつ書いてください。
```

**「上から4つ」ではなく「動くものが1本通る4つ」**が肝心です。入力・処理・表示が揃わないと画面が動きません。印刷や見た目の仕上げは自然に後ろへ落ちます。

出てきた4つを見て、**自分で納得できなければ入れ替えてください。** 決めるのはあなたです。

> **4つが多い・少ないと感じたら調整して構いません。** 迷ったら**減らす**ほうに倒してください。3つ動いて終わるほうが、5つ中途半端より確実に良い一日になります。

### ✅ チェックポイント5

- [ ] `TASKS.md` の今日やる分が4つ以内に絞られている
- [ ] それぞれに「画面のどこを見れば終わったと分かるか」が書いてある
- [ ] やらないと決めたものが、理由つきで残っている
- [ ] **最初の1つが何かがはっきりしている**

## 9. ハンズオン⑥ 実装（70分・メイン）

ここが後半の中心です。**全員同じアプリを作るのではなく、同じプロセスを使ってそれぞれ違うものを作ります。**

> **この70分、あなたはファイルを一度も自分の手で編集しません。** コードも `TASKS.md` も、書き換えるのはすべてClaude Codeです。あなたの仕事は**指示を出す・画面を見る・目印で判定する**の3つだけ。手で直したくなったら、それは指示で伝えるべきことです。

### 進め方

1. **最初の1つから着手**: 8で決めた最初のやることを、最小の形で作らせます（コピペ用テンプレ: [templates/first-instruction.md](../templates/first-instruction.md)）

```text
TASKS.md の1つ目だけを、最小の形で実装してください。
他のものにはまだ手をつけないでください。
```

2. **見て、直す**: できたら必ずブラウザで自分の目で確認します。**`TASKS.md` に書いた「終わったと分かる目印」が、そのままチェックリストです。** 違和感があれば、前半で覚えた作法どおり**2〜3個まとめて1回**で直させます

3. **15分ごとのチェックポイント運用**: 講師の合図（または自分のタイマー）で、次を実行してください

   まず、**`TASKS.md` に書いた「終わったと分かる目印」を、自分の目で確認します。**

   | 目印の確認 | どうするか |
   |---|---|
   | **OK** | **コミットしてプッシュする**（下のプロンプト） |
   | **NG** | 前半で覚えた**リカバリー3手**（貼る・戻す・小さくする）で動く状態に戻してから、あらためて確認 |

   目印がOKなら、そのまま頼んでください。**gitが分からなくても構いません。**

```text
目印を確認できました。いまの状態をコミットして、プッシュしてください。
```

   **確認できたものだけを残していく**——これが今日の保存の作法です。動いていないものはコミットしません。

   > プッシュ先は**事前準備0.4.0でforkした、自分のリポジトリ**です。ほかの参加者と衝突することはないので、遠慮なく何度でもプッシュしてください。

4. **`TASKS.md` の状態を更新させる**: 次へ進む前に、終わったものへ印を付けさせます。**自分の手でファイルを開いて書き換えないでください。** 今日はファイルを触るのもClaude Codeの仕事です

```text
いま終わった分を、TASKS.md の状態に反映してください。
```

   **どこまで来たかが常にファイルに残っている**のが、この70分の正しい進み方です

### 詰まったときのエスカレーション順

1. リカバリー3手（貼る・戻す・小さくする）— まず自分で2回試す
2. `/model` で重いモデルに切り替えて、同じことをもう一度頼む
3. 挙手 → メンターが巡回します
4. それでも詰まったら、やることを削ってでも「動く状態」を優先する。**完成度より、確認できる状態を保つことが優先です**

### よくある状況と対処

| 状況 | 対処 |
|---|---|
| 最初の1つが15分経っても動かない | 大きすぎるサイン。メンターと一緒にさらに小さく割る |
| 予定より早く4つとも終わった | 「今回やらないこと」から1つ戻して、同じ型でもう一周する |
| 途中でもっと良いアイデアを思いついた | **今日は乗り換えない。** 「思いついたことを TASKS.md の『今回やらないこと』に書き足して」と頼んで持ち帰る |
| 利用枠の上限に当たった | 挙手 → メンター機でペア作業に切り替え |
| `CONTEXT.md` と違う言葉で実装されている | 「`CONTEXT.md` の用語に合わせて」と伝える。宿題で用語集を作った人はここで効きます |

### ✅ チェックポイント6

今日やると決めた4つのうち、**主要なものが動いている**状態で10へ。全部揃っていなくても構いません。仕上げの時間で追い込みます。

### 🚀 拡張ミッション③（早く終わった人向け・任意）

- 〔共通〕**「今回やらないこと」から1つ戻す**: 今日の型（最小実装 → 目印で確認 → 保存）でもう一周する
- 〔Eng〕**ブランチを切ってPRを出し、レビューをもらう**: 本線では main にそのままコミットしていますが、実務ではブランチを切り、プルリクエスト（PR）にして他の人の目を通します。ここもClaude Codeに頼めます

    ```text
    このやることの分をブランチに切ってコミットし、プッシュして、プルリクエストを作ってください。
    PRの説明には、何を変えたかと、どこを見れば動作を確認できるかを書いてください。
    ```

    PRの向き先は**自分のfork内**（`main` ← 作業ブランチ）で構いません。元のリポジトリへ向けると、他の参加者のPRと混ざります。PRができたらURLを隣の人に渡し、**レビューしてもらってください。** 見る側は「どこを見れば動くと分かるか」がPRに書かれているかを確認します。**「目印を書く」という今日の作法が、そのままレビュー可能性になる**——これが実務との接続点です
- 〔Eng〕**完了条件を渡して任せてみる**: `TASKS.md` の1つを、その「終わったと分かる目印」ごと `/goal` に渡し、満たすまで自走させてみる。**これが「任せきる」の入口です**（→ [columns.md](columns.md) ★8）
- 〔Eng〕**インフラ構成を設計させる**: 「このアプリをどこで動かし、データはどこに置くべきか」をClaudeに設計させ、選択理由を説明させる。デプロイまでは今日はやりません
- 〔Eng〕**リリース自動化に挑戦する**: GitHubにpushしたら自動でチェックが走るGitHub Actionsのワークフローを1本作らせてみる

## 10. ハンズオン⑦ レビュー・改善（20分）

動いたら終わりではありません。**その先の品質を、Claudeに点検・改善させます。**

### やらせること

前半5で作ったSecurity Review Skillがあれば、ここで実戦投入します。無ければ、そのままプロンプトで代用して構いません（コピペ用テンプレ: [templates/verify-prompt.md](../templates/verify-prompt.md)）。

```text
実装したコードをレビューしてください。次を確認し、見つかった問題は直してください。
1. 簡単なテスト（動作確認できる範囲でよい）
2. セキュリティ上の問題（秘密情報の直書き、入力の未検証な使用など）
3. 読みにくい・重複しているコードのリファクタリング
4. 改善したほうがよい点の提案
5. 今日時間切れで残った場合、次に実装すべきことのリスト
```

5番で出てきたものは、`TASKS.md` に残させます。ここも手で書かず、続けてこう頼んでください。

```text
5で挙げた「次に実装すべきこと」を、TASKS.md の「今回やらないこと」に書き足してください。
```

今日の続きは、そこから始められます。

> **「できました」を鵜呑みにしない。** Claudeは実際には確認せず「できています」と答えてしまうことがあります。最後は必ず**あなたの目**で動作を確認してください。あなたの確認が最終権限です。

### ✅ チェックポイント7（完成判定）

- [ ] 主要な機能が自分の目で動くことを確認した
- [ ] レビューで見つかった問題に一通り目を通した（すべて直せていなくてもよい）
- [ ] `TASKS.md` に、次にやるべきことが残っている

3つチェックが付いたら、それが今日の「完成」の定義です。

## 11. 成果共有（7分）

3〜4名にデモしてもらいます。見どころは作品そのものより**プロセス**です。発表者は次の4点を短く共有してください。

1. 何を作ったか
2. 自作のSkillは、どんな質問を返してきたか
3. どんな指示が効いたか（実際の文言があれば見せる）
4. どこでAIが失敗したか、どう抜けたか

聞く側は「その指示、もらった」と思ったらメモしてください。**完成度を競う場ではなく、それぞれ違うものを同じプロセスで作った、という事実を確認する場です。**

## 12. クロージング（3分）

### 今日やったこと

```
Vibe Coding → Intentの明確化 → Skillによる拡張 → 仕様化 → 計画 → 実装 → Review
```

このハンズオン自体が、この一連の流れを体験する教材でした。前半で「ノリで作れてしまう」体験をし、その後「何を作りたいのかを明確にする」壁にぶつかり、**自分で作ったSkill**でそれを乗り越え、後半でIntentを実際のソフトウェアに変換しました。

**いちばん持ち帰ってほしいのは、Skillに数行足しただけで宿題の持ち物が変わった、という体験です。** 仕組みを設計すると、出てくるものが変わる。今日いじったのは、AIの振る舞いそのものでした。
