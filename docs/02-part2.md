# 後半（2時間45分）自分で定義したIntentを、動いて・公開されたソフトウェアにする

後半のゴール: **宿題で詰めた仕様とやることリストを、「今日やる分」に線を引き、上から順に動かし、レビューを通し、URLで人に見せられる状態にして持ち帰ること。**

## 今日の全体地図

3パート構成の最後です。

```
前半 → 【宿題】 → 後半（今ここ）
```

- **前半（済）**: Vibe Codingを体験し、自分が作りたいものを言葉にし、`tsumetsume`・`ddd`・`tsumete` の3つのSkillを自分で作った
- **宿題（済）**: 自作の `tsumete` に自分のアイデアを問い詰めさせ、**仕様（`README.md`）とやることリスト（`TASKS.md`）**まで具体化した
- **後半（今ここ）**: やることに線を引き、上から順に実装し、レビューを仕組みにし、実際に公開する

前半と宿題の成果が、そのまま後半の入力になります。**宿題が思うように進まなかった人も後半は進められます**（→ 7. 宿題ふりかえり）。

## 7. 宿題ふりかえり（5分）

まず、**宿題で使った `myapp` のフォルダ**をVS Codeで開いてください。メニューの「ファイル」→「フォルダーを開く…」から、**そのフォルダを直接**選びます（`~/github/myapp`。普段の置き場所を使った人はそちらです）。

```
~/github/myapp/   ← ここを開く
├── README.md      宿題で詰めた仕様
├── TASKS.md       宿題で作ったやることリスト
├── CONTEXT.md     用語集（あれば）
└── docs/adr/      決定記録（あれば）
```

開いたら `/usage` で利用枠の残量を、`/status` でいま選んでいるモデルを確認します。**残量が半分を切っている人は挙手してください。** このあと実装（9）に70分使うので、足りないことはここで分かったほうが手当てできます。

そのうえで、宿題の状態を3段階のどれかに位置づけてください。

| 状態 | 手元にあるもの | このあとどうするか |
|---|---|---|
| **揃っている** | `README.md` と `TASKS.md` の両方 | このまま8へ |
| **仕様だけある** | `README.md` はあるが `TASKS.md` が無い | 8の冒頭で `TASKS.md` を作るところから始める（下のプロンプト） |
| **そもそも決まっていない** | 宿題に着手できなかった | 挙手してください。前半2〜3で作ったものを種に、メンターと一緒に急いで固めます |

`TASKS.md` が無い人は、8の冒頭でこれを貼ってください。

```text
README.md を読んで、実装する順に「やること」の一覧を TASKS.md に書き出してください。

上から順にやれば、途中で止まっても動くものが残る順番にしてください。
```

**どの状態でも後半は進められます。** 焦って乗り換えず、今持っているものを育てる方向で進んでください。

## 8. ハンズオン⑤ 今日やる分に線を引く（15分）

宿題で詰めた人ほど、`TASKS.md` のやることは多くなっているはずです。**それは正しい状態です。** 減らす必要はありません。ここでやるのは、**今日触る分と、持ち帰る分に線を引くこと**だけです。

### なぜ線を引くのか

実装は70分です。やることが10個あれば1つ7分。**丁寧に詰めた人ほど1つあたりの時間が短くなって終わらない**——これを防ぎます。

### ステップ1: 粒度を揃える（5分）

まず、大きすぎるものを割ります。

```text
TASKS.md を読んで、次を指摘してください。
- 15分では終わらなさそうな大きさのもの
- 「画面のどこを見れば終わったと分かるか」が書かれていないもの
- 順番を入れ替えたほうが、途中で止まっても動くものが残るもの

指摘だけしてください。まだ直さないでください。
```

指摘を**自分の言葉で読み**、納得したものだけ反映させます。全部を鵜呑みにする必要はありません。

```text
1と3を反映してください。2は今日は対象外にします。
```

### ステップ2: 今日やる4つを選ぶ（10分）

ここが後半の勝負どころです。

```text
TASKS.md のやることを、今日やる4つと、持ち帰る分に分けてください。

今日の4つは、それだけで「動くものが1本通る」組み合わせにしてください。
残りは TASKS.md の「今回やらないこと」に移し、なぜ今日やらないかを一行ずつ書いてください。
```

**「上から4つ」ではなく「動くものが1本通る4つ」**が肝心です。入力・処理・表示が揃わないと画面が動きません。印刷や見た目の仕上げは自然に後ろへ落ちます。

出てきた4つを見て、**自分で納得できなければ入れ替えてください。** 決めるのはあなたです。

> **4つが多い・少ないと感じたら調整して構いません。** 迷ったら**減らす**ほうに倒してください。3つ動いて終わるほうが、5つ中途半端より確実に良い一日になります。

> **「今回やらないこと」は捨て場所ではありません。** ここに書いたものが、12でそのままNotionのページやBacklogの課題になり、明日からの続きになります。**理由を一行書いておくと、明日の自分が判断をやり直さずに済みます。**

## 9. ハンズオン⑥ 実装（70分・メイン）

ここが後半の中心です。**全員同じアプリを作るのではなく、同じプロセスを使ってそれぞれ違うものを作ります。**

> **この70分、あなたはファイルを一度も自分の手で編集しません。** コードも `TASKS.md` も、書き換えるのはすべてClaude Codeです。あなたの仕事は**指示を出す・画面を見る・目印で判定する**の3つだけ。手で直したくなったら、それは指示で伝えるべきことです。

### まず、実装の進め方をスキルに任せる（5分）

前半4では「詰めるスキル」を自分で作りました。**後半で使うのは、実装の進め方そのものをスキルにしたもの**です。完成例が [skills/tdd/SKILL.md](../skills/tdd/SKILL.md) にあります。前半のGrill Me系Skillと違い、**これは自分で書かず、コピーして使って構いません。**

```text
skills/tdd/SKILL.md の内容を、
~/.claude/skills/tdd/SKILL.md として保存してください。
フォルダが無ければ作ってください。
```

保存できたら `/clear` で会話を切ってください。**スキルは新しい会話から読み込まれます。**

> **なぜスキルにするのか。** この70分で、あなたは同じ4ステップを4〜5周します。**毎回同じことを言う代わりに、一度ファイルに書いておく**——前半4でやったことと、まったく同じ理由です。今日はそれを、対話の作法ではなく**開発工程そのもの**に対してやっています。

### この70分の回し方

**`TASKS.md` を中心に置いた4ステップを、15分ごとに1周させます。** 何をやっているか分からなくなったら、いつでもこの図に戻ってください。

```
   ┌──────────────────────────────────────────┐
   │  TASKS.md（司令塔・常に最新）              │
   └──────────────────────────────────────────┘
        ↓ ①上から1つ取る          ↑ ④終わった分を反映させる
   ┌─────────────┐          ┌─────────────┐
   │ ②最小の形で実装させる │ ──────→ │ ③目印を自分の目で確認 │
   └─────────────┘          └─────────────┘
                                      ↓ OKなら コミット＋プッシュ
```

回し始めるのに必要なのは、この一言だけです。

```text
TASKS.md の次のやることを実装してください。
```

`tdd` スキルが起動すると、**いきなりコードを書き始めず、まず「終わったと分かる目印」を読み上げて確認**してきます。**そこが出発点です。** 目印が書かれていないやることは、ここで目印を決めるところから始まります。

#### このスキルが守っている3つ

| ルール | なぜ |
|---|---|
| **1回に1件だけ** | まとめて実装すると、動かなかったときにどれが原因か分からない |
| **目印は「画面で見えること」だけ** | 「関数が正しく実装されている」は目印になりません。**あなたが操作して確認できること**だけです |
| **「終わった」と決めるのは、あなた** | Claudeが自分の実装を自分で確かめても、何も確かめたことになりません |

3つ目がいちばん大事です。**Claudeが「できました」と言っても、それは終わったという意味ではありません。** あなたがブラウザで目印を見て、初めて終わります。スキルはそこで**確認を求めて止まる**ように書いてあります。

#### 15分ごとのチェックポイント運用

講師の合図（または自分のタイマー）で、次を実行してください。

まず、**`TASKS.md` に書いた「終わったと分かる目印」を、自分の目で確認します。**

| 目印の確認 | どうするか |
|---|---|
| **OK** | **コミットしてプッシュする**（下のプロンプト） |
| **NG** | 前半で覚えた**リカバリー3手**（貼る・戻す・小さくする）で動く状態に戻してから、あらためて確認 |

目印がOKなら、そのまま頼んでください。**gitが分からなくても構いません。**

```text
目印を確認できました。いまの状態をコミットして、プッシュしてください。
```

**確認できたものだけを残していく**——これが今日の保存の作法です。動いていないものはコミットしません。

> プッシュ先は**ハンズオン②で作った `myapp`（自分だけのリポジトリ）**です。ほかの参加者と衝突することはないので、遠慮なく何度でもプッシュしてください。

#### スキルが呼ばれないときは

前半3で体験したとおり、**スキルを使うかどうかは最終的にClaudeが判断します。** 目印の確認を飛ばしていきなりコードを書き始めたら、4ステップを手で指示してください。**結果は同じです**（コピペ用テンプレ: [templates/first-instruction.md](../templates/first-instruction.md)）。

```text
TASKS.md の1つ目だけを、最小の形で実装してください。
他のものにはまだ手をつけないでください。
```

```text
いま終わった分を、TASKS.md の状態に反映してください。
```

**どこまで来たかが常にファイルに残っている**のが、この70分の正しい進み方です。

> **この70分の間は、セキュリティレビューのHookはまだ入れません。** 15分ごとのプッシュが止まってしまうからです。**先に作りきり、10でレビューを仕組みにしてから、11で外に出す**——この順番自体が今日の設計です。

> **`tdd` はリファクタリングをしません。** 読みにくいコードや重複は、この70分では放置して構いません。**整えるのは動いたあと**——10の `code-review` の仕事です。工程を分けているのは、**同時にやると片方が雑になる**からです。

### 詰まったときのエスカレーション順

1. リカバリー3手（貼る・戻す・小さくする）— まず自分で2回試す
2. `/model` で重いモデルに切り替えて、同じことをもう一度頼む
3. 挙手 → メンターが巡回します
4. それでも詰まったら、やることを削ってでも「動く状態」を優先する。**完成度より、確認できる状態を保つことが優先です**

### よくある状況と対処

| 状況 | 対処 |
|---|---|
| 最初の1つが15分経っても動かない | 大きすぎるサイン。メンターと一緒にさらに小さく割る |
| 予定より早く4つとも終わった | 「今回やらないこと」から1つ戻して、同じ型でもう一周する |
| 途中でもっと良いアイデアを思いついた | **今日は乗り換えない。** 「思いついたことを TASKS.md の『今回やらないこと』に書き足して」と頼んで持ち帰る |
| 利用枠の上限に当たった | 挙手 → メンター機でペア作業に切り替え |

## 10. ハンズオン⑦ レビューを仕組みにする（30分）

動いたら終わりではありません。**この直後、11で本当に外へ公開します。** 公開してしまってからでは取り返しがつかないものがあるので、**出す前に必ずレビューが通っている状態**をここで作ります。

前半5で触れた「Skillは判断を介する、Hooksは条件が合えば確実に動く」を、ここで実戦投入します。

### 「レビューして」は、1つの質問ではありません

一言で「レビューして」と頼むと、返ってくる指摘は全部混ざります。**混ざったリストは、どれが重いのか分からなくなります。** ここでは**3つの別々の質問**として扱います。

| 質問 | 担当 |
|---|---|
| **頼んだものを作ったか**（仕様どおりか） | `code-review` の Spec 軸 |
| **まともな書き方をしているか**（作法どおりか） | `code-review` の Standards 軸 |
| **危ないところは無いか** | `security-review` |

上2つを分ける理由は、**片方が片方を隠すから**です。

- **作法は完璧だが、違うものを作っている** → 作法だけ見ていたら合格に見える
- **頼まれたとおりだが、書き方が散らかっている** → 仕様だけ見ていたら合格に見える

この2つはまったく別の状態です。1本のリストにまとめると、見えなくなります。

### ① レビュースキルを2枚用意する（6分）

完成例が [skills/code-review/SKILL.md](../skills/code-review/SKILL.md) と [skills/security-review/SKILL.md](../skills/security-review/SKILL.md) にあります。**どちらも自分で書かず、コピーして使って構いません。**

```text
skills/code-review/SKILL.md と skills/security-review/SKILL.md の内容を、
それぞれ ~/.claude/skills/code-review/SKILL.md と
~/.claude/skills/security-review/SKILL.md として保存してください。
フォルダが無ければ作ってください。

保存したら、security-review のほうの最後に次の2つを足してください。
1. 観点として「公開するフォルダの中に、公開してよいものだけが入っているか」を追加する
   （メモ書き・実在の個人名・設定ファイル・鍵などが混ざっていないか）
2. 「レビューが終わったら .claude/security-reviewed というファイルを作成（touch）すること」
```

2つ目の一行が、このあと④のHookの土台になります。**「レビューが済んだ」という事実を、Claudeの記憶ではなくファイルとして残す**ための印です。

保存できたら `/clear` で会話を切ってください。

> **印を作るのは `security-review` だけです。** `code-review` はこの印に触りません。**外に出してよい条件は「危なくないこと」であって、「作法が綺麗なこと」ではない**——この線引きを、スキルの分担そのもので表しています。

### ② 2軸でレビューして、直す（12分）

```text
コードレビューして
```

**仕様どおりか**と**作法どおりか**が、**別々の見出しで並んで**返ってくるはずです。1本のリストになっていたら、「2つの軸に分けて」と言い直してください。

> **Spec軸が読むのは、宿題であなたが書いた `README.md` です。** ここが今日の隠れた山場かもしれません。**自分で書いた仕様が、人に読まれるだけの文章ではなく、機械がレビューに使う入力として実際に働きます。** 「使いやすく」「いい感じに」を残さずに書いた宿題が、ここで効きます。逆に曖昧なままだと、この軸は何も言えません。

出てきた指摘を**自分の言葉で読み**、直すものを選んでください。**全部直す必要はありません。**

```text
仕様の1と2、作法の1を直してください。残りは今日は対象外にします。
```

> **「今回やらないこと」に書いたものが実装されていたら、それは重い指摘です。** 動くから良い、ではありません。**決めたことと違うものができている**というサインなので、直すか、決定のほうを更新するか、どちらかを選んでください。

直さなかったものは、持ち帰りに回します。

```text
直さなかった指摘を、TASKS.md の「今回やらないこと」に書き足してください。
```

**司令塔は最後まで `TASKS.md` です。** レビューで出た宿題も、ここに集約させます。

### ③ セキュリティレビューを通す（4分）

**必ずこの順番です。** ②で直したことが、危なさの状態を変えている可能性があるからです。

```text
セキュリティレビューして
```

秘密情報の直書き・入力の未検証な使用などを、重大度つきで報告してくるはずです。見つかった問題は指示して直させてください（コピペ用テンプレ: [templates/verify-prompt.md](../templates/verify-prompt.md)。Skillが呼ばれないときはこちらで代用しても構いません）。

**直したあとは、もう一度セキュリティレビューを通してください。** 直したことで、危なさの状態がまた変わっているからです。**この「直したら通し直す」を、次の④で仕組みにします。**

> **「できました」を鵜呑みにしない。** Claudeは実際には確認せず「できています」と答えてしまうことがあります。最後は必ず**あなたの目**で動作を確認してください。あなたの確認が最終権限です。

### ④ Hookで「必ず実行される」に変える（8分）

ここまでは、**あなたが呼んだからレビューが走りました。** 呼ぶのを忘れたら実行されません。そして忘れやすいのは、まさに急いでいるとき——**公開する直前**です。

そこで、Hookを2つ設定します。**「レビュー済みの印」を軸にした、たった2行の仕組み**です。

| Hook | タイミング | やること | 意味 |
|---|---|---|---|
| **A** | コードを編集した直後（PostToolUse / Edit・Write） | レビュー済みの印を消す | 変更したらレビューはやり直し |
| **B** | 外に出す直前（PreToolUse / Bash で `git push` や `wrangler deploy`） | 印が無ければ止める | 未レビューのものは外に出せない |

**AとBが揃うと、「最後に触ったコードは必ずレビューを通っている」が保証されます。** 片方だけでは、一度レビューを通した後にいくら書き換えても素通りしてしまいます。

```text
このプロジェクトの .claude/settings.json に、次の2つのHookを設定してください。

【Hook A】
- タイミング: ファイルを編集・作成した直後（PostToolUse、対象はEditとWrite）
- 内容: .claude/security-reviewed というファイルがあれば削除する

【Hook B】
- タイミング: Bashコマンドの実行直前（PreToolUse、対象はBash）
- 内容: 実行されようとしているコマンドに "git push" または "wrangler deploy" が
  含まれていて、かつ .claude/security-reviewed が無い場合は、そのコマンドを止めて
  「先に『セキュリティレビューして』を実行してください」という理由を返す
- 判定の中身は .claude/hooks/require-security-review.sh というシェルスクリプトに書き、
  settings.json からはそれを呼ぶ形にしてください（あとで自分で読めるようにするため）

あわせて .gitignore に .claude/security-reviewed を追加してください。
settings.json や必要なフォルダが無ければ作成してください。
```

> **スクリプトの中身を一度は自分の目で見てください。** Hooksは権限プロンプトを経由せず自動実行されます（前半5）。**中身を理解できるものだけを登録する**、が原則です。20行程度のはずなので、読めなければ「このスクリプトを1行ずつ日本語で説明して」と頼んでください。

#### 止まることを自分の目で確認する

設定できたら `/clear` で会話を切り、**わざと未レビューの状態を作って試します。**

1. アプリのファイルを何か1つ編集させる（色を変える、など何でもよい）→ **Hook Aが印を消します**
2. そのままプッシュを頼む → **Hook Bが止めるはずです**

```text
いまの状態をコミットして、プッシュしてください。
```

3. 止められたら、あらためて `セキュリティレビューして` を実行する → 印が作られます
4. もう一度プッシュを頼む → **今度は通ります**

**Skillは「呼べば動く」、Hookは「呼ばなくても止めてくれる」**——この違いを、止まる瞬間として自分の目で確認してください。ここが前半5の回収点です。

> **止まらないときは** `/hooks` で2つとも登録されているか確認してください。入っているのに動かない場合は、Claude Codeを一度終了して開き直してから再確認します。**それでも直らなければ、Hookは一旦諦めて①〜③のレビューだけで11へ進んでください。** 今日の完成判定には影響しません。

- [ ] セキュリティレビューを通し、見つかった問題に一通り目を通した（すべて直せていなくてもよい）

## 11. ハンズオン⑧ Cloudflareに公開する（20分）

ここまで作ったものは、**あなたのPCの中にしかありません。** ファイルを開けば動きますが、隣の人に見せるには画面を覗いてもらうしかない。ここでそれを、**URLを送れば誰でも見られる状態**にします。

### なぜCloudflareなのか

今日のアプリは**ブラウザだけで動く静的なもの**（HTML・CSS・JavaScript）です。サーバー側で動く処理もデータベースもありません。この形は**静的ホスティング**という一番シンプルな置き方で公開でき、Cloudflareはそれを**無料枠で・世界中に配信される形で**提供しています。

> **Cloudflareの中でも今の本流は「Workers」です。** 以前は静的サイト向けに「Pages」という別サービスがありましたが、Cloudflareは現在**Workers側に機能投資を集約し、新規は Workers から始めることを推奨**しています（Pagesも引き続き利用可能です）。この教材もWorkers側の手順で書いています。

### ステップ1: 公開するフォルダを分ける（全員・5分）

**いま `myapp` フォルダには、公開したくないものが混ざっています。** `README.md`（仕様）、`TASKS.md`（やること）、`CONTEXT.md`、`.claude/`（設定）——これらは**あなたの作業用**であって、世界中に見せるものではありません。

フォルダごと投げると、**それら全部が一緒に公開されます。**

```text
公開用に public/ フォルダを作り、公開してよいファイルだけをそこに移動してください。
- 移動するもの: アプリのHTML・CSS・JavaScript・画像
- 移動しないもの: README.md・TASKS.md・CONTEXT.md・docs/・.claude/・.git/
移動したあと、ブラウザで public/index.html を開いて今までどおり動くことを確認できる状態にしてください。
```

移動できたら、**必ず一度 `public/index.html` をブラウザで開いて動作を確認してください。** ここで壊れていることに気づかずに公開すると、原因の切り分けが難しくなります。

そのうえで、もう一度だけレビューを通します。

```text
セキュリティレビューして。特に public/ に入れたファイルを、
これから全世界に公開してよいかという目で見てください。
```

**「他人に渡して困るものが残っていないか」——これはSkillの最後の観点そのものです。** 実装中は抽象的だったこの問いが、公開する直前にだけ具体的になります。

### ステップ2: 公開する（10分）

**ルートは2つあります。** 自分に合うほうを選んでください。**どちらでも「公開された」という体験は同じです。**

| | ルートA: ドラッグ&ドロップ | ルートB: コマンドで公開 |
|---|---|---|
| 誰向け | **全員（本線）** | Node.jsが入っている人〔Eng〕 |
| 必要なもの | ブラウザだけ | Node.js・Cloudflareアカウント |
| 所要 | 2分 | 5〜10分 |
| Hookは効くか | 効かない（Claude Codeを通らないため） | **効く**（`wrangler deploy` で止まる） |

#### ルートA: Cloudflare Drop にドラッグ&ドロップする（全員・本線）

1. ブラウザで [cloudflare.com/drop](https://cloudflare.com/drop) を開く
2. **ステップ1で作った `public/` フォルダ**を、そのままドラッグ&ドロップする（zipでも可）
3. URLが発行され、その場で公開されます

**アカウントは要りません。** ただし**このURLは1時間で消えます。** 残したい人は、表示されている **Claim** を押してCloudflareアカウントでサインイン（またはその場で無料作成）してください。Claimすると、そのままあなたのアカウントの中に恒久的なサイトとして残ります。

> **1時間で消えることは、今日はむしろ好都合です。** 「とりあえず人に見せる」だけなら消えたほうが後腐れがありません。**続きを作る気がある人だけClaimしてください。**

#### ルートB: `wrangler` で自分のアカウントに公開する〔Eng〕

Claude Codeにそのまま頼めます。

```text
このアプリを Cloudflare Workers の静的アセットとして公開したいです。
1. wrangler.jsonc を作り、assets の directory を ./public/ に向けてください（Worker のスクリプトは不要です）
2. npx wrangler login でログインしてください（ブラウザが開くので私が許可します）
3. npx wrangler deploy で公開し、発行されたURLを教えてください
```

**ここでHook Bに止められるはずです。** 1つ目で `wrangler.jsonc` を作った時点で**ファイルの書き込みが起きるので、Hook Aがレビュー済みの印を消します。** その状態で3つ目のデプロイに進むため、Hook Bが「印が無い」と判定して止める——という流れです。

**これは故障ではありません。** 止まったら、そのまま続けてください。

```text
セキュリティレビューして
```

レビューが通れば印が作り直されるので、もう一度デプロイを頼めば今度は通ります。**「設定を1行でも足したら、外に出す前にもう一度見る」が仕組みとして効いた瞬間**です。面倒に見えますが、止めてほしいのはまさにこういう「あと一歩」の場面です。

できあがる `wrangler.jsonc` はこれだけです。**中身を見て、何を公開しているのかを自分で把握してください。**

```jsonc
{
  "name": "myapp",
  "compatibility_date": "2026-08-29",
  "assets": {
    "directory": "./public/"
  }
}
```

`directory` に書いたフォルダの中身が、そのまま公開されます。**ここが `./` になっていたら、リポジトリ全部が公開されます。** 必ず `./public/` を指していることを確認してください。

> **`npx wrangler login` はブラウザでの許可操作が必要です。** Claude Code側で止まって見えるときは、VS Codeのターミナル（「表示」→「ターミナル」）で自分で `npx wrangler login` を実行してから、あらためてデプロイを頼んでください。

### ステップ3: 自分の目で確認する（5分）

**発行されたURLを、自分のスマートフォンで開いてください。** PCのブラウザではなく、です。

- 意図したものが表示されるか
- 動かしてみて、PCで見たときと同じように動くか
- **見せたくないものが表示されていないか**

確認できたら、**URLを隣の人に送って開いてもらってください。** 他人の環境で開かれて初めて「公開した」ことになります。

最後に、**ここまでの変更を保存します。** `public/` への移動も `wrangler.jsonc` も、まだコミットされていません。

```text
いまの状態をコミットして、プッシュしてください。
公開URLを README.md の先頭に1行追記してからにしてください。
```

**ルートAで公開した人も、ここでHook Bが止めてくるはずです。** レビューを通してからもう一度頼んでください。**「外に出す前に必ず見る」が、pushでもデプロイでも同じように効く**ことを、ここで確認できます。

> **公開したということの意味。** URLを知っている人は誰でも見られます（検索には出にくいですが、秘密ではありません）。**あなたのアプリがブラウザに保存しているデータ（`localStorage` など）は、見る人ごとに別々**で、あなたの手元のデータが相手に見えることはありません。逆に言えば、**あなたが入力したデータは公開されていない**ということです。ここを混同しないでください。

> **宿題の「外部サービス連携なし」と矛盾しないの?** しません。**変わったのはアプリの置き場所だけで、アプリ自体は静的なままです。** ログインも、サーバーへのデータ送信も増えていません。「作ったものをどこに置くか」と「アプリが何とつながるか」は別の話です。

## 12. ハンズオン⑨ 仕事の道具とMCPでつなぐ（15分）

最後に、**「今回やらないこと」を、明日の自分やチームに引き渡します。**

前半2ではGmailとつなぎました。同じ仕組み（MCP）で、仕事で使っているタスク管理ツールにもつなげます。**ここでの目的は「タスク管理をNotionやBacklogに移すこと」ではありません。** 今日の司令塔は最後まで `TASKS.md` です。やるのは**出口を1本つけること**——手元のファイルに溜まった持ち帰り分を、明日開く場所へ流し込むところまでです。

### つなぐ（8分）

**どちらか片方で構いません。** 迷ったらNotionです。

#### Notion — ネイティブ統合あり、つなぐだけ

前半2のGmailと同じ手順です。

1. ブラウザで [claude.ai](https://claude.ai) を開く
2. 左側メニューの「**カスタマイズ**」→「**コネクタ**」を開く
3. 一覧から **Notion** を探して「接続」を押す
4. Notionアカウントでログインし、許可画面の内容を確認して許可する

難しい設定は不要です。**個人のNotionを使いたくない人は、この場では接続せず手順を見るだけで構いません。**

#### Backlog — ネイティブ統合なし、自分でMCPサーバーを設定する

Backlogはclaude.aiのコネクタ一覧にはありません。**自分でMCPサーバーを追加**します。

> **このルートにはNode.jsが必要です**（MCPサーバーを `npx` で起動するため）。ターミナルで `node -v` を実行してバージョンが出ない人は、**Notion側を選んでください。** Windowsの人は事前準備で入れているので使えます。

Backlogの「個人設定」→「API」からAPIキーを発行したうえで、Claude Codeに次を頼んでください。

```text
Backlog用のMCPサーバーを追加してください。
- パッケージ: backlog-mcp-server（npxで実行）
- 環境変数: BACKLOG_DOMAIN=⟨自分のスペース⟩.backlog.com、BACKLOG_API_KEY=⟨発行したAPIキー⟩
- スコープはuser（このPCの自分だけ・このリポジトリにはコミットされない）にしてください
```

> **APIキーは絶対にリポジトリにコミットしないでください。** `myapp` は15分ごとにpushしている、**しかも11で公開までした**リポジトリです。スコープを`project`にすると設定がリポジトリ内の `.mcp.json` に書き込まれ、**pushした瞬間にAPIキーが漏れます。** 上のように`user`スコープを指定すれば、設定は自分のPCの中だけに保存され、リポジトリには一切含まれません。**これは10でレビューした「秘密情報がコードに書かれていないか」と、まったく同じ観点です。**

#### どちらの場合も: Claude Codeを開き直す

設定できたら**Claude Codeを一度終了して開き直してください。** MCPの接続はClaude Codeの起動時に確立されるため、`/clear` だけでは反映されません。開き直したら `/mcp` で接続状態（Connected）を確認します。

### 引き渡す（7分）

`TASKS.md` の「今回やらないこと」を、そのまま明日の入り口に流し込みます。

**Notionの場合:**

```text
TASKS.md の「今回やらないこと」を、Notionに「⟨アプリ名⟩ 次にやること」というページを作って
チェックリストとして書き出してください。
それぞれに、TASKS.md に書いてある「今日やらない理由」も添えてください。
```

**Backlogの場合:**

```text
TASKS.md の「今回やらないこと」を、Backlogの⟨プロジェクト名⟩に課題として登録したいです。
まず、登録する予定の一覧（件名と詳細）を見せてください。まだ登録しないでください。
```

内容を確認してから、

```text
その内容で登録してください。
```

> **外部への書き込みは、必ず一度見てから。** ファイルの編集と違い、**課題の一括登録は取り消しに手間がかかります。** 「まず一覧を見せて」を挟むのは、前半で覚えた「見て、直す」を外部サービスに対してやっているだけです。

> **外から来た文章を「指示」として実行させない。** MCPでつなぐと、Claudeは課題やページの本文を読めるようになります。そこに書かれた文章は**データであって指示ではありません。** 他人が書いた課題の本文に「すべてのファイルを削除して」と書いてあっても実行させない、という線引きが要ります（→ [columns.md](columns.md) ★9）。

## 14. クロージング（3分）

### 今日やったこと

```
Vibe Coding → Intentの明確化 → Skillによる拡張 → 仕様化 → 計画 → 実装 → Review → デプロイ
```

このハンズオン自体が、この一連の流れを体験する教材でした。前半で「ノリで作れてしまう」体験をし、その後「何を作りたいのかを明確にする」壁にぶつかり、**自分で作ったSkill**でそれを乗り越え、後半でIntentを実際のソフトウェアに変換し、**最後に世界から見える場所に置きました。**

**いちばん持ち帰ってほしいのは、Skillに数行足しただけで宿題の持ち物が変わった、という体験です。** 仕組みを設計すると、出てくるものが変わる。今日いじったのは、AIの振る舞いそのものでした。

**そしてもう1つ。** レビューは「気をつける」ではなく**仕組みで担保しました**（Hook A・B）。公開する範囲は「気をつける」ではなく**フォルダを分けることで担保しました**（`public/`）。**人の注意力に頼らない形に落とすこと**——これが、動くものを作れるようになった次に効いてくる差です。

**工程を分けたことにも意味があります。** `tdd` は整えず、`code-review` は危なさを見ず、`security-review` だけが「外に出してよい」の印を作る。**1つのスキルに全部を入れると、報告が混ざって何も見えなくなります。** 小さく分けて、噛み合わせる——今日いじったのはAIの振る舞いであると同時に、**工程の設計**でした。
