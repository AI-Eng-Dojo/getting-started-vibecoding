## 7. 宿題ふりかえり（5分）

まず、宿題で使った `myapp` のフォルダをVS Codeで開いてください。メニューの「ファイル」→「フォルダーを開く…」から選びます（`~/github/myapp`。普段の置き場所を使っている人はそちら）。

```
~/github/myapp/   ← これを開く
├── README.md      宿題で詰めた仕様
├── TASKS.md       宿題で作ったやることリスト
├── CONTEXT.md     用語集（あれば）
└── docs/adr/      決定記録（あれば）
```

次に `/usage` で利用枠の残量を、`/status` でいま選んでいるモデルを確認します。**残量が半分を切っている人は、プランのアップグレードか軽量なモデルを利用してください。**

そのうえで、宿題がどこまでできているか確認してください。

| 手元にあるもの | このあとどうするか |
|---|---|
| `README.md` と `TASKS.md` の両方が揃っている | このまま8へ |
| `README.md` はあるが `TASKS.md` が無い | `TASKS.md` を作る（下のプロンプト） |
| どちらも無い（宿題に着手できなかった） | 下の「宿題に着手できなかった人向け」の見本を使う |

`TASKS.md` がまだ無い人は、以下のようにして作成してください。

```text
README.md を読んで、実装する順に「やること」の一覧を TASKS.md に書き出してください。
1つは15分以内で終わる大きさにし、それぞれに完了定義（画面のどこを見れば終わったと分かるか）を書いてください。
上から順にやれば、途中で止まっても動くものが残る順番にしてください。
```

### 宿題に着手できなかった人向け

`README.md` と `TASKS.md` がどちらも無い人は、題材「習慣トラッカー」のサンプルを利用します。

```text
次の2つのURLの中身を、このフォルダの README.md と TASKS.md として保存してください。
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/starters/c-habit-tracker/homework/README.md
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/starters/c-habit-tracker/homework/TASKS.md

いまある README.md は上書きせず、同じ場所に README-myidea.md という名前で退避して残してください。
```

前半3で書いた自分のREADMEは `README-myidea.md` として残ります。今日は使わなくても、持ち帰って再開できます。

## 8. ハンズオン⑤ MVPを決める（15分）

宿題で詰めた人ほど、`TASKS.md` のタスクが多くなっているはずです。減らす必要はありません。ここで今日やる分を決めましょう。可能な限り、アプリとして価値の高い最低限の実装（MVP）に収めます。

### ステップ1: 粒度を揃える（5分）

まず、大きすぎるタスクがあれば分割します。

```text
TASKS.md を読んで、次を指摘してください。
- 15分では終わらなさそうな大きさのタスク
- 完了定義（画面のどこを見れば終わったと分かるか）が書かれていないタスク

指摘だけしてください。まだ直さないでください。
```

指摘を確認し、納得したものだけ反映させます。

```text
1と3を反映してください。2は今日は対象外にします。
```

### ステップ2: MVPに絞り込む（10分）

今日実装するのは、アプリとして価値がいちばん高い部分だけです。それが動けば「このアプリは何をするものか」が画面で伝わる。その最小の組み合わせがMVPです。

```text
TASKS.md のやることを、MVP（今日やる分）と持ち帰る分に分けてください。

MVPの条件は次の2つです。
- それだけで「このアプリが何をするものか」が画面で伝わること
- 入力・処理・表示がつながって、動くものが1本通ること

MVPに入らないものは TASKS.md の「持ち帰る分」という見出しにまとめてください。
完了定義は消さずに残したまま、今日やらない理由を一行ずつ書き足してください。

「今回やらないこと」（詰めるときに今回のスコープから外すと決めたもの）は、
別の見出しのままにしてください。README.md にしか書かれていない場合は、
理由ごと TASKS.md にも同じ見出しで写してください。
```

実装は70分、タスク1つは15分以内。入りきらないなら、MVPでない可能性があります。

> **迷ったら、いったん減らしてください。** 中途半端に多く作るより、少なくても動くものになっているほうが良いです。削った分は後日対応してください。

> **見出しを2つに分けるのはなぜか。** 中身の性質が違うからです。
>
> | 見出し | 何が入るか | 明日どうするか |
> |---|---|---|
> | **持ち帰る分** | やることとして書き出したが、今日の時間に入らなかったもの | 完了定義があるので、そのまま次の1つとして始められる |
> | **今回やらないこと** | 詰めるときに今回のスコープから外すと決めたもの | 戻すなら仕様（`README.md`）から変える |
>
> 混ぜると、決めたはずのことが「あとで戻す候補」に並びます。**どちらも12でNotionのページやBacklogの課題になる**ので、今日やらない理由はどちらにも一行書いてください。

### ✅ チェックポイント5

- [ ] `TASKS.md` の今日やる分がMVP分に絞られている
- [ ] 入力・処理・表示の処理がつながっていて、動くものができるタスク一覧になっている
- [ ] MVP構築は70分に収まる分量である
- [ ] それぞれに完了定義（画面のどこを見れば終わったと分かるか）が書いてある
- [ ] **「持ち帰る分」に、完了定義と「今日やらない理由」がそろって残っている**（全部MVPに入ったなら空で構いません）
- [ ] 今回のスコープから外したものが、「今回やらないこと」に理由つきで残っている
- [ ] **最初の1つが何かがはっきりしている**

## 9. ハンズオン⑥ 実装（70分）

> **この実装工程において、あなたはファイルを一度も自分の手で編集しません。** コードも `TASKS.md` も、書き換えるのはすべてClaude Codeです。「自分でやったほうが早い」と感じる瞬間もありますが、自分の手で直してしまうとAIの編集履歴に残らないので、徹底してください。

### まず、実装の進め方をスキルに任せる（5分）

前半4では「詰めるスキル」を自分で作りました。後半で使うのは、実装の進め方そのものをスキルにしたものです。完成例が [skills/tdd/SKILL.md](../skills/tdd/SKILL.md) にあります。前半のGrill Me系Skillと違い、これは自分で書かず、コピーして使って構いません。

```text
次のURLの中身を、~/.claude/skills/tdd/SKILL.md として保存してください。
フォルダが無ければ作ってください。

https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/skills/tdd/SKILL.md
```

> 教材リポジトリはcloneしていないので、URLで渡します。取得の許可を聞かれたら許可してください。取得できなかった場合は、上のURLをブラウザで開いて全文をコピーし、Claude Codeに貼って「これを `~/.claude/skills/tdd/SKILL.md` として保存して」と頼めば同じことができます。

保存できたら `/clear` で会話を切ってください。

> **なぜスキルにするのか。** この70分で、あなたは同じ4ステップを4〜5周します。毎回同じことを言う代わりに、一度ファイルに書いておく。前半4でやったことと、まったく同じ理由です。今日はそれを、対話の作法ではなく開発工程そのものに対してやっています。

### 実装の進めかた

`TASKS.md` を中心に、1タスクずつ処理させます。回し始めるのに必要なのは、この一言だけです。

```text
TASKS.md の次のやることを実装してください。
```

`tdd` スキルが起動すると、いきなりコードを書き始めず、まず**完了定義**を読み上げて確認してきます。完了定義がまだ書かれていない場合は、そこを決めるところから始めましょう。

#### このスキルのルール

| ルール | なぜ |
|---|---|
| **1回に1件だけ** | まとめて実装すると、動かなかったときにどれが原因か分からないため |
| **完了定義は「画面で判断できる基準」** | たとえば「関数が正しく実装されている」は完了定義になりません。 |
| **「完了」と判断するのは、ユーザー** | Claudeが自分の実装を自分で確かめても、何も確かめたことになりません |

#### コミット＆プッシュ

完了判断がOKなら、以下のように頼んでください。gitが分からなくても構いません。

```text
完了定義を確認できました。いまの状態をコミットして、プッシュしてください。
```

#### スキルが呼ばれないときは

前半5で見たとおり、スキルを使うかどうかは最終的にClaudeが判断します。完了定義の確認を飛ばしていきなりコードを書き始めたら、止めてください

```text
TASKS.md の1つ目だけを、最小の形で実装してください。
他のものにはまだ手をつけないでください。
```

```text
いま終わった分を、TASKS.md の状態に反映してください。
```

**どこまで来たかを常にファイルに残しておくことで**、いつでも安全に途中から再開できます。

### よくある状況と対処

| 状況 | 対処 |
|---|---|
| 最初の1つが15分経っても動かない | 大きすぎるサイン。メンターと一緒にさらに小さく割る |
| 予定より早くMVPが動いた | 「持ち帰る分」から1つ戻して、同じ型でもう一周する |
| 途中でもっと良いアイデアを思いついた | **今日は乗り換えない。** 「思いついたことを TASKS.md の『持ち帰る分』に書き足して」と頼んで持ち帰る |
| 利用枠の上限に当たった | 挙手 → メンター機でペア作業に切り替え |
| `CONTEXT.md` と違う言葉で実装されている | 「`CONTEXT.md` の用語に合わせて」と伝える。宿題で用語集を作った人はここで効きます |
| どの案でいくか決められなくて止まっている | **本実装を続けない。** `prototype` スキル（拡張ミッション③）で、捨てる前提の小さいものを作って決める |
| どうしても `myapp` が動く形にならない | リカバリー3手で、最後に動いていた状態まで戻してください。今日やると決めた分のうち、動いたところまでで構いません。**動かないものは直すのではなく削ります。** 10以降は「動いているものをレビューして、公開して、引き渡す」工程なので、動く画面が1つあれば全部通ります |

### ✅ チェックポイント6

今日やると決めたMVPのうち、**主要なものが動いている**状態で10へ。

### 🚀 拡張ミッション③（早く終わった人向け・任意）

- 〔共通〕**「持ち帰る分」から1つ戻す**: 今日の型（最小実装 → 完了定義で確認 → 保存）でもう一周する。完了定義が書いてあるので、そのまま次の1つとして始められます。**「今回やらないこと」からは戻しません。** そちらを戻すのは、仕様を変えることだからです
- 〔Eng〕**ブランチを切ってPRを出し、レビューをもらう**: 本線では main にそのままコミットしていますが、実務ではブランチを切り、プルリクエスト（PR）にして他の人の目を通します。ここもClaude Codeに頼めます

    ```text
    このやることの分をブランチに切ってコミットし、プッシュして、プルリクエストを作ってください。
    PRの説明には、何を変えたかと、どこを見れば動作を確認できるかを書いてください。
    ```

    PRの向き先は自分の `myapp` の中（`main` ← 作業ブランチ）です。**`myapp` は非公開なので、URLを渡しただけでは相手から見えません。** 隣の人に見てもらうには、次のどちらかを先にやります。

    | やり方 | どうするか | 向いている場面 |
    |---|---|---|
    | **相手を1人だけ招く**（推奨） | GitHubの `myapp` → Settings → Collaborators → 隣の人のアカウントを追加 | 中身を不特定多数に晒さずに済みます |
    | 公開に切り替える | Settings → General → 一番下の Danger Zone → Change visibility → Public | 中身を見られて困らないと自分で判断できるとき |

    PRができたらURLを隣の人に渡し、レビューしてもらってください。見る側は「どこを見れば動くと分かるか」がPRに書かれているかを確認します。**「完了定義を書く」という今日の作法が、そのままレビュー可能性になります。**
- 〔Eng〕**完了定義を渡して任せてみる**: `TASKS.md` の1つを、その完了定義ごと `/goal` に渡し、満たすまで自走させてみる。これが「任せきる」の入口です（→ [columns.md](columns.md) ★7）
- 〔共通〕**`prototype` で迷いを潰す**: 決められない設計や「この動きで合っているか分からない」を、捨てる前提の小さい試作で判断します。完成例が [skills/prototype/SKILL.md](../skills/prototype/SKILL.md) にあります

    ```text
    次のURLの中身を、~/.claude/skills/prototype/SKILL.md として保存してください。

    https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/skills/prototype/SKILL.md
    ```

    保存して `/clear` したら、迷っているところをそのまま伝えてください（「一覧の並び順を新しい順にするか、期限が近い順にするか決められない」など）。両方を1画面で切り替えられる試作が出てきます。決まったら試作は捨て、決めたことだけを `CONTEXT.md` に残します。**本実装させる前に、判断材料を先に作る。** これが今日の型のもう一段上です
- 〔Eng〕**11の前に、自分で構成を設計してみる**: 「このアプリをどこで動かし、データはどこに置くべきか」をClaudeに設計させ、選択理由を説明させてください。11でCloudflareに出す手順と答え合わせできます。なぜ静的ホスティングで足りるのか、どこから先はサーバーが要るのかを、自分の言葉で言えるようになるのが狙いです

## 10. ハンズオン⑦ レビューを仕組みにする（37分）

この直後、11でここまでできたものをインターネットに公開します。公開した後では取り返しがつかないものがあるので、**デプロイする前に必ずコードレビューとセキュリティレビューが通っている状態**にするためにスキルを追加します。

前半5で触れた「Skillは判断を介する、Hooksは条件が合えば確実に動く」を、ここで実戦投入します。

### レビュー内容

| レビュー観点 | スキル名 |
|---|---|
| **仕様どおりに作ったか** | `code-review` (Spec 軸) |
| **作法どおりの書きかたで書かれているか** | `code-review` (Standards 軸) |
| **セキュリティ的に危ないところは無いか** | `security-review` |

### ① コードレビュースキルとセキュリティレビュースキルを用意する（6分）

完成例が [skills/code-review/SKILL.md](../skills/code-review/SKILL.md) と [skills/security-review/SKILL.md](../skills/security-review/SKILL.md) にあります。どちらも自分で書かず、コピーして使って構いません。

```text
次の2つのURLの中身を、それぞれ
~/.claude/skills/code-review/SKILL.md と
~/.claude/skills/security-review/SKILL.md として保存してください。
フォルダが無ければ作ってください。

https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/skills/code-review/SKILL.md
https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/skills/security-review/SKILL.md
```

保存できたら `/clear` で会話を切ってください。

`security-review` の末尾には、「レビューが終わったら `.claude/security-reviewed` という空ファイルを作る」という一行が入っています。**「外に出してよい」という判断を、Claudeの記憶ではなくファイルとして残す**ための完了チェックで、これが④のHookの土台になります。一度自分の目で見ておいてください。

> **完了チェックを作るのは `security-review` だけです。** `code-review` はこの完了チェックに触りません。

### ② コードレビューを実行する（12分）

```text
コードレビューして
```

> **Spec軸は `README.md` を読みます。** 仕様が曖昧なままだと、このレビューはうまく動きません。

> **作法（Standards）の指摘についてはコードに慣れてない人は読めなくても、大丈夫です。** 
>
> 作法の指摘を全部「対象外」にしても、今日の完成判定には影響しません。

出てきた指摘を確認して、直すものを選んでください。必ずしも全部直す必要はありません。

```text
仕様の1と2、作法の1を直してください。残りは今日は対象外にします。
```

直さなかったものは、持ち帰りに回します。

```text
直さなかった指摘を、TASKS.md に「レビューで出た宿題」という見出しで書き足してください。
それぞれに重大度と、今日直さない理由を書いてください。
```

**`TASKS.md` にすべてのタスクと状態を記載しておきましょう。** レビューで出た宿題も、ここに集約させます。**重大度を残すのは、明日どれから手を付けるかが一目で決まるようにするため**です。

### ③ セキュリティレビューを実行する（4分）

```text
セキュリティレビューして
```

秘密情報の直書き・入力の未検証な使用などを、重大度つきで報告してくるはずです。見つかった問題は指示して直させてください（コピペ用テンプレ: [templates/verify-prompt.md](../templates/verify-prompt.md)。Skillが呼ばれないときはこちらで代用しても構いません）。

直したあとは、もう一度セキュリティレビューを通してください。直したことで、危なさの状態がまた変わっているからです。この「直したら通し直す」を、次の④で仕組みにします。

直さなかったものは、②と同じところへ残します。

```text
直さなかったセキュリティ指摘も、TASKS.md の「レビューで出た宿題」に書き足してください。
それぞれに重大度と、今日直さない理由を書いてください。
```

**ここを飛ばすと、いちばん危ない宿題だけが手元に残ります。** 12で外へ渡すのは、この見出しに書かれたものです。

### ④ Hookで「必ず実行される」ようにする（15分）

ここまでは、あなたが指示したときだけレビューが走りました。指示を忘れたら実行されません。

そこで、Hookを2つ設定します。

| Hook | タイミング | やること | 意味 |
|---|---|---|---|
| **A** | コードを編集した直後（PostToolUse / Edit・Write） | レビュー済みの完了チェックを消す | 変更したらレビューはやり直し |
| **B** | 外に出す直前（PreToolUse / Bash で `git push` や `wrangler deploy`） | 完了チェックが無ければ止める | 未レビューのものは外に出せない |

> **ただし、これはトリガタイミングに記載のとおり「保証」ではありません。** 捕捉できるのは、Claude Codeが Edit・Write でファイルを変えたときと、`git push`・`wrangler deploy` というコマンドを実行しようとしたときだけです。
>
> | すっぽ抜ける経路 | なぜ |
> |---|---|
> | 自分の手でファイルを直接編集する | Claude Codeを通らないのでHook Aが気づかない |
> | ブラウザから公開する（ルートA） | 同じく、Claude Codeを通らない |
> | 別の書き方で外に出す（`npm run deploy` など） | Hook Bはコマンドの文字列を見ているだけ |
>

気になったら後日改善してみてください。

```text
このプロジェクトの .claude/settings.json に、次の2つのHookを設定してください。

【Hook A】
- タイミング: ファイルを編集・作成した直後（PostToolUse、対象はEditとWrite）
- 内容: .claude/security-reviewed というファイルがあれば削除する

【Hook B】
- タイミング: Bashコマンドの実行直前（PreToolUse、対象はBash）
- 内容: 実行されようとしているコマンドに "git push" または "wrangler deploy" が
  含まれていて、かつ .claude/security-reviewed が無い場合は、そのコマンドを止めて
  「先に『セキュリティレビューして』を実行してください」という理由を返す
- 判定の中身は、次のURLから .claude/hooks/require-security-review.sh として
  保存し、実行できるようにしてください。settings.json からはそれを呼ぶ形にします
  https://raw.githubusercontent.com/AI-Eng-Dojo/getting-started-vibecoding/main/hooks/require-security-review.sh

あわせて .gitignore に .claude/security-reviewed を追加してください。
settings.json や必要なフォルダが無ければ作成してください。
```

> **判定スクリプトは、自分で書かずコピーして使います。** `tdd` や `security-review` と同じ扱いです（→ [hooks/README.md](../hooks/README.md)）。
>
> Hooksは権限プロンプトを経由せず自動実行されます（前半5）。だから原則は「中身を理解できるものだけを登録する」です。**その場でAIに書かせたスクリプトを、書いた本人の説明だけを頼りに登録するのは、この原則を満たしていません。** 検証済みのものを配るのはそのためです。

#### 止まることを自分の目で確認する

設定できたら `/clear` で会話を切り、わざと未レビューの状態を作って試します。

1. アプリのファイルを何か1つ編集させる（色を変える、など何でもよい）→ Hook Aが完了チェックを消します
2. そのままプッシュを頼む → Hook Bが止めるはずです

```text
いまの状態をコミットして、プッシュしてください。
```

3. 止められたら、あらためて `セキュリティレビューして` を実行する → 完了チェックが作られます
4. もう一度プッシュを頼む → 今度は通ります

**Skillは「呼べば動く」、Hookは「呼ばなくても止めてくれる」**ことを確認してください。

> **止まらないときは** `/hooks` で2つとも登録されているか確認してください。入っているのに動かない場合は、Claude Codeを一度終了して開き直してから再確認します。それでも直らなければ、Hookは一旦諦めて①〜③のレビューだけで11へ進んでください。今日の完成判定には影響しません。

## 11. ハンズオン⑧ Cloudflareに公開する（20分）

ここまで作ったものは、あなたのPCの中にしかありません。ファイルを開けば動きますが、隣の人に見せるには画面を覗いてもらうしかない。ここでそれを、**URLを送れば誰でも見られる状態**にします。

### なぜCloudflareなのか

今日のアプリはブラウザだけで動く静的なもの（HTML・CSS・JavaScript）です。サーバー側で動く処理もデータベースもありません。この形は**静的ホスティング**という一番シンプルな置き方で公開でき、Cloudflareはそれを無料枠で・世界中に配信される形で提供しています。

> **Cloudflareの中でも今の本流は「Workers」です。** 以前は静的サイト向けに「Pages」という別サービスがありましたが、Cloudflareは現在Workers側に機能投資を集約し、新規は Workers から始めることを推奨しています（Pagesも引き続き利用可能です）。この教材もWorkers側の手順で書いています。

### ステップ1: 公開するフォルダを分ける（全員・5分）

いま `myapp` フォルダには、公開したくないものが混ざっています。`README.md`（仕様）、`TASKS.md`（やること）、`CONTEXT.md`、`.claude/`（設定）は、あなたの作業用であって、世界中に見せるものではありません。**フォルダごと投げると、それら全部が一緒に公開されます。**

```text
公開用に public/ フォルダを作り、公開してよいファイルだけをそこに移動してください。
- 移動するもの: アプリのHTML・CSS・JavaScript・画像
- 移動しないもの: README.md・TASKS.md・CONTEXT.md・docs/・.claude/・.git/
移動したあと、ブラウザで public/index.html を開いて今までどおり動くことを確認できる状態にしてください。
```

移動できたら、必ず一度 `public/index.html` をブラウザで開いて動作を確認してください。ここで壊れていることに気づかずに公開すると、原因の切り分けが難しくなります。

そのうえで、もう一度だけレビューを通します。

```text
セキュリティレビューして。特に public/ に入れたファイルを、
これから全世界に公開してよいかという目で見てください。
```

「他人に渡して困るものが残っていないか」は、Skillの最後の観点そのものです。実装中は抽象的だったこの問いが、公開する直前にだけ具体的になります。

### ステップ2: 公開する（10分）

ルートは2つあります。自分に合うほうを選んでください。どちらでも「公開された」という体験は同じです。

| | ルートA: ドラッグ&ドロップ | ルートB: コマンドで公開 |
|---|---|---|
| 誰向け | **全員（本線）** | 〔Eng〕コマンドに抵抗がない人 |
| 必要なもの | ブラウザだけ | Cloudflareアカウント（Node.jsは全員導入済み） |
| 所要 | 2分 | 5〜10分 |
| Hookは効くか | 効かない（Claude Codeを通らないため） | **効く**（`wrangler deploy` で止まる） |

#### ルートA: Cloudflare Drop にドラッグ&ドロップする（全員・本線）

1. ブラウザで [cloudflare.com/drop](https://cloudflare.com/drop) を開く
2. ステップ1で作った `public/` フォルダを、そのままドラッグ&ドロップする（zipでも可）
3. URLが発行され、その場で公開されます

アカウントは要りません。ただし**このURLは1時間で消えます。** 残したい人は、表示されている Claim を押し、「Sign in with Google」から個人のGoogleアカウントでサインインしてください（事前準備0.1④と同じ経路です。アカウントが無ければその場で作られます）。Claimすると、そのままあなたのアカウントの中に恒久的なサイトとして残ります。

#### ルートB: `wrangler` で自分のアカウントに公開する〔エンジニア向け〕

Claude Codeにそのまま頼めます。

```text
このアプリを Cloudflare Workers の静的アセットとして公開したいです。
1. wrangler.jsonc を作り、assets の directory を ./public/ に向けてください（Worker のスクリプトは不要です）
2. npx wrangler login でログインしてください（ブラウザが開くので私が許可します）
3. npx wrangler whoami を実行して、ログインできているか確認してください。
   「You are not authenticated」と出たら、そのまま先に進まずに教えてください
4. 確認できたら npx wrangler deploy で公開し、発行されたURLを教えてください
```

> **3を飛ばさないでください。** `npx wrangler login` は、ブラウザの許可画面まで進みきらずに終わってもターミナル側にエラーを出しません。「ブラウザが開いた」はログインできた証拠ではありません。`npx wrangler whoami` でアカウント名が表示されて初めて、ログインできています。ここを飛ばすと失敗するのは4のデプロイなので、「デプロイが失敗した」ように見えて原因が分かりません。

**ここでHook Bに止められるはずです。** 1つ目で `wrangler.jsonc` を作った時点でファイルの書き込みが起きるので、Hook Aがレビュー済みの完了チェックを消します。その状態で3つ目のデプロイに進むため、Hook Bが「完了チェックが無い」と判定して止める、という流れです。故障ではありません。止まったら、そのまま続けてください。

```text
セキュリティレビューして
```

レビューが通れば完了チェックが作り直されるので、もう一度デプロイを頼めば今度は通ります。「設定を1行でも足したら、外に出す前にもう一度見る」が仕組みとして効いた瞬間です。面倒に見えますが、止めてほしいのはまさにこういう「あと一歩」の場面です。

できあがる `wrangler.jsonc` はこれだけです。中身を見て、何を公開しているのかを自分で把握してください。

```jsonc
{
  "name": "myapp",
  "compatibility_date": "2026-08-29",
  "assets": {
    "directory": "./public/"
  }
}
```

`directory` に書いたフォルダの中身が、そのまま公開されます。**ここが `./` になっていたら、リポジトリ全部が公開されます。** 必ず `./public/` を指していることを確認してください。

> `npx wrangler login` はブラウザでの許可操作が必要です。Claude Code側で止まって見えるときは、VS Codeのターミナル（「表示」→「ターミナル」）で自分で `npx wrangler login` を実行してから、あらためてデプロイを頼んでください。

### ステップ3: 自分の目で確認する（5分）

**発行されたURLを、自分のスマートフォンで開いてください。** PCのブラウザではなく、です。

- 意図したものが表示されるか
- 動かしてみて、PCで見たときと同じように動くか
- 見せたくないものが表示されていないか

確認できたら、URLを隣の人に送って開いてもらってください。他人の環境で開かれて初めて「公開した」ことになります。

最後に、ここまでの変更を保存します。`public/` への移動も `wrangler.jsonc` も、まだコミットされていません。

```text
いまの状態をコミットして、プッシュしてください。
公開URLを README.md の先頭に1行追記してからにしてください。
```

ルートAで公開した人も、ここでHook Bが止めてくるはずです。レビューを通してからもう一度頼んでください。「外に出す前に必ず見る」が、pushでもデプロイでも同じように効くことを、ここで確認できます。

> **公開したということの意味。** URLを知っている人は誰でも見られます（検索には出にくいですが、秘密ではありません）。あなたのアプリがブラウザに保存しているデータ（`localStorage` など）は見る人ごとに別々で、あなたの手元のデータが相手に見えることはありません。逆に言えば、あなたが入力したデータは公開されていないということです。ここを混同しないでください。

> **見せる相手を絞りたくなったら。** 「まだ人に見せる段階じゃない」「知り合いにだけ見せたい」という場合は、Basic認証（開くときにIDとパスワードを求める、一番簡単な鍵）をかける手があります。とくに、持ち帰ってAIを組み込んだ人には必要になります。生成の裏でお金がかかるものを誰でも叩ける状態にしておくと、URLを知った人の分まであなたに請求が来ます（→ 🚀拡張ミッション④）。

## 12. ハンズオン⑨ 仕事の道具とMCPでつなぐ（15分）

### MCPをつなぐ（8分）

どちらか片方で構いません。迷ったらネイティブ統合されているNotionがよいでしょう。

#### Notion — ネイティブ統合あり、つなぐだけ

#### Backlog — ネイティブ統合なし、自分でMCPサーバーを設定する

Backlogはclaude.aiのコネクタ一覧にはありません。自分でMCPサーバーを追加します。

> このルートはNode.jsを使います（MCPサーバーを `npx` で起動するため）。事前準備0.2で全員入れているので、そのまま進めて構いません。ターミナルで `node -v` を実行してバージョンが出ない場合だけ、Notion側を選んでください。

```text

- 環境変数: BACKLOG_DOMAIN=⟨自分のスペース⟩.backlog.com、BACKLOG_API_KEY=⟨発行したAPIキー⟩
- スコープはuser（このPCの自分だけ・このリポジトリにはコミットされない）にしてください
```

> **バージョンを固定しているのは意図的です。** `npx backlog-mcp-server` のようにバージョンを書かないと、そのとき最新のものが取ってきて実行されます。何が動くかが日によって変わるということなので、中身を確認したものだけを動かすために番号まで書きます。前半5でHooksについて言ったこと（「中身を理解できるものだけを登録する」）と同じ考え方です。

> **APIキーは絶対にリポジトリにコミットしないでください。** `myapp` は15分ごとにpushしている、しかも11で公開までしたリポジトリです。スコープを `project` にすると設定がリポジトリ内の `.mcp.json` に書き込まれ、**pushした瞬間にAPIキーが漏れます。** 上のように `user` スコープを指定すれば、設定は自分のPCの中だけに保存され、リポジトリには一切含まれません。これは10でレビューした「秘密情報がコードに書かれていないか」と、まったく同じ観点です。

## 14. クロージング（3分）

### 今日やったこと

```
バイブコーディング → Intentの明確化 → Skillによる拡張 → 仕様化 → 計画 → 実装 → レビュー → デプロイ
```

このハンズオン自体が、この一連の流れを体験する教材でした。前半で「ノリで作れてしまう」体験をし、その後「何を作りたいのかを明確にする」壁にぶつかり、自分で作ったSkillでそれを乗り越え、後半でIntentを実際のソフトウェアに変換し、最後に世界から見える場所に置きました。

**いちばん持ち帰ってほしいのは、Skillに数行足しただけで宿題の持ち物が変わった、という体験です。** 仕組みを設計すると、出てくるものが変わる。今日いじったのは、AIの振る舞いそのものでした。

そしてもう1つ。レビューは「気をつける」ではなく仕組みに寄せました（Hook A・B）。公開する範囲は「気をつける」ではなくフォルダを分けることで担保しました（`public/`）。**人の注意力に頼らない形に落とすこと。** これが、動くものを作れるようになった次に効いてくる差です。ただし今日のHookは完全ではありません（10④で見たとおり、手編集やブラウザからの公開は抜けます）。「どこまでを仕組みが見ていて、どこからは見ていないのか」を自分で言えることまで含めて、持ち帰ってほしい部分です。

工程を分けたことにも意味があります。`tdd` は整えず、`code-review` は危なさを見ず、`security-review` だけが「外に出してよい」の完了チェックを作る。1つのスキルに全部を入れると、報告が混ざって何も見えなくなります。小さく分けて、噛み合わせる。今日いじったのはAIの振る舞いであると同時に、工程の設計でした。
